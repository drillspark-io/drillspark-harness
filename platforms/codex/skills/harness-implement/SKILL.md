# 図からCodexのハーネスを作る

[実行規約](../../reference/runtime.md)、[共通手順](../../reference/workflow-contract.md)、
[Codex対応表](../../reference/MAPPING.md)、[設計の問い](FRONTIER.md) を読む。
MCP接続を確認し、docs/harness/<name>/の索引と工程成果物を読んで再開する。
業務改善/AI化依頼書.mdがあるなら改善案・業務一覧・保留も読み、目的や承認点を聞き直さない。
依頼書の「業務名」が処理で、その行の作業は工程。混同しない。

1. 目的を定義する。対象者、成果物、成功指標、対象外、実行環境と生成先を設計.mdへ記録する。
   不明点は既存資料で調べ、利用者固有の判断だけ確認する。目的と処理一覧の合意を記録する。
2. このセッションで扱う処理1つを選ぶ。工程の骨格を1枚作り承認を受け、工程内の作業を
   1枚ずつ作って承認を受ける。create_project直後に処理/<name>/図.mdへURLを記録する。
   get_diagram_rules、diagram-lint、validate_diagramを使う。図ごとの5種の介入点、成果物、
   検査担当、ループ上限とエスカレーション先を明記し、親子の備考を一致させる。
3. 承認済み図を再取得し、成果物一覧・ファイル仕様・介入点・依存関係を抽出する。
   通す入力/止める入力と期待値を実行可能なテストへ落とす。合格条件.mdを提示し、承認後に凍結する。
   `FRONTIER.md` の問いを確認し、図が決めていない権限・停止点・再開点を憶測で補わない。
4. Codex対応表に従い実体を依存順に作る。skillは .agents/skills、agentは .codex/agents のTOML、
   hookの実体は .codex/hooks。全体のAGENTS.md/config.toml/hooks.jsonは統合へ渡す仕様に留める。
   必要な常駐指示、必要時だけ読む資料、別コンテキスト、機械強制を使い分ける。
   判断（置き場、粒度、権限、停止と再開、入力/出力、検査、失敗時の扱い）を実装.mdに残す。
5. `harness-design-reviewer` を別エージェントで起動し、図と現物と固定基準を独自に調べさせる。
   指摘を修正して凍結テストを実行する。条件・判定基準を実装に合わせて編集しない。
6. 実装.mdに作ったもの・箇所・テスト結果・未対応・統合へ渡す仕様を保存する。
   file-saved-lintで実在を確認後、索引を実装済みにする。未検証を合格扱いにしない。

雛形は [設計.md.template](../../reference/設計.md.template)。
別処理は新しいセッション。全処理が揃ってからharness-compose、再起動後の評価は独立したharness-evaluator。
設定の読込や実タスクは生成した同一セッションでは確認済みにしない。

### 先に自分で固める判断

実装前に次を決め、処理/<name>/実装.mdの「実装前判断の答え」へ残す。該当しないものも「無し」と書く。
判断の根拠が利用者固有の方針なら確認し、技術的に調べられることは自分で調べる。

1. 置き場: 常駐する索引、必要時の手順、パス限定指示、別agentをCodex対応表で分ける。
2. 強制の方法: 指示だけで不足する条件をhookや権限へ割り当て、強制できない範囲を明記する。
3. 人間の介入点: 5種類を起動・回答待ち・人間作業・通知先・基準管理へ割り当てる。
4. 停止と再開: 回数上限、予算、無進展、強制停止と再開ファイルを決める。機械的に保証しない予算を保証と書かない。
5. 検証の分離: 別コンテキスト、固定基準、実際の書込制限を確認する。
6. 削る: 標準機能で足りる部品は足さない。足さなかった候補と理由も残す。
