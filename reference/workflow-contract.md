# DrillSpark Harness — 共通のワークフロー契約

Claude Code / Codex の両版が使う業務上の意味。実行ツール・設定の書式は各環境の入口と対応表に従う。

## 図と工程

- 処理 = 独立した仕事ひとつ。1処理 = 1 DrillSparkプロジェクト。1ハーネスはフォルダにまとめる。
- 第一階層は工程、第二階層は工程内の作業。工程が渡す成果物と検査担当も図にする。
- 工程をまとめて承認させない。骨格1枚→その承認→工程内の作業1枚→その承認の順。
- マクロ図のレーンは工程、ドリルダウンは担当。マクロの点線をエージェント委譲と誤読しない。
- get_diagram_rules の現行全文を取得してから作図する。validate_diagram とローカル diagram-lint の両方を通す。
- 生成側とレビュー側は別コンテキスト。レビュー側は根拠を独自に読み、指摘を返す。自分の生成物の自己採点を合格判定に使わない。
- 未確認の事実に相談先、一般知識からの補完に「一般例」を付ける。実測と見積もりを区別する。

## 書類の表現

- 書類を受け取る・参照する・作成する・確認する・渡す工程では、その書類を document ノードで明示する。
  請求書・申請書・見積書・報告書・チェックリスト・記事原稿など、紙と電子ファイルの両方を含む。
  現状図・改善後の図・ハーネス設計図の第一階層と第二階層に適用し、その図で必要な書類を描く。
- 書類は `6@{ shape: doc, label: "請求書" }` の形式にする。実際の書類名をラベルにし、
  「請求書を発行する」のような作業は通常の作業ノードとして別に残す。
  書類名を作業のラベルや備考に書くだけで、書類ノードの代わりにしない。
- 関連する作業の脇に置き、参照する書類→作業、作業→作成した書類の向きで接続する。
  接続線は現行のレーン・線種ルールに従う。書類を通らない作業間の制御フローを保ち、
  書類を手順の途中に挟んだり、書類への接続を判断の分岐として扱ったりしない。
- 書類ノードには `%% duration[6]: 0` を付け、作成・確認にかかる時間は対応する作業へ記録する。
  分かっている保存先・形式・用途は備考に記録する。工程間で渡す書類はどこで作り、どこで使うかを明確にする。
- 書類がない業務に架空の書類を追加しない。必要性や名称が不明なら確認する。
  データベースやシステム自体は書類と区別する。レビューでは入力・出力の書類が図から漏れていないか確認する。

## 人間の介入点


起動・承認・人間が実行する作業・エスカレーション先・基準の決定の5種類を記録する。
承認は応答を受け取るまで未成立。拒否/修正要求は該当工程へ戻し、後続の変更をしない。
中断時は対象図・承認範囲・保留と相談先・修正回数・次の入力をファイルへ残す。
同じ承認範囲について既に明確な指示があるなら聞き直さない。範囲が変わったときだけ確認する。

## 業務改善

1. 業務一覧: 担当・きっかけ・作業・道具・渡し先・頻度×時間・実測/未計測・目的・聞いた相手を整理する。
2. 利用者が一覧を確認し、process-abc で月間時間を計算して改善対象を選ぶ。
3. 現状を工程→工程内の作業の順で描き、それぞれ利用者が確認する。
4. 成功の形を決め、ECRS（なくす→まとめる→並べ替える→簡単にする）の順で一問ずつ検討する。
5. 改善後の図を現状と比較し、誰がやるか・優先度・時間の根拠を明記する。
6. AI化依頼書にH1–H5、承認する操作、保留と相談先を記録し、別のレビュー役が共通基準で確認する。

表の列・値・H1–H5の定義は [business-improvement-tables.md](business-improvement-tables.md)、
判定は [business-improvement-criteria.md](business-improvement-criteria.md) を唯一の正本とする。
利用者の業務を実際に自動化する工程には入らない。依頼書は設定生成への入力。
別業務へ移るかは利用者が決める。会話の教訓は最大10行にまとめる。

## ハーネス生成と改善

1. 目的: 誰のため・成果物・成功指標・対象外。成功指標は満たしても目的未達になる例も考える。
2. 処理一覧: 独立した入力・出力・担当・目的の単位で整理する。工程を処理として水増ししない。
3. 1回1処理、別処理は新しいセッション。図を1枚ずつ確認する。
4. 図から成果物・介入点・機械テストを導く。仕様にない決定は根拠を調べ、利用者固有の判断だけ質問する。
5. 合格条件を利用者の承認で凍結する。実装失敗に合わせて条件や同梱の評価基準を緩めない。
6. 実体を依存順に実装し、別レビュー役の指摘を修正し、凍結したテストを走らせる。
7. 全処理が揃ってから統合する。既存の無関係な設定と制限は保持する。重複するフックの実行順を仮定しない。
8. 新しいセッションで登録と動作を確かめ、実タスク・人間の停止点・成功指標を評価する。
9. 改善は現状の実ファイル→現状図の照合→理想図の承認→差分の引き渡し。改善役は設定を直接修正しない。

工程成果物は `docs/harness/<name>/` に保存する。雛形は [設計.md.template](設計.md.template)。
各工程でファイルを書く→file-saved-lint→索引の状態更新の順。状態は未着手/図 確定/合格条件 凍結/実装済み。
索引に詳細を複製しない。評価未実施を実装済みと混同しない。
衝突・理想図の修正は3往復まで。解決しなければ保留と根拠を利用者へ返す。

## 可視化

- process-improve-view: 対象業務1件、4つの業務表が入力。8ブロックの自己完結HTML。
  同じ業務のページを更新する。表の順序・事実・印を保持し、独自に評価しない。
- harness-visualize: 対象処理1件、図・設計・実装記録・評価記録を重ねる。
  全ノードを実装箇所と結び、未評価は未評価のまま表示する。別実行は別名、同実行の直しは2回まで。
- 図の取得失敗を描いたふりで埋めない。いつ・何を・どう取得し・何が返り・次に何が必要かを示す。
- スクリプトとlintが定義する形式を保ち、保存後に読み戻す。閲覧ページから外部への公開は別の利用者指示が必要。
