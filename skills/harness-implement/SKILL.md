# harness-implement — 目的から作図して設定に落とす

7つの工程のうち**〈目的を考える〉から〈評価する〉までを担当**する。〈改善する〉は `harness-improve` へ渡す。

```
目的を考える → 処理の種類を考える → 処理を作る → 合格条件を決める → 実装する → 評価する →（改善する）
```

**承認は図までに集約する。** 図が契約で、その下（実装の中身）は図と合格条件から導く。
図より下に人間のゲートを置くと、オーナーが判断できない情報でゲートが埋まる（2026-08-24 実測）。
実装前に残すゲートは**合格条件の凍結1つだけ**。

**処理**＝ハーネスが持つ独立したワークフロー（ブログを書く・動画を作る）。**工程**＝その処理の中身。
混ぜると工程が壊れる。適用先は常に Claude Code なので対応表は1つで済む。

**`設計.md` の置き場は `docs/harness/<ハーネス名>/設計.md`。**
〈目的を考える〉〈処理の種類を考える〉の成果・〈合格条件を決める〉の成果物一覧と合格条件・
〈実装する〉の記録が1つのファイルに集まる。
〈評価する〉の評価は**このファイルだけを物差しにする**ので、ここに無いものは測れない。
雛形: [`reference/設計.md.template`](../../reference/設計.md.template)

**合格条件は実装より先に書く。** あとから書くと実装に合わせて条件のほうが緩む。
承認された時点で凍結し、〈実装する〉は「実装を直す」ことでしか通さない。
この1本が〈実装する〉の完了判定と〈評価する〉の評価の両方を兼ねる。

→ 対応表 [MAPPING.md](MAPPING.md)（変換時に必ず読む）／問いの立て方 [FRONTIER.md](FRONTIER.md)

図がすでにあるなら〈目的を考える〉〈処理の種類を考える〉〈処理を作る〉を飛ばして〈合格条件を決める〉から入る。

**工程を自動で連鎖させない。** 各工程の Start は**人間の介入点（起動）**で、
1工程を終えたらそこで止まり、オーナーが次を指示してから進む。承認ゲートを通っても、
それは「その工程の成果物を認めた」だけで「次を始めてよい」ではない。
まとめて走らせると、途中で方針が変わったときに捨てる量が工程の数だけ増える。

## 始める前に — DrillSpark に繋がるか確かめる

**DrillSpark は必須。図が契約なので、図が無いと承認する対象そのものが無い。**

**工程1に入る前に `mcp__drillspark__list_projects()` を1回だけ流す。** 繋がっていれば何も言わずに進む。
繋がっていなければ**そこで止めて案内する** — 手順・症状の切り分け・案内の文面は
[`reference/drillspark-setup.md`](../../reference/drillspark-setup.md)。

**繋がらないときに代わりの手段で進めない。** CLI に mermaid を貼る・図を飛ばして
`設計.md` の文章だけで実装へ進む、のどちらもしない。
**図が要るのは工程3だが、確認は工程1より前に置く** — 工程3で詰まると、
承認ゲートを2つ通した成果（目的・処理一覧）が宙に浮く。

## 出力の作法

**この節は全工程に効く。** 2026-08-24 の実測で、オーナーから同じ型の指摘が9回出た。
原因は1つ — この手順書が「何を作るか」を細かく規定しながら、**「どう出すか」を一度も規定していなかった**。
その結果、実行役は手元にある情報を一度に全部吐く。

1. **段階的に出す。** 一度に全部出さない。1画面で読み切れる量に切る
2. **現在地を出す。** 出力の先頭に1行 — `[4/7 合格条件を決める ｜ 図 4枚目/5枚 ｜ 次: 実装する]`。
   工程に入るときは「この工程が全体のどこで、何を決める場か」を1〜2行で述べる
3. **利用者の言葉で書く。** 作り手の語彙を利用者向けの文面に出さない（下の注釈表）
4. **内部IDを利用者向けの文面に出さない。** 図のノード番号は作業中の参照用であって、
   オーナーはその図を見ていない。ゲートは工程名で名乗る（「目的の承認」であって「承認ゲート 2_7」ではない）
5. **質問は `AskUserQuestion` で出す。** テキストで番号付きの質問を並べない。
   1回4問までなので多いときは分ける。自由記述が要る問いも、想定される答えを選択肢に出したうえで
   自由記述を受ける
6. **CLI で ASCII の作図をしない。** 図は DrillSpark のリンクに任せ、
   CLI にはレーンごとの箇条書きで「どの順に何をするか」だけ出す
7. **ゲートで出すのは3つだけ** — ①決まったこと ②**守られない可能性がある点**（リスクの言葉で）
   ③判断してほしい1点。レビューの往復や内部の修正表は `設計.md` に残し、CLI に出さない
8. **長い文書は要約を出し、全文を見るかを選ばせる。** 「438行です。全文を確認しますか、要約で承認しますか」

### 人間の介入点5種 — 利用者に見せるときは必ず注釈を付ける

この5語は判定基準の MUST の書式そのものなので**改名しない**。**注釈を付ける。**

| 内部の語 | 利用者向けの言い方 |
|---|---|
| 起動 | 誰がその作業を始めるか。人が毎回言って始めるのか、自動で始まるのか |
| 承認ゲート | 途中で必ず止まって、人に見せて確認する場所 |
| 実行 | 機械にはできず、人がやるしかない作業 |
| エスカレーション先 | うまくいかないとき、誰のところへ上げるか |
| 基準の決定 | 合格・不合格の線を誰が引くか |

### 実装の語も言い換える

| 内部の語 | 利用者向けの言い方 |
|---|---|
| hook の `exit 2` | 書き出した瞬間に自動で検査が走り、落ちたら**書き込みを止めて**理由を返す |
| お願い／柵 | 本文に「必ず通すこと」と書くだけだと破れる。機械が必ず走る形にした |
| 検証役の分離 | 合否を持つのは書いた本人ではなく検査の側。基準も本人が書き換えられない場所に置く |
| MUST／傾向 | 落ちたら差し戻す1本／記録するだけで差し戻さないもの |
| `permissions.deny` ／ `ask` | そのファイルを書けなくする設定／書く前に確認ダイアログが必ず出る設定 |

## 絶対に飛ばさない4点

ハーネス設定の変更は HarnessRisk 実測で**最脆弱フェーズ**。以下は手順であって推奨ではない。

1. **承認を2段で取る。** ①**合格条件**を凍結してから作り始める。
   ②**実行をその場で変えるもの**は、書く前に内容そのものの承認を取る —
   `settings.json` の hook と権限、および**既に `settings.json` から参照されているスクリプト**。
   hook はファイル監視で**書いた瞬間から全操作に効く**ので、書いてから見せるのでは遅い。
   skill / agent / rules / 未参照のスクリプトは呼ばれるまで効かないので、作ってから見せてよい
2. **成功メッセージを完了根拠にしない。** 生成・保存後は必ず読み戻して中身を確認する
   （`update_diagram` が success を返しつつ内容が巻き戻っていた実例がある）
3. **再実行は図1枚単位。** 全体を作り直さず、指定された図に対応する成果物だけ出し直す
4. **検証基準を生成側に置かない。** GO判定・lint基準は、それを満たす側が書き換えられない場所へ

## 目的を考える

**担当はオーナー。** エージェントは調べて問いを立てるだけで、答えを決めない。

**事実を調べるのは自分の仕事。** リポジトリ・コミット履歴・既存の設定で分かることを人間に聞かない。
調べたうえで、**決まっていないことをまとめて1ラウンドで問う**。1問ずつ聞かない。
各問に推奨と「逆を選ぶとどうなるか」を付ける。**上限は3ラウンド** — 超えたら打ち切り、
決まらなかった点を保留として明記して先へ進む。

**3は上限であってノルマではない。** 未決がゼロになった時点で終わる。1ラウンドで空になれば1回で終える。
**答えの出た問いを次のラウンドで再掲しない。** 2ラウンド目に出してよいのは、
前のラウンドの答えで**初めて前提が固まった**問いだけ（→ [FRONTIER.md](FRONTIER.md) 1「決定木として扱う」）。
納得のいく答えが出た問いをもう一度出すと、オーナーには「答えても進まない」ように見え、
上限の3が消化ノルマとして働きはじめる。

**ラウンド数は会話で数えず、`設計.md` の「保留中の論点」に何ラウンド目かを書いて数える。**
**実行役は自分のラウンド数を数えられない**（2026-08-23 実測。上限は人間が手で管理していた）。
書いておけば、文脈が切れても続きから数えられる。

決めるのは4つ。**誰のためか / 何を成果物とするか（パスまで）/ 成功を何で測るか / やらないことは何か。**

**成功指標はオーナーが決める。エージェントは案を出すだけ。**
合否の線（MUST）は1〜2本に絞り、残りは傾向として記録する — 線を増やすほどどれも守られなくなる。
**その指標が満点でも目的が未達になる型**を1つ書く（Goodhart 対策）。

成果物は `設計.md` という**文章**。図にしない — 目的はフローではないので、図にすると嘘になる。
最後に**目的の承認**を取る。差し戻しは人間が毎回判断するので回数の上限を置かない。

## 処理の種類を考える

`設計.md` の目的から処理の候補を挙げ、**入口・出口・失敗経路・定期実行・人間の関与**の5観点で抜けを埋める。
目的に書かれていない処理を勝手に足さない。

- **入口** — 何が来たら始まるか（誰が起動するか・入力は何か）
- **出口** — 終わったとき何が出来ているか（成果物とその置き場）
- **失敗経路** — うまくいかないときどこへ行くか
- **定期実行** — 決まった時間に自動で動くのか、毎回人が起動するのか
- **人間の関与** — どこで人が止まる・決める・手を動かすか

**まだ矢印を引かない。** 種類を漏れなく並べることだけに集中する。
先に線を引くと、つなぎやすい処理だけが残って抜けに気づけなくなる。
5つとも埋まって初めてオーナーに見せる。埋まっていない欄は「未定」と書く —
空欄のまま出すと、抜けているのか決まっていないのかが区別できない。

数が多ければ**分類してまとめ**、`設計.md` に一覧として記入する。処理を消して数を合わせない。
却下したものは却下したと残す。どう作図するか・プロジェクトをどう分けるかは、この工程では決めない。

**人間の介入点が2つある。飛ばさない。**

1. **【人間の実行】種類の過不足を答えてもらう** — 一覧を出したら**そこで止めて聞く**。
   ドメインを知らないと出てこない処理がある。エージェントが出した一覧は叩き台でしかない
2. **【承認ゲート】処理一覧はこれでよいか** — `設計.md` に書いたあと、確定する前に止める。
   処理一覧は**以降のすべての作図の入力**で、ここが違うと全部の図が無駄になる。
   あとから処理を足すときも必ずこのゲートを通す — 一覧に載らない処理は〈評価する〉の実タスク通しと
   過不足監査から漏れる

## 処理を作る

**1処理＝1 DrillSpark プロジェクト。** 図の書き方は `get_diagram_rules()` と MAPPING.md 2節。

### 階層の規約

**第一階層（ルート図）には工程だけを置き、第二階層以下に作業を置く。**
混ぜると読み手が「いま何の粒度を見ているか」を見失う。

| 階層 | 何を置くか |
|---|---|
| ルート図 | **工程だけ。** ドリルダウンを持つノード（サブプロセス）として置く。工程の中の手順を書かない |
| 第二階層以下 | **作業。** その工程の中で実際に手を動かす単位 |

作業が5〜10に収まらなければ、**ノードを小さく詰め込まずに階層を1段足す。**

### 1枚ずつ描いて1枚ずつ確認する

**まとめて描かない。** 最初の1枚はルート図（骨格）で、骨格が違うと下のドリルダウンが全部無駄になる。

```
図を1枚描く → 構造 lint → 【承認ゲート】この図でよいか → 残りがあれば次の1枚へ
```

**機械が見るものを人間のゲートへ持ち込まない。**
数値ID・二重引用符ラベル・`%% duration`・多出力・到達性・レーンと線種・IDの重複は
`node scripts/harness-diagram-lint.js <file>` が見る。目視で数え直さない。lint を通してからオーナーに見せる。

ループが3つ出るが、**回数の上限が要るものは1つも無い。**

| ループ | 上限 | 理由 |
|---|---|---|
| lint 不合格 → 描き直す | 不要 | 機械判定。直せば必ず抜ける |
| 承認 いいえ → 描き直す | 不要 | 人間が毎回判断する。止めるのは人間 |
| 残っている図 → 次の1枚 | 不要 | 件数で終わる反復。枚数が減るので必ず止まる |

**上限が要るのは「同じことをやり直す」ループだけ。** この線引きが無いと健全な反復まで差し戻し対象になる。

## 合格条件を決める

**この工程が実装前の最後のゲート。** 元は〈設計する〉という工程で、概要設計・詳細設計・
レビュー2回・承認を積んでいた（実測 145分）。**オーナーが判断できない情報でゲートが埋まった**ので、
合格条件を決めることだけに絞り、設計のレビューは〈実装する〉の内側へ移した。

### 図を取る

```
mcp__drillspark__get_project(project_id)   # 全図が一度に取れる
mcp__drillspark__get_diagram_rules()       # 作図規約。読み取り時も参照する
```

図1枚単位の再適用なら、対象のドリルダウン図＋その親図だけを見る。

### 構造を決定論的に抽出する

LLM の読解に頼らず、まず機械的に取れるものを取る。取れないものだけ散文から読む。

| 決定論で取る | 散文（備考）から読む |
|---|---|
| ノードID・形状・ラベル・所属レーン | 設計根拠・原則 |
| エッジの向き・実線/点線・ラベル | ループ上限などの回数制限 |
| 備考のDSL行（`lane:` `hook:` `permission:` `rule:`） | 生成先パス・制約 |

無視する要素（`click` / `classDef` / `style` / `rowOrder` / `duration` 等）は MAPPING.md 7節。

### 図から成果物の一覧を出す

図のノード・レーン・ゲート・停止点を、作るファイルへ割り付ける。

| | |
|---|---|
| skill | `.claude/skills/<name>/SKILL.md` |
| agent | `.claude/agents/<name>.md` |
| hook 定義 | `.claude/settings.json` の `hooks` |
| hook 実体 | `.claude/hooks/<name>.js` |
| 恒常ルール | `CLAUDE.md` / `.claude/rules/<topic>.md` |

**両方向で突き合わせる。** 対応物の無いノードと、根拠のノードが無い成果物の両方を見る。
片方向だけ見ると、落としたノードか勝手に足した成果物のどちらかを必ず見逃す。

**図に無いものをここで足さない。** 足したくなったら図へ戻す — 図が契約なので、契約の外で増やさない。

### 図に無い決定を1ラウンドで聞く

図に無い決定を**黙って仮定しない**。仮定した箇所がそのまま欠陥になる。

**この工程がオーナーに問える最後の場所**なので、前提が決まっている問い（＝フロンティア）を
全部洗い出し、**1ラウンドでまとめて聞く**。各問に「推奨・理由・逆を選ぶとどうなるか」を付ける。
**事実を調べるのは自分の仕事。** 調べられないもの（私的情報・組織の方針・未決の運用）だけ聞く。

**調査は本体でやらずサブエージェントへ投げる。** 問いの数だけ調査が走ると中間結果で文脈が埋まる。
`Explore` か `general-purpose` に投げ、結論だけ受け取る。**調査で止まらない。**

→ 網羅チェックリスト11項目は [FRONTIER.md](FRONTIER.md)

### 合格条件をテストデータで書く

**決定論で判定できるものだけ**を実データで書き、**コピペでそのまま実行できる形**にする（実行コマンドまで）。
置き場は `.claude/tests/<ハーネス名>/`。

| 種類 | 書くテストデータ |
|---|---|
| hook | 流すイベント JSON と期待する終了コード。**通す入力で 0・止める入力で 2** を両方 |
| lint・スクリプト | 違反サンプルと合格サンプル、引数、期待する標準出力 |
| skill・agent | 登録を確かめるコマンド（`claude plugin validate --strict` / `/skills` / `/agents`） |
| 図 | `node scripts/harness-diagram-lint.js <file>`（構造。`validate_diagram` は構文しか見ない） |

**終了コードだけを見る合格条件にしない。** 全部 exit 2 を返すだけの壊れた lint も
「違反サンプルで 2」を満たしてしまう。**違反サンプル1件につき、意図した指摘が1件だけ出ること**まで確かめる。

**決定論で判定できないものは合格条件にしない。** 人間の目に頼る判定は `設計.md` の**成功指標**として書き、
〈評価する〉で人間が測る。推測で埋めない。

### 人間の介入点5種を表にする

起動・承認ゲート・実行・エスカレーション先・基準の決定を、
**どの図のどのノードから来たか**と**どのファイルのどの記述で実現するか**の対で並べる。
1つも無いなら「無し」と明記する — 書かないのと「無い」と書くのは違う。

### 凍結する

一覧・合格条件・介入点の表をオーナーに見せて承認を取る。**出すのは3つだけ**（→〈出力の作法〉7）。
**承認された合格条件はここで凍結する。**以降、通らないときに直すのは実装であって条件ではない。

**凍結の解き方も決めておく。** 後から変えるときは `harness-improve` の**評価基準の変更承認ゲート**を通す。
「判定に落ちたから基準を緩める」向きの変更はそこで却下される。
凍結だけして解き方を決めないと、結局は無審査で書き換えられる。

## 実装する

**図と凍結した合格条件から一気に作る。** 工程に分けて人間を逐一止めない。
止めるのは検証役と機械であって、人間ではない。

### 先に自分で固める6判断

人間には聞かない。ここで決めきる。

1. **置き場を決める** — 常時オンにしてよいものだけ `CLAUDE.md`（目次・200行以内）。
   30行超の手順は skill、パス限定は `paths:` 付き rule、見せたくない脇道は agent。→ MAPPING.md 3.1節
2. **お願いを仕組みへ格上げする** — 「必ず」「絶対にするな」を指示文に残さない。
   hook の exit 2 と `permissions.deny` へ移す。指示は破れるが柵は破れない
3. **人間の介入点を機構へ割り当てる** — 5種を skill 起動 / cron / ゲートで止まる / 通知先 /
   書き換え不能な置き場のどれにするか決める。承認を連打させる設計は承認そのものを無力化する
4. **ループの止め方と再開点を決める** — 上限回数・予算・無進展の検知・強制停止の4つと、
   途中で落ちたときどこから戻るか
5. **検証役を生成役から分離する** — 判定基準は、それを満たす側が書き換えられない場所へ
6. **削る** — 標準機能で足りるものは足さない。モデルが自力でやるようになった指示は消す

### 各ファイルの仕様を決めて依存順に作る

MAPPING.md をそのまま適用する。**表に無い要素を推測で埋めない。**
推測が避けられない箇所は **⚠ 推測** と明記して記録に残す。

| 種類 | 決めること |
|---|---|
| hook | イベント / `matcher` と `if` の2段 / 終了コード / 止めたとき Claude へ渡す文 |
| skill・agent | frontmatter の値そのもの（→ MAPPING.md 6.1 の綴り対照表） |
| スクリプト | 引数・標準入出力・終了コード |

**依存順は、参照される実体（スクリプト → skill / agent / rules）が先、`settings.json` が最後。**
この順にすると、最後に書くものがちょうど一番危ないものになる。
**既存ファイルを上書きしないことを先に確認する。**
特に **skill と agent で同義フィールドの綴りが違う**（skill は `disallowed-tools`、agent は `disallowedTools`）。

### 別インスタンスにレビューさせる

作り終えたら **`harness-design-reviewer` に見せる**。**ここで人間を止めない。**
生成役とは別インスタンスが、6判断すべてに答えがあるか・お願いのまま残した強制がないか・
介入点5種が機構に紐づいているか・ループに上限とエスカレーション先があるかを見る。
レビュー役は**指摘だけを返し、直さない**。判定線は
[`reference/harness-design-criteria.md`](../../reference/harness-design-criteria.md)。
**ここで基準のほうを緩めない。**

### 合格条件を走らせる

〈合格条件を決める〉で凍結したものをそのまま走らせる。落ちたら**実装を直す。条件のほうを直さない。**

Claude Code は**壊れた定義を黙って無視する**。agent に `name` が無ければドキュメント扱いで
一覧にすら出ず、`description` 欠落や YAML 破損は debug ログにしか出ない。書き込んだら読み戻す。

**直しは通算3回まで。** レビューの差し戻しと合格条件の不合格を**合わせて**数える。
**会話で数えず、状態をファイルに残して数える** — 会話が長くなると数え直せなくなる。
超えたら**オーナーへ報告して止まる**。何がどの基準になぜ落ちたかを再現手順つきで添える。勝手に4回目を試さない。

### 実行を変える設定は、書く前に内容を見せる

実体が揃ったら、`settings.json` に**実際に書き込む JSON そのもの**を提示して止まる。
仕様の再掲ではない。hook なら、イベント・`matcher` と `if` の2段・ブロックの終了コード・
**止めたとき Claude へ渡す文**まで含める。
「ダメです」だけ返すと Claude は別経路を探し始めるので、代わりにどうすればよいかを書く。

承認後に書き込み、JSON パースと `/hooks` の登録を確認する。

### 最後に、セッションの再起動を促す

**【人間の実行】これは機械にはできない。** 書き終えたら**必ずオーナーに再起動を頼む。**

**書けた ≠ 登録された。** ファイルがあることを登録の証拠にしない。
セッション開始時に無かったディレクトリを新設した場合、再起動しないと skill・agent・hook が登録されない。
ここを飛ばすと、**書けたが動かないものを合格と数えたまま**〈評価する〉へ進む（2026-08-24 実測で検出）。

最後に、参照した図のIDと `updated_at`・作った成果物・判断した ⚠・未完を記録する。

### 基準と合格条件はどこで作るか

判定に使うものは3層あり、**作る場所と作る人が違う**。混ぜると検証の独立性が消える。

| | 何を測るか | 誰が作るか | いつ | どこに置くか |
|---|---|---|---|---|
| **成功指標** | 目的を達成したか（人間の目で測る） | **オーナー** | 〈目的を考える〉 | `設計.md` |
| **評価基準** | GO / NO-GO の線（MUST / 傾向） | エージェントが**降ろす**だけ | 〈合格条件を決める〉 | `.claude/rules/<topic>.md` のみ |
| **合格条件** | 決定論で判定できるテスト | エージェント | 〈合格条件を決める〉 | `.claude/tests/<ハーネス名>/` |

**評価基準はここで発明しない。** 〈目的を考える〉でオーナーが決めた「成功を何で測るか」「やらないこと」から
降ろすだけ。エージェントが基準そのものを起草すると、満たしやすい基準に寄る。

**評価基準を `CLAUDE.md` に置かない。** `CLAUDE.md` は実装役が通常運用で編集する場所なので、
そこに置いた瞬間に「生成側から書き換えない」が成立しなくなる。`.claude/rules/<topic>.md` に限る。

**評価基準ファイルも成果物の1つ**なので、一覧に載せて〈実装する〉で書く。
そのファイル自身に「**生成役はこれを書き換えない。基準の変更もオーナー承認を通す**」と書いておく。
このプラグイン自身の判定基準 [`reference/harness-design-criteria.md`](../../reference/harness-design-criteria.md)
がその書き方の実例で、`harness-design-reviewer` と `harness-evaluator` はこれを毎回読む。

合格条件と評価基準は生成側が書くが、**実装より先に書き・レビュー役を通し・オーナー承認で凍結する**の
3点で緩みを止める。順序が逆になった時点でこの防御は消える。

## 評価する

**この工程は自分で実行しない。`harness-evaluator` に渡す。**
実装したインスタンスに自己評価させない — エージェントは自分の成果物を自信を持って称賛するので、
同じ文脈を持ったまま測ると通ってしまう。渡すのは次の3つ。

- 〈実装する〉の記録（入力図のID・作った成果物・走らせた合格条件とその結果・⚠・未完）
- `設計.md`（処理一覧と成功指標。これが無いと実タスク通しも指標の測定も入力を持てない）
- 合格条件の置き場（`.claude/tests/<ハーネス名>/`）

以下は `harness-evaluator` が何をするかで、**こちらが代行する手順ではない**。
渡す材料が揃っているかを確かめるために読む。

**0. 再起動と登録を先に確かめる。** オーナーにセッションを再起動してもらってから、
`/hooks` `/skills` `/agents` に実際に出るかを見る。**ファイルがあることを登録の証拠にしない。**
ここを飛ばすと、書けたが動かないものを合格と数える。

**1. 凍結した合格条件を走らせる。** そのまま実行する。条件を書き換えない。

```bash
echo '{"hook_event_name":"PreToolUse","tool_name":"Edit","tool_input":{"file_path":"frontend/src/x.ts"}}' \
  | node .claude/hooks/<name>.js; echo "exit=$?"
```

hook は stdin から JSON を読むので、素で実行すると健全な hook でも JSON.parse に失敗して
1 で落ちる（誤検知）。通す入力で 0、止める入力で 2 を両方確かめる。

**1つでも落ちたら実タスクへ進まず差し戻す。** 壊れた部品の上で目的の達成を測っても、
何が効かなかったのかが分からない。

**2. 処理ごとに実タスクを通す。** テストが通ることと使えることは別。
ハーネスが持つ**処理を1つずつ**、実際の入力で最初から最後まで走らせる。1つ通して全部動くとみなさない。
**人間ゲートで実際に止まるか・エスカレーションが宛先に届くか・ループが上限で止まるかは、ここでしか分からない。**

**3. 宣言した介入点が実物にあるか照合する。** 図が宣言した5種を1つずつ、実ファイルの実装と突き合わせる。
**片方にしか無いものが1つでもあれば不合格。** 落とすとエージェントが人間に断らずに外へ出る。

**4. 過不足を数える。** 3方向で見る。**これは記録するだけで差し戻さない。**

| 向き | 見るもの |
|---|---|
| 図 → ファイル | 図にあってファイルに無いもの |
| ファイル → 図 | ファイルにあって図に無いもの |
| 実行ログ → ファイル | 一度も使われなかったもの（呼ばれない skill・発火ゼロの hook・参照されない rules） |

構造のズレだけを見て、散文の言い回しの違いはズレとしない。
**使われない部品はここでは削らない** — 1回のタスクで使われないのが正常な部品もある。
削る候補として報告し、削除は改善の工程でオーナーが決める。

**5. 目的の成功指標を測る。** `設計.md` の「成功を何で測るか」に戻る。
**ハーネス無し、または前の版で同じタスクを走らせた結果と比べる。**
ハーネスを更新したことは、ハーネスが効いたことを意味しない。

**6. 達成の判定は人間がする。** テストが全部通っていても目的が未達なのは普通に起きる。
**合格基準は目的の代理でしかない**ので、数字だけ良くて中身が壊れている型を疑う。

不合格なら、何がどの基準になぜ違反したかを**再現手順つき**で書く。称賛は書かない。
判断できないものは判断できないと書く。

## 改善は harness-improve へ

評価で出た指摘を直すのはこのスキルの仕事ではない。`harness-improve` に渡す。
構造を直したら、その図に限定して〈合格条件を決める〉から再実行する。

## 図に落ちない情報

構造から取れるのは「何が・誰から誰へ・どの順で」まで。次は**必ず備考か人間から取る**:
ループ上限 / タイムアウト / 権限の粒度 / プロンプトの文言 / 失敗時のエスカレーション先。

規約違反は機械が捕まえるが、「書けたはずのものを書いたか」は人間しか捕まえられない。
**レビューを省略できる日は来ない。** 省いてよいのは人間のゲートであって、検証そのものではない。

  放置し、〈処理の種類を考える〉の人間ゲートが実装から丸ごと落ちた（2026-08-23 〈評価する〉の初回評価で検出）

- **知識が資料にあることと、手順に載っていることは別。** セッション再起動が要ることは
  MAPPING.md に書いてあったが手順に無く、実装後に誰も促さなかった（2026-08-24 実測）
