# harness-implement — 目的から作図して設定に落とす

工程は8つ。このスキルは**〈目的を考える〉〜〈実装する〉と〈評価する〉を担当**する。
**〈統合する〉は `harness-compose`、〈改善する〉は `harness-improve`** へ渡す。

```
目的を考える → 処理の種類を考える
  →〔1処理ずつ〕処理を作る → 合格条件を決める → 実装する
  →（全処理そろったら）統合する → 評価する →（改善する）
```

**〈処理を作る〉〈合格条件を決める〉〈実装する〉は、1回の起動で1処理だけ扱う。**
次の処理は**オーナーが新しいセッションで起動する**。同じセッションで2処理目に入らない。

同じ文脈のまま2処理目に入ると規約違反が混入し、**規約を読み直させても直らない。
分離の単位はセッション**（詳細 →〈処理を作る〉）。

**承認は図までに集約する。** 図が契約で、その下（実装の中身）は図と合格条件から導く。
図より下に人間のゲートを置くと、オーナーが判断できない情報でゲートが埋まる。
実装前に残すゲートは**合格条件の凍結1つだけ**。

**処理**＝ハーネスが持つ独立したワークフロー（ブログを書く・動画を作る）。**工程**＝その処理の中身。
混ぜると工程が壊れる。
**オーナー**＝ハーネスの持ち主。このスキルを起動し、承認とエスカレーションを受ける本人。

## 成果物は工程ごとにファイルで残す

**1処理ずつ別のセッションで作るので、セッションをまたいで残るのはファイルだけ。**
会話に置いたものは次の回には無い。**工程を1つ終えるたびに、その工程の成果物をファイルに書く。**

```text
docs/harness/<ハーネス名>/
  設計.md                      索引。目的（工程1）と処理一覧＋状態列（工程2）だけを持つ
  処理/<処理名>/図.md           工程3 — 図のURL・キーと枚数・承認日・その図が宣言した介入点
  処理/<処理名>/合格条件.md      工程4 — 成果物の一覧・介入点5種の表・合格条件。承認で凍結する単位
  処理/<処理名>/実装.md          工程5 — 実装前判断の答え・作ったものと箇所・統合へ渡す仕様・⚠ 推測・未完
  統合.md                       工程6（harness-compose）
  評価/<日付>.md                工程7（harness-evaluator）
  改善/<日付>.md                工程8（harness-improve）
```

雛形はすべて [`reference/設計.md.template`](../../reference/設計.md.template) にある。

**ファイルが正、状態列は索引。** 各工程は必ず**①ファイルを書く → ②保存を機械で確かめる →
③`設計.md` の状態列を更新する**の順に進む。索引に**中身を再掲しない** — 同じものが2箇所にあると、
直したほうと直さなかったほうができる。食い違いは〈評価する〉の過不足で数えられる欠陥になる。

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/file-saved-lint.js" docs/harness/<ハーネス名>/処理/<処理名>/図.md
```

**「書き出した」は、書き出したつもりで終わっていても同じ言葉で報告できる。**
在るかどうかは機械にしか分からないので、工程の最後に必ず走らせる
（渡したパスが実在して空でないかだけを見る）。

**状態列は `未着手 / 図 確定 / 合格条件 凍結 / 実装済み`。**
書いていないと、新しいセッションは「どの処理の何が承認済みか」を知る手段が無く、
**承認済みの図を描き直す**か**未承認のまま実装へ進む**かのどちらかが必ず起きる
（「実行役は自分では数えられない。状態はファイルに残して数える」の同じ型）。

**合格条件は実装より先に書く。** あとから書くと実装に合わせて条件のほうが緩む。
承認された時点で凍結し、〈実装する〉は「実装を直す」ことでしか通さない。
この1本が〈実装する〉の完了判定と〈評価する〉の評価の両方を兼ねる。

→ 対応表 [MAPPING.md](MAPPING.md)（変換時に必ず読む）／問いの立て方 [FRONTIER.md](FRONTIER.md)

図がすでにあるなら〈目的を考える〉〈処理の種類を考える〉〈処理を作る〉を飛ばして〈合格条件を決める〉から入る。

**工程を自動で連鎖させない。** 各工程の Start は**人間の介入点（起動）**で、
1工程を終えたらそこで止まり、オーナーが次を指示してから進む。承認ゲートを通っても、
それは「その工程の成果物を認めた」だけで「次を始めてよい」ではない。
まとめて走らせると、途中で方針が変わったときに捨てる量が工程の数だけ増える。

## 始める前に — DrillSpark に繋がるか確かめる

**DrillSpark は必須。図が契約なので、図が無いと承認する対象そのものが無い。**

**このスキルを起動したら、どの工程から入る回でも最初に `list_projects()`（接頭辞は `mcp__drillspark__` か `mcp__claude_ai_DrillSpark__`） を1回だけ流す。**
繋がっていれば何も言わずに進む（「接続を確認しました」も報告しない）。
1処理ずつ別のセッションで作るので、**工程1を通らずに〈処理を作る〉から入る回のほうが多い** —
そこが一番 DrillSpark を使う場所なので、確認を工程1に紐づけない。
繋がっていなければ**そこで止めて案内する** — 手順・症状の切り分け・案内の文面は
[`reference/drillspark-setup.md`](../../reference/drillspark-setup.md)。

**繋がらないときに代わりの手段で進めない。** CLI に mermaid を貼る・図を飛ばして
`設計.md` の文章だけで実装へ進む、のどちらもしない。
**図が要るのは工程3だが、確認は工程1より前に置く** — 工程3で詰まると、
承認ゲートを2つ通した成果（目的・処理一覧）が宙に浮く。

## 業務改善の依頼書から始めるとき

カレントディレクトリに `業務改善/AI化依頼書.md` があれば、**それがこのハーネスの入力**です（`process-improve` の成果物）。
依頼書・`業務改善/改善案.md`・`業務改善/業務一覧.md` を先に読み、**そこに書いてあることを聞き直しません。**

| 決めること | 依頼書側にあるもの |
|---|---|
| 誰のため | 業務一覧の「誰が」 |
| 成果物 | 業務一覧の「次へ渡す先」（改善後の出口） |
| 成功を何で測るか | 改善案の「成功の形」。未計測の数字は基準値にせず傾向に置く |
| やらないこと | 依頼書の「承認の決め方」と、AIに任せないと決めた工程 |
| **処理の候補** | **依頼書の行（業務名＋工程）が1行1候補。** 任せ方（H1〜H5）と「承認が要る操作」がそのまま人間の関与になる |

〈目的を考える〉の締めの表には、この候補を「候補（依頼書より）」として並べます — **「処理はまだ1つも無い」と出しません。**
〈処理の種類を考える〉では、候補ごとに5観点を埋めます: 入口＝業務一覧の「きっかけ」か前の工程の出口、出口＝次の工程へ渡すもの、
定期実行＝業務一覧の頻度、人間の関与＝「承認あり」の操作と任せ方。**連続する工程は1つの処理にまとめてよく**
（候補を探す → 作る → 公開する を1本にするか、分けるか）、それだけをオーナーに問います。
〈処理を作る〉では、業務一覧の「図の在りか」に `改善後:` の URL があれば、**その図の AI レーンのノードと第二階層を処理の図の下書き**にします。
描き直しません。無ければ現状の図から起こします。

## 出力の作法

**この節は全工程に効く。** 「何を作るか」だけ細かく規定して**「どう出すか」を規定しないと、
実行役は手元にある情報を一度に全部吐く**。

1. **段階的に出す。** 一度に全部出さない。1画面で読み切れる量に切る
2. **現在地を出す。** 出力の先頭に1行 — `[4/8 合格条件を決める ｜ 図 4枚目/5枚 ｜ 次: 実装する]`。
   工程に入るときは「この工程が全体のどこで、何を決める場か」を1〜2行で述べる
3. **利用者の言葉で書く。** 作り手の語彙を利用者向けの文面に出さない（下の注釈表）
4. **内部IDを利用者向けの文面に出さない。** 図のノード番号は作業中の参照用であって、
   オーナーはその図を見ていない。ゲートは工程名で名乗る（「目的の承認」であって「承認ゲート 2_7」ではない）
5. **質問は `AskUserQuestion` で出す。** テキストで番号付きの質問を並べない。
   `AskUserQuestion` が無い環境（`claude -p` などの非対話実行）では、散文で問いを1つ出して止まり、先へ進まない。
   1回4問までなので多いときは分ける。自由記述が要る問いも、想定される答えを選択肢に出したうえで
   自由記述を受ける
6. **CLI で ASCII の作図をしない。** 図は DrillSpark のリンクに任せ、
   CLI にはレーンごとの箇条書きで「どの順に何をするか」だけ出す
7. **ゲートで出すのは3つだけ** — ①決まったこと ②**守られない可能性がある点**（リスクの言葉で）
   ③判断してほしい1点。レビューの往復や内部の修正表は `設計.md` に残し、CLI に出さない
8. **長い文書は要約を出し、全文を見るかを選ばせる。** 「438行です。全文を確認しますか、要約で承認しますか」
9. **終わるときは「次に言う言葉」まで出す。** 工程の区切り・処理の完了・セッションの終わりは、
   ①いま終わったことと保存先 ②処理一覧と状態列の表（`設計.md` のまま転記）
   ③**次に入力する文面をコピペできる形で1つ**、の3点で締める。
   利用者はAIの初心者かもしれない — 「新しいセッションで」とだけ言われても何をすればよいか分からない。
   次の形まで書いて渡す:
   「今の会話を閉じて、新しい会話を始めてください。**進捗はファイルに保存済みなので消えません。**
   新しい会話で、この1行を貼ってください →
   `harness-implement で「<処理名>」の続きを作りたい。設計は docs/harness/<ハーネス名>/設計.md`」。
   どの処理を勧めるかは状態列から選んで**具体名で**書く（「次の処理」と書かない — 貼るだけで動く形にする）

### 人間の介入点5種 — 利用者に見せるときは必ず注釈を付ける

この5語は判定基準の MUST の書式そのものなので**改名しない**。**注釈を付ける。**

| 内部の語 | 利用者向けの言い方 |
|---|---|
| 起動 | 誰がその作業を始めるか。人が毎回言って始めるのか、自動で始まるのか |
| 承認ゲート | 途中で必ず止まって、人に見せて確認する場所 |
| 実行 | 機械にはできず、人がやるしかない作業 |
| エスカレーション先 | うまくいかないとき、誰のところへ上げるか |
| 基準の決定 | 合格・不合格の線を誰が引くか |

### 実装の語も言い換える

| 内部の語 | 利用者向けの言い方 |
|---|---|
| hook の `exit 2` | 書き出した瞬間に自動で検査が走り、落ちたら**書き込みを止めて**理由を返す |
| お願い／柵 | 本文に「必ず通すこと」と書くだけだと破れる。機械が必ず走る形にした |
| 検証役の分離 | 合否を持つのは書いた本人ではなく検査の側。基準も本人が書き換えられない場所に置く |
| MUST／傾向 | 落ちたら差し戻す1本／記録するだけで差し戻さないもの |
| `permissions.deny` ／ `ask` | そのファイルを書けなくする設定／書く前に確認ダイアログが必ず出る設定 |

## 絶対に飛ばさない4点

ハーネス設定の変更は**最も壊れやすい局面**。以下は手順であって推奨ではない。

1. **承認を2段で取る。** ①**合格条件**を凍結してから作り始める。
   ②**実行をその場で変えるもの**は、書く前に内容そのものの承認を取る —
   `settings.json` の hook と権限、および**既に `settings.json` から参照されているスクリプト**。
   hook はファイル監視で**書いた瞬間から全操作に効く**ので、書いてから見せるのでは遅い。
   skill / agent / rules / 未参照のスクリプトは呼ばれるまで効かないので、作ってから見せてよい。
   **`settings.json` を新しく書くのは `harness-compose`** なので、②がこのスキルで要るのは
   **既に参照されているスクリプトを触る回**（＝図1枚単位の再適用）だけ
2. **成功メッセージを完了根拠にしない。** 生成・保存後は必ず読み戻して中身を確認する
   （`update_diagram` が success を返しつつ内容が巻き戻っていた実例がある）
3. **再実行は図1枚単位。** 全体を作り直さず、指定された図に対応する成果物だけ出し直す
4. **検証基準を生成側に置かない。** GO判定・lint基準は、それを満たす側が書き換えられない場所へ

## 目的を考える

**担当はオーナー。** エージェントは調べて問いを立てるだけで、答えを決めない。

**事実を調べるのは自分の仕事。** リポジトリ・コミット履歴・既存の設定で分かることを人間に聞かない。
調べたうえで、**決まっていないことをまとめて1ラウンドで問う**。1問ずつ聞かない。
各問に推奨と「逆を選ぶとどうなるか」を付ける。**上限は3ラウンド** — 超えたら打ち切り、
決まらなかった点を保留として明記して先へ進む。

**3は上限であってノルマではない。** 未決がゼロになった時点で終わる。1ラウンドで空になれば1回で終える。
**答えの出た問いを次のラウンドで再掲しない。** 2ラウンド目に出してよいのは、
前のラウンドの答えで**初めて前提が固まった**問いだけ（→ [FRONTIER.md](FRONTIER.md) 1「決定木として扱う」）。
納得のいく答えが出た問いをもう一度出すと、オーナーには「答えても進まない」ように見え、
上限の3が消化ノルマとして働きはじめる。

**ラウンド数は会話で数えず、`設計.md` の「保留中の論点」に何ラウンド目かを書いて数える。**
**実行役は自分のラウンド数を数えられない**（数えさせると、上限の管理が人間の手作業に戻る）。
書いておけば、文脈が切れても続きから数えられる。

決めるのは4つ。**誰のためか / 何を成果物とするか（パスまで）/ 成功を何で測るか / やらないことは何か。**
「誰のため」は役割で書く — アカウント名・メールアドレスは `設計.md` に書かない（`docs/` は公開されうる）。

**成功指標はオーナーが決める。エージェントは案を出すだけ。**
案は SMART の形で出す（→ [FRONTIER.md](FRONTIER.md)「観点の借り方」）。
合否の線（MUST）は1〜2本に絞り、残りは傾向として記録する — 線を増やすほどどれも守られなくなる。
**その指標が満点でも目的が未達になる型**を1つ書く（Goodhart 対策）。

成果物は `設計.md` の目的の節という**文章**。図にしない — 目的はフローではないので、図にすると嘘になる。
最後に**目的の承認**を取る。差し戻しは人間が毎回判断するので回数の上限を置かない。
承認されたら書き出し、`file-saved-lint.js` に `設計.md` のパスを渡して保存を確かめる。

## 処理の種類を考える

`設計.md` の目的から処理の候補を挙げ、**入口・出口・失敗経路・定期実行・人間の関与**の5観点で抜けを埋める。
抜け探しには SIPOC を重ねる（→ [FRONTIER.md](FRONTIER.md)「観点の借り方」。見つけたものは5観点の欄に書く）。
目的に書かれていない処理を勝手に足さない。

- **入口** — 何が来たら始まるか（誰が起動するか・入力は何か）
- **出口** — 終わったとき何が出来ているか（成果物とその置き場）
- **失敗経路** — うまくいかないときどこへ行くか
- **定期実行** — 決まった時間に自動で動くのか、毎回人が起動するのか
- **人間の関与** — どこで人が止まる・決める・手を動かすか

**まだ矢印を引かない。** 種類を漏れなく並べることだけに集中する。
先に線を引くと、つなぎやすい処理だけが残って抜けに気づけなくなる。
5つとも埋まって初めてオーナーに見せる。埋まっていない欄は「未定」と書く —
空欄のまま出すと、抜けているのか決まっていないのかが区別できない。

数が多ければ**分類してまとめ**、`設計.md` に一覧として記入する。処理を消して数を合わせない。
却下したものは却下したと残す。どう作図するか・プロジェクトをどう分けるかは、この工程では決めない。

**人間の介入点が2つある。飛ばさない。**

1. **【人間の実行】種類の過不足を答えてもらう** — 一覧を出したら**そこで止めて聞く**。
   ドメインを知らないと出てこない処理がある。エージェントが出した一覧は叩き台でしかない
2. **【承認ゲート】処理一覧はこれでよいか** — `設計.md` に書いたあと、確定する前に止める。
   処理一覧は**以降のすべての作図の入力**で、ここが違うと全部の図が無駄になる。
   あとから処理を足すときも必ずこのゲートを通す — 一覧に載らない処理は〈評価する〉の実タスク通しと
   過不足監査から漏れる

## 処理を作る

**1処理＝1 DrillSpark プロジェクト。** 図の書き方は `get_diagram_rules()` と MAPPING.md 2節。

### 階層の規約

**第一階層（ルート図）には工程だけを置き、第二階層以下に作業を置く。**
混ぜると読み手が「いま何の粒度を見ているか」を見失う。

| 階層 | 何を置くか |
|---|---|
| ルート図 | **工程だけ。** ドリルダウンを持つノード（サブプロセス）として置く。工程の中の手順を書かない |
| 第二階層以下 | **作業。** その工程の中で実際に手を動かす単位 |

作業が10前後に収まらなければ、**ノードを小さく詰め込まずに階層を1段足す**（lint が止めるのは15超）。

**ドリルダウンのレーンは担当で切り、各レーンの先頭ノードの備考に `lane: human|agent|system|external` を
1行書く**（→ MAPPING.md 5節）。書かないと、〈合格条件を決める〉でレーンの担当を名前から推測することになり、
対応表の行き先が2通りに読める。

### 1枚ずつ描いて1枚ずつ確認する

**まとめて描かない。** 最初の1枚はルート図（骨格）で、骨格が違うと下のドリルダウンが全部無駄になる。

```
図を1枚描く → 構造 lint → 【承認ゲート】この図でよいか → 残りがあれば次の1枚へ
```

**機械が見るものを人間のゲートへ持ち込まない。**
数値ID・二重引用符ラベル・`%% duration`・多出力・到達性・レーンと線種・IDの重複は
`node "${CLAUDE_PLUGIN_ROOT}/scripts/diagram-lint.js" <file>` が見る。目視で数え直さない。lint を通してからオーナーに見せる。

ループが3つ出るが、**回数の上限が要るものは1つも無い。**

| ループ | 上限 | 理由 |
|---|---|---|
| lint 不合格 → 描き直す | 不要 | 機械判定。直せば必ず抜ける |
| 承認 いいえ → 描き直す | 不要 | 人間が毎回判断する。止めるのは人間 |
| 残っている図 → 次の1枚 | 不要 | 件数で終わる反復。枚数が減るので必ず止まる |

**上限が要るのは「同じことをやり直す」ループだけ。** この線引きが無いと健全な反復まで差し戻し対象になる。

### 1回の起動＝1処理。次の処理は新しいセッションで

**1つの処理を作り終えたら、そのセッションはそこで終わる。** 次の処理はオーナーが新しいセッションで起動する。
同じセッションで続けると、**前の処理の粒度・レーンの切り方・承認の取り方が次の処理に混入する。**

**サブエージェントに描かせない。** サブエージェントは利用者と直接やり取りできないので、
**1枚ごとの承認ゲートが成立しない**。
親が取り次ぐ形にしても、親は全処理の文脈を持っているので混入がそのまま戻ってくる。
**分離の単位はセッション**にする。処理の中では同じセッションで描き続ける — 1枚目を描いた本人が2枚目を描く。

新しいセッションが読むもの:

| 読む | 読まない |
|---|---|
| `設計.md`（索引・目的・処理一覧と状態列） | **前の処理のフォルダ。** `処理/<別の処理名>/` は図・実装ともに開かない |
| **自分の処理のフォルダ** `処理/<この処理名>/` | 前の処理の図。mermaid も URL も見に行かない |
| 作図規約（`get_diagram_rules()` と MAPPING.md 2節）・判定基準ファイル | 前の処理で「こう描いた」という判断の経緯 |

**フォルダを処理ごとに分けてあるのはこのため。** 前の処理の `図.md` や `実装.md` も、
前の処理の図と同じ扱いで読まない。

**記憶より図と `設計.md` が正。** セッションをまたぐと前の回の言い分は残らない。
**指示と図が食い違ったら、図を正として報告する。指示に合わせて図を変えない。**

**決定が図の複数箇所に波及するとき、列挙は「漏れている前提」で読む。**
数えた波及は実際より少ないのが常で、**見落とすのはノードのラベル** —
分岐が `{"7つの塊と印がそろったか?"}` のように**数を持っている**。備考だけ直すと、
図のゲートウェイが周囲の備考すべてと矛盾する。
**数・順序・件数は、備考だけでなくノードのラベル・分岐のラベル・レーン名にも入る。**

**1工程を終えたらファイルに書き、保存を確かめ、`設計.md` の状態列を更新して終わる。**
そこが次のセッションの入口になる。**終わるときの案内は〈出力の作法〉9** — 残っている処理の一覧と、
新しいセッションで貼る1行まで出して終わる。状態列は仕組みであって案内ではない。
オーナーに見に行かせない。

**残すのは成果物の記録だけで、「どう描いたか」は書かない。**
`図.md` に書くのは事実 — 図のURL・キーと枚数・承認日・その図が宣言した介入点。
作図の判断の経緯を書くと、それが次の処理を作るセッションへの混入源になる。
**引き継ぎのための別ファイルも作らない**（置き場が2つあると、どちらが正か分からなくなる）。

## 合格条件を決める

**この工程が実装前の最後のゲート。** 承認を求めるのは合格条件だけ。
設計のレビューまでここで承認を積むと**オーナーが判断できない情報でゲートが埋まる**ので、
設計のレビューは〈実装する〉の内側にある。

### 図を取る

```
mcp__drillspark__get_project(project_id)   # 全図が一度に取れる
mcp__drillspark__get_diagram_rules()       # 作図規約。読み取り時も参照する
```

図1枚単位の再適用なら、対象のドリルダウン図＋その親図だけを見る。

### 構造を決定論的に抽出する

LLM の読解に頼らず、まず機械的に取れるものを取る。取れないものだけ散文から読む。

| 決定論で取る | 散文（備考）から読む |
|---|---|
| ノードID・形状・ラベル・所属レーン | 設計根拠・原則 |
| エッジの向き・実線/点線・ラベル | ループ上限などの回数制限 |
| 備考のDSL行（`lane:` `hook:` `permission:` `rule:`） | 生成先パス・制約 |

無視する要素（`click` / `classDef` / `style` / `rowOrder` / `duration` 等）は MAPPING.md 7節。

### 図から成果物の一覧を出す

図のノード・レーン・ゲート・停止点を、作るファイルへ割り付ける。

| | |
|---|---|
| skill | `.claude/skills/<name>/SKILL.md` |
| agent | `.claude/agents/<name>.md` |
| hook 定義 | `.claude/settings.json` の `hooks` |
| hook 実体 | `.claude/hooks/<name>.js` |
| 恒常ルール | `CLAUDE.md` / `.claude/rules/<topic>.md` |

**両方向で突き合わせる。** 対応物の無いノードと、根拠のノードが無い成果物の両方を見る。
片方向だけ見ると、落としたノードか勝手に足した成果物のどちらかを必ず見逃す。

**図に無いものをここで足さない。** 足したくなったら図へ戻す — 図が契約なので、契約の外で増やさない。

### 図に無い決定を1ラウンドで聞く

図に無い決定を**黙って仮定しない**。仮定した箇所がそのまま欠陥になる。

**この工程がオーナーに問える最後の場所**なので、前提が決まっている問い（＝フロンティア）を
全部洗い出し、**1ラウンドでまとめて聞く**。各問に「推奨・理由・逆を選ぶとどうなるか」を付ける。
**事実を調べるのは自分の仕事。** 調べられないもの（私的情報・組織の方針・未決の運用）だけ聞く。

**調査は本体でやらずサブエージェントへ投げる。** 問いの数だけ調査が走ると中間結果で文脈が埋まる。
`Explore` か `general-purpose` に投げ、結論だけ受け取る。**調査で止まらない。**

→ 網羅チェックリスト11項目は [FRONTIER.md](FRONTIER.md)

### 合格条件をテストデータで書く

**決定論で判定できるものだけ**を実データで書き、**コピペでそのまま実行できる形**にする（実行コマンドまで）。
置き場は `.claude/tests/<ハーネス名>/`。

| 種類 | 書くテストデータ |
|---|---|
| hook | 流すイベント JSON と期待する終了コード。**通す入力で 0・止める入力で 2** を両方 |
| lint・スクリプト | 違反サンプルと合格サンプル、引数、期待する標準出力 |
| skill・agent | 登録を確かめるコマンド（`claude plugin validate --strict` / `/skills` / `/agents`） |
| 図 | `node "${CLAUDE_PLUGIN_ROOT}/scripts/diagram-lint.js" <file>`（構造。`validate_diagram` は構文しか見ない） |

**終了コードだけを見る合格条件にしない。** 全部 exit 2 を返すだけの壊れた lint も
「違反サンプルで 2」を満たしてしまう。**違反サンプル1件につき、意図した指摘が1件だけ出ること**まで確かめる。

**決定論で判定できないものは合格条件にしない。** 人間の目に頼る判定は `設計.md` の**成功指標**として書き、
〈評価する〉で人間が測る。推測で埋めない。

### 人間の介入点5種を表にする

起動・承認ゲート・実行・エスカレーション先・基準の決定を、
**どの図のどのノードから来たか**と**どのファイルのどの記述で実現するか**の対で並べる。
1つも無いなら「無し」と明記する — 書かないのと「無い」と書くのは違う。

### 凍結する

一覧・合格条件・介入点の表をオーナーに見せて承認を取る。**出すのは3つだけ**（→〈出力の作法〉7）。
**承認された合格条件はここで凍結する。**以降、通らないときに直すのは実装であって条件ではない。

**凍結の単位はファイル。** 承認されたら `処理/<処理名>/合格条件.md` に書き出し、
保存を機械で確かめ、状態列を「合格条件 凍結」にする。
**このファイルは以後、実装の都合で編集しない。**統合はこのファイルを**そのまま集めるだけ**で、
中身を書き換えない。ファイル単位で凍結してあると、集める側が中身に触る理由が無くなる。

**凍結の解き方も決めておく。** 後から変えるときは、`harness-improve` で理想図の差分として起こし、
この工程で凍結し直す。実装の途中で直接書き換える経路は無い。
凍結だけして解き方を決めないと、結局は無審査で書き換えられる。

## 実装する

**図と凍結した合格条件から一気に作る。** 工程に分けて人間を逐一止めない。
止めるのは検証役と機械であって、人間ではない。

### 先に自分で固める判断

人間には聞かない。ここで決めきる。

**この一覧の正本はこの節だけ。** 他のファイル・図・レビュー役は数を書かずに
「実装前判断」として参照する — 数を写した先は、一覧が変わっても直らない。

**答えは会話に置かず、`処理/<処理名>/実装.md` の「実装前判断の答え」節に書く**（雛形は
`設計.md.template`）。会話に置いた答えは次のセッションには無く、レビュー役からも見えない。
該当が無い判断は「無し」と明記する — 書かないのと「無い」と書くのは違う。
**「削る」は足さなかった候補と理由まで書く** — 何も作らない判断は、書かないと検証できない。

1. **置き場を決める** — 常時オンにしてよいものだけ `CLAUDE.md`（目次・200行以内）。
   30行超の手順は skill、パス限定は `paths:` 付き rule、見せたくない脇道は agent。→ MAPPING.md 3.1節
2. **お願いを仕組みへ格上げする** — 「必ず」「絶対にするな」を指示文に残さない。
   hook の exit 2 と `permissions.deny` へ移す。指示は破れるが柵は破れない
3. **人間の介入点を機構へ割り当てる** — 5種を skill 起動 / cron / ゲートで止まる / 通知先 /
   書き換え不能な置き場のどれにするか決める。承認を連打させる設計は承認そのものを無力化する
4. **ループの止め方と再開点を決める** — 上限回数・予算・無進展の検知・強制停止の4つと、
   途中で落ちたときどこから戻るか。実現手段は MAPPING.md 3.2（予算だけは機構が無い — 表を見よ）
5. **検証役を生成役から分離する** — 判定基準は、それを満たす側が書き換えられない場所へ
6. **削る** — 標準機能で足りるものは足さない。モデルが自力でやるようになった指示は消す

### 各ファイルの仕様を決めて依存順に作る

MAPPING.md をそのまま適用する。**表に無い要素を推測で埋めない。**
推測が避けられない箇所は **⚠ 推測** と明記して記録に残す。

| 種類 | 決めること |
|---|---|
| hook | イベント / `matcher` と `if` の2段 / 終了コード / 止めたとき Claude へ渡す文 |
| skill・agent | frontmatter の値そのもの（→ MAPPING.md 6.1 の綴り対照表） |
| スクリプト | 引数・標準入出力・終了コード |

skill 本文の書き方は3点だけ守る。`description` は「何をするか」と「いつ使うか」の両方を書く
（呼ばれなさすぎる方に倒れやすいので、トリガーになる言い回しを具体的に入れる）。本文は500行未満
（超えそうなら別ファイルへの案内に切り替える）。大文字の命令を並べるより**なぜそうするかを書く**。
繰り返し出る作業は `scripts/` に束ねて本文から呼ぶ。

**この工程で作るのは、その処理に閉じた実体だけ** — skill / agent / `paths:` 付き rule / スクリプト /
その処理の合格条件。**ハーネスに1つしかないもの（`settings.json` の hook と権限、`CLAUDE.md`）は書かない。**
処理ごとに書くと、2処理目が1処理目の設定を上書きする。**書くのは `harness-compose` の1箇所だけ。**
hook が要る処理は、**hook の実体（`.claude/hooks/<name>.js`）までを作り、定義（`settings.json` の
`hooks`）は「compose へ渡す仕様」として `処理/<処理名>/実装.md` に書いて終わる。**

**依存順は、参照される実体（スクリプト → skill / agent / rules）が先。**
**既存ファイルを上書きしないことを先に確認する。**
特に **skill と agent で同義フィールドの綴りが違う**（skill は `disallowed-tools`、agent は `disallowedTools`）。

### 別インスタンスにレビューさせる

作り終えたら **`harness-design-reviewer` に見せる**。**ここで人間を止めない。**
生成役とは別インスタンスが、実装前判断のすべてに答えが `実装.md` に書かれているか・お願いのまま残した強制がないか・
介入点5種が機構に紐づいているか・ループに上限とエスカレーション先があるかを見る。
レビュー役は**指摘だけを返し、直さない**。判定線は
[`reference/harness-design-criteria.md`](../../reference/harness-design-criteria.md)。
**ここで基準のほうを緩めない。**

### 合格条件を走らせる

〈合格条件を決める〉で凍結したものをそのまま走らせる。落ちたら**実装を直す。条件のほうを直さない。**

**既存の処理の合格条件も全部走らせる（回帰）。** 自分の処理の条件だけでは、
**既存のハーネスを壊しても通ってしまう**。`設計.md` の処理一覧で状態が「実装済み」の処理の
`合格条件.md` を順に実行する（読むのは実行コマンドだけ — 前の処理の図や実装の経緯は読まない）。
**落ちたら自分の実装を直す。既存側の実装にも条件にも触らない** — 既存側を直したくなったら、
それはこの処理の仕事ではない。オーナーへ報告して止まる。

Claude Code は**壊れた定義を黙って無視する**。agent に `name` が無ければドキュメント扱いで
一覧にすら出ず、`description` 欠落や YAML 破損は debug ログにしか出ない。書き込んだら読み戻す。

**直しは通算3回まで。** レビューの差し戻しと合格条件の不合格を**合わせて**数える。
**会話で数えず、状態をファイルに残して数える** — 会話が長くなると数え直せなくなる。
超えたら**オーナーへ報告して止まる**。何がどの基準になぜ落ちたかを再現手順つきで添える。勝手に4回目を試さない。

### 実行を変える設定は、書く前に内容を見せる

**通常の回はここで `settings.json` を書かない。**`harness-compose` に渡す仕様として
`処理/<処理名>/実装.md` に書く — イベント・`matcher` と `if` の2段・ブロックの終了コード・
**止めたとき Claude へ渡す文**まで。仕様の再掲では足りない。
「ダメです」だけ返すと Claude は別経路を探し始めるので、代わりにどうすればよいかも書く。

**例外は、既に `settings.json` から参照されているスクリプトを触る回**（図1枚単位の再適用）。
このときは**実際に書き込む内容そのものを提示して止まり**、承認後に書き込んで読み戻す。
書いた瞬間から全操作に効くので、書いてから見せるのでは遅い。

### 処理がそろっていなければ、統合の前で止まる

**残りの処理があるなら、ここで終わる。** `設計.md` の処理一覧の状態を更新し、
「次は別のセッションで処理◯を作る」とだけ伝える。**続けて2処理目に入らない。**

全処理がそろったら、次は `harness-compose`（統合する）。**これも別のセッションで起動する。**

### この回に作った skill・agent は、このセッションでは登録されない

**書けた ≠ 登録された。** 新規の agent と、開始時に無かったディレクトリの skill は再起動まで動かない。
この回では実起動の検証をせず、`実装.md` の未完に「再起動後に実起動を確認」と書く。
再起動を頼むのは `harness-compose`、登録を確かめるのは `harness-evaluator`。

最後に `処理/<処理名>/実装.md` を書く — 参照した図のIDと `updated_at`・作った成果物と
**それが実ファイルのどこになったか**・統合へ渡す hook 定義の仕様・判断した ⚠ 推測・未完。
保存を機械で確かめ、`設計.md` の状態列を「実装済み」にする。
**このファイルが〈統合する〉と〈評価する〉の入力**で、〈可視化する〉が「工程 → 実設定のどこ」を
転記する先でもある。ここに無いものは、以後どの工程からも見えない。

### 基準と合格条件はどこで作るか

判定に使うものは3層あり、**作る場所と作る人が違う**。混ぜると検証の独立性が消える。

| | 何を測るか | 誰が作るか | いつ | どこに置くか |
|---|---|---|---|---|
| **成功指標** | 目的を達成したか（人間の目で測る） | **オーナー** | 〈目的を考える〉 | `設計.md` |
| **評価基準** | GO / NO-GO の線（MUST / 傾向） | エージェントが**降ろす**だけ | 〈合格条件を決める〉 | `.claude/rules/<topic>.md` のみ |
| **合格条件** | 決定論で判定できるテスト | エージェント | 〈合格条件を決める〉 | `.claude/tests/<ハーネス名>/` |

**評価基準はここで発明しない。** 〈目的を考える〉でオーナーが決めた「成功を何で測るか」「やらないこと」から
降ろすだけ。エージェントが基準そのものを起草すると、満たしやすい基準に寄る。

**評価基準を `CLAUDE.md` に置かない。** `CLAUDE.md` は実装役が通常運用で編集する場所なので、
そこに置いた瞬間に「生成側から書き換えない」が成立しなくなる。`.claude/rules/<topic>.md` に限る。

**評価基準ファイルも成果物の1つ**なので、一覧に載せて〈実装する〉で書く。
そのファイル自身に「**生成役はこれを書き換えない。基準の変更もオーナー承認を通す**」と書いておく。
このプラグイン自身の判定基準 [`reference/harness-design-criteria.md`](../../reference/harness-design-criteria.md)
がその書き方の実例で、`harness-design-reviewer` と `harness-evaluator` はこれを毎回読む。

合格条件と評価基準は生成側が書くが、**実装より先に書き・レビュー役を通し・オーナー承認で凍結する**の
3点で緩みを止める。順序が逆になった時点でこの防御は消える。

## 評価する

**この工程は自分で実行しない。`harness-evaluator` に渡す。**
実装したインスタンスに自己評価させない — エージェントは自分の成果物を自信を持って称賛するので、
同じ文脈を持ったまま測ると通ってしまう。

**評価は全処理そろって統合が終わってから、ハーネス全体に対して1回**。処理ごとには評価しない —
`settings.json` と `CLAUDE.md` は統合してはじめて確定するので、その前に測っても実物を測れない。
渡すのは次の3つ。

- `docs/harness/<ハーネス名>/` **一式** — 索引の `設計.md`（処理一覧・状態・成功指標）、
  処理ごとの `図.md`・`合格条件.md`・`実装.md`、`統合.md`
- 合格条件の置き場（`.claude/tests/<ハーネス名>/`。統合が1つに集めたもの）
- **渡すのはファイルであって会話ではない。** 処理ごとのセッションの会話は残っていないし、渡さない

手順の正本は [`agents/harness-evaluator.md`](../../agents/harness-evaluator.md)。こちらが代行する手順ではない。
上の3点が揃っているかだけ確かめて渡す。

## 統合は harness-compose へ／改善は harness-improve へ

**処理を1つずつ作るので、ハーネス全体になるのは統合を通ってから。**
全処理そろったら `harness-compose` に渡す（別のセッションで起動する）。
渡すのは `docs/harness/<ハーネス名>/` のファイル一式（索引と、処理ごとの `図.md`・`合格条件.md`・`実装.md`）だけで、
**処理ごとのセッションの会話は渡さない**。

評価で出た指摘を直すのもこのスキルの仕事ではない。`harness-improve` に渡す。
構造を直したら、**その処理のセッションを新しく起こし**、その図に限定して〈合格条件を決める〉から再実行する。

## 図に落ちない情報

構造から取れるのは「何が・誰から誰へ・どの順で」まで。次は**必ず備考か人間から取る**:
ループ上限 / タイムアウト / 権限の粒度 / プロンプトの文言 / 失敗時のエスカレーション先。

規約違反は機械が捕まえるが、「書けたはずのものを書いたか」は人間しか捕まえられない。
**レビューを省略できる日は来ない。** 省いてよいのは人間のゲートであって、検証そのものではない。

## 教訓（最大10行・超えたら統合してから追記）

- 図にノードを足したら、**同じターンでスキル本文も直す**。図だけ足してファイル側を放置すると、
  人間ゲートが実装から丸ごと落ちる（〈評価する〉で初めて発覚する）
- **「どう出すか」を規定しないと、実行役は手元の情報を一度に全部吐く。** →〈出力の作法〉
- **知識が資料にあることと、手順に載っていることは別。** セッション再起動が要ることは
  MAPPING.md に書いてあっても、手順に無ければ実装後に誰も促さない
- **承認ゲートを含む工程をサブエージェントに出さない**（→〈処理を作る〉）。
  図に描いて初めて成立しない経路として見えた — **描けない図は、実装できない手順の証拠**
