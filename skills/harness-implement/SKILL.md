# harness-implement — 目的から作図して設定に落とす

7つの工程のうち**〈目的を考える〉から〈評価する〉までを担当**する。〈改善する〉は `harness-improve` へ渡す。
**工程は名前で呼ぶ。番号では呼ばない。** 番号は図のノードを指すときだけ使う（`5_10_12` など）。
図の root では Start が 1、End が 10 を取るので、工程のノード番号は 2〜8 になる。

> 本文に出てくる `2_7` `3_4` `5_10_12` のような ID は、**このスキル自身を設計した DrillSpark 図の
> ノード番号**。その図は同梱していないので、読むうえでは飛ばしてよい。
> 消さずに残しているのは、各指示が「どの判断から来たか」を後から追えるようにするため。
> あなたが作るハーネスの図とは無関係。

```
目的を考える → 処理の種類を考える → 処理を作る → 設計する → 実装する → 評価する →（改善する）
```

**処理**＝ハーネスが持つ独立したワークフロー（ブログを書く・動画を作る）。**工程**＝その処理の中身。
混ぜると工程が壊れる。適用先は常に Claude Code なので対応表は1つで済む。

〈設計する〉と〈実装する〉の受け渡しは**詳細設計**という文書で行う。中身は**成果物の一覧**（何を作るか・パスまで）、
**各ファイルの仕様**（frontmatter の値・hook のイベントと条件と終了コード・スクリプトの入出力）、
**合格条件とそのテストデータ**（決定論で判定できるものだけ・そのまま実行できる形で）、
**依存順序**、**人間の介入点の表**の5つ。置き場は `設計.md` の「詳細設計」節。
〈実装する〉はこれだけを見て作る。「差分」は既存ファイルを変えるときの見せ方であって、設計そのものではない。

**`設計.md` の置き場は `docs/harness/<ハーネス名>/設計.md`。**
〈目的を考える〉〈処理の種類を考える〉の成果・〈設計する〉の詳細設計・〈実装する〉の適用範囲の記録が1つのファイルに集まる。
〈評価する〉の評価は**このファイルだけを物差しにする**ので、ここに無いものは測れない。
雛形: [`reference/設計.md.template`](../../reference/設計.md.template)

**合格条件は実装より先に書く。** あとから書くと実装に合わせて条件のほうが緩む。
承認された時点で凍結し、〈実装する〉は「実装を直す」ことでしか通さない。
この1本が〈実装する〉の完了判定と〈評価する〉の評価の両方を兼ねる。

→ 対応表 [MAPPING.md](MAPPING.md)（変換時に必ず読む）／問いの立て方 [FRONTIER.md](FRONTIER.md)

図がすでにあるなら〈目的を考える〉〈処理の種類を考える〉〈処理を作る〉を飛ばして〈設計する〉から入る。

**工程を自動で連鎖させない。** 各工程の Start は**人間の介入点（起動）**で、
1工程を終えたらそこで止まり、オーナーが次を指示してから進む。承認ゲートを通っても、
それは「その工程の成果物を認めた」だけで「次を始めてよい」ではない。
まとめて走らせると、途中で方針が変わったときに捨てる量が工程の数だけ増える。

## 絶対に飛ばさない4点

ハーネス設定の変更は HarnessRisk 実測で**最脆弱フェーズ**。以下は手順であって推奨ではない。

1. **承認を2段で取る。** ①**詳細設計**（何を作るか・各ファイルの仕様・合格条件・依存順序）を承認してから作り始める。
   ②**実行をその場で変えるもの**は、書く前に内容そのものの承認を取る —
   `settings.json` の hook と権限、および**既に `settings.json` から参照されているスクリプト**。
   hook はファイル監視で**書いた瞬間から全操作に効く**ので、書いてから見せるのでは遅い。
   skill / agent / rules / 未参照のスクリプトは呼ばれるまで効かないので、作ってから見せてよい
2. **成功メッセージを完了根拠にしない。** 生成・保存後は必ず読み戻して中身を確認する
   （`update_diagram` が success を返しつつ内容が巻き戻っていた実例がある）
3. **再実行は図1枚単位。** 全体を作り直さず、指定された図に対応する成果物だけ出し直す
4. **検証基準を生成側に置かない。** GO判定・lint基準は、それを満たす側が書き換えられない場所へ
   （verifier-deployment gap）

## 目的を考える

**目的が曖昧なまま処理を切ると全部やり直しになる。**

まずリポジトリ・コミット履歴・既存スキル・設定を**調べてから**問う。調べれば分かることを人間に聞かない。
そのうえで目的のフロンティア（誰のため・何を成果物とするか・成功を何で測るか・やらないこと）を
1ラウンドでまとめて出し、人間の回答を待つ。3ラウンドで空にならなければ打ち切り、
決まらなかった点を「保留」として明記する。

成果物は **`設計.md` という文章**。図にしない — 目的はフローではないので、図にすると嘘になる。
最後に人間の承認を取る（`2_7`）。差し戻しは上限3回で、超えたら先へ進めずに止めて報告する。

> **上流のゲートは4つある** — `2_7` 目的 ／ `3_7` 処理一覧 ／ `4_5` ルート図 ／ `4_7` ドリルダウン1枚ごと。
> ここを「唯一のゲート」と書いていたために〈処理の種類を考える〉のゲートが実装から落ちた（〈評価する〉の初回評価で検出）。

## 処理の種類を考える

`設計.md` の目的から処理の候補を挙げ、**入口・出口・失敗経路・定期実行・人間の関与**の5観点で
抜けを埋める。目的に書かれていない処理を勝手に足さない。

**まだ矢印を引かない。** 種類を漏れなく並べることだけに集中する。
先に線を引くと、つなぎやすい処理だけが残って抜けに気づけなくなる。

数が多ければ**分類してまとめ**、`設計.md` に一覧として記入する。処理を消して数を合わせない。
どう作図するか・プロジェクトをどう分けるかは、この工程では決めない。

**人間の介入点が2つある。飛ばさない。**

1. **【人間の実行】種類の過不足を答えてもらう**（`3_4`）— 一覧を出したら**そこで止めて聞く**。
   ドメインを知らないと出てこない処理がある。エージェントが出した一覧は叩き台でしかない
2. **【承認ゲート】処理一覧はこれでよいか**（`3_7`）— `設計.md` に書いたあと、確定する前に止める。
   処理一覧は**以降のすべての作図の入力**で、ここが違うと全部の図が無駄になる。
   あとから処理を足すときも必ずこのゲートを通す — 一覧に載らない処理は〈評価する〉の実タスク通しと
   過不足監査から漏れる。差し戻しは上限3回で、超えたら止めて報告する

## 処理を作る

**1処理＝1プロジェクト。** 処理が2つ（ブログ執筆と動画作成など）ならプロジェクトも2つ作り、
**同じフォルダ**に置いてハーネス単位でまとめる。処理どうしをつなぐ図は作らない（全体像は `設計.md`）。

**まとめて作らない。1処理ずつ、1枚ずつ。**

1. 未着手の処理を1つ選び、そのプロジェクトを作る
2. **工程を並べたルート図で骨格を固め、人間の確認を取る** — 骨格が変わると下が全部無駄になる
3. **工程を1つずつ**ドリルダウンで描く。1枚ごとに検証・保存・読み戻しまでやって確認を取る。
   まとめて最後に見せると、早く気づけば捨てずに済んだ作業まで捨てることになる
4. 全工程が終わったら次の処理へ

作図の規律:

- レーンは**マクロ図＝工程／ドリルダウン＝担当**で切り分ける（MAPPING.md 2節）
- **人間の介入点5種を必ず図に出す**。1つも無いなら「無し」と明記する（MAPPING.md 2.1節）
- ループには**上限とエスカレーション先**を書く。備考に埋めず、できるだけ構造で示す
- 1図5〜10に収まらなければ階層を足す
- `validate_diagram` で保存前に検証する。`update_diagram` は**全置換**なので、
  変更しない備考を再送する。保存後は必ず `get_diagram` で読み戻す
- 紙で決まらないことは描いて現物を見る。「レーンを2つに割るべきか」は議論では決まらない

決めるのは人間。エージェントは推奨と「逆を選ぶとどうなるか」を出すだけ。

## ハーネスを設計する

### 図を取る

```
mcp__drillspark__get_project(project_id)   # 全図が一度に取れる
mcp__drillspark__get_diagram_rules()       # 作図規約。読み取り時も参照する
```

図1枚単位の再適用なら、対象のドリルダウン図＋その親図だけを見る。

### 構造を決定論的に抽出する

LLM の読解に頼らず、まず機械的に取れるものを取る。取れないものだけ散文から読む。

| 決定論で取る | 散文（備考）から読む |
|---|---|
| ノードID・形状・ラベル・所属レーン | 設計根拠・原則 |
| エッジの向き・実線/点線・ラベル | ループ上限などの回数制限 |
| 備考のDSL行（`lane:` `hook:` `permission:` `rule:`） | 生成先パス・制約 |

無視する要素（`click` / `classDef` / `style` / `rowOrder` / `duration` 等）は MAPPING.md 7節。

### 概要設計を固める

構造だけでは決まらない判断を、**問いを出す前に**固める。順に6つ。

1. **置き場を決める** — 常時オンにしてよいものだけ `CLAUDE.md`（目次・200行以内）。
   30行超の手順は skill、パス限定は `paths:` 付き rule、見せたくない脇道は agent。
   → 判定表は [MAPPING.md](MAPPING.md) 3.1節
2. **お願いを仕組みへ格上げする** — 「必ず」「絶対にするな」を指示文に残さない。
   hook の exit 2 と `permissions.deny` へ移す。指示は破れるが柵は破れない
3. **人間の介入点を機構へ割り当てる** — 5種（起動・承認ゲート・実行・エスカレーション先・基準の決定）を
   skill 起動 / cron / 設計ゲートで止まる / PR レビュー / 通知先 / 書き換え不能な置き場のどれにするか決める。
   承認を連打させる設計は承認そのものを無力化する
4. **ループの止め方と再開点を決める** — 上限回数・予算・無進展の検知・強制停止の4つと、
   途中で落ちたときどこから戻るか。合格基準は目的の代理でしかないので、
   基準だけ上がって中身が壊れる事故を想定しておく
5. **検証役を生成役から分離する** — 判定基準は、それを満たす側が書き換えられない場所へ
6. **削る** — 標準機能で足りるものは足さない。モデルが自力でやるようになった指示は消す。
   部品を増やすほど良くなるわけではない

固めたら **`harness-design-reviewer` に見せる**。設計した側とは別インスタンスが、
6判断すべてに答えがあるか・お願いのまま残した強制がないか・介入点5種が機構に紐づいているか・
ループに上限とエスカレーション先があるかを見る。直せる指摘は**上限2回**で直し、
解けなかった指摘は ⚠ のまま次節〈フロンティア〉の問いに回す。**ここで基準のほうを緩めない。**

決まらないものは推測で埋めず ⚠ を付けて次のフロンティアへ回す。
**ここでは人間に聞かない** — 1つずつ聞くと次節〈フロンティア〉の1ラウンド原則が崩れる。
レビュー役には見せるが、それは人間への質問ではない。

### フロンティアを洗い出して一度に聞く

図に無い決定を**黙って仮定しない**。仮定した箇所がそのまま欠陥になる。

前提がすでに決まっている問い（＝フロンティア）を全部洗い出し、**1ラウンドでまとめて聞く**。
番号を振り、各問に「推奨・理由・逆を選ぶとどうなるか」を付ける。1問ずつ聞かない。

**事実を調べるのは自分の仕事。** 調べられないもの（私的情報・組織の方針・未決の運用）だけ聞く。

**調査は本体でやらず、サブエージェントへ投げる**（図5 のレーン「調査サブエージェント」）。
〈目的を考える〉の調査は目的まわりに限られるので本体で読んでよいが、ここは問いの数だけ調査が走るので、
中間結果でメインの文脈が埋まる。`Explore` か `general-purpose` に投げ、結論だけ受け取る。
**調査で止まらない。** 結果に依存する問いだけ次ラウンドへ回し、残りは先に人間へ出す。

フロンティアが空になってから詳細設計へ進む。→ 網羅チェックリスト11項目は [FRONTIER.md](FRONTIER.md)

### 詳細設計を書く

〈概要設計〉は概念のまま。ここで**ファイル1本ずつの話へ降ろす**。
MAPPING.md をそのまま適用する。**表に無い要素を推測で埋めない。**
2026-08-20 の実測で、移し先仕様を推測したエージェントが2回間違えた。
推測が避けられない箇所は **⚠ 推測** と明記して人間に判定させる。

**1. 成果物の一覧を出す。** 図のノード・レーン・ゲート・停止点を、作るファイルへ割り付ける。

| | |
|---|---|
| skill | `.claude/skills/<name>/SKILL.md` |
| agent | `.claude/agents/<name>.md` |
| hook 定義 | `.claude/settings.json` の `hooks` |
| hook 実体 | `.claude/hooks/<name>.js` |
| 恒常ルール | `CLAUDE.md` / `.claude/rules/<topic>.md` |

**2. ノードと成果物を両方向で突き合わせる。** 対応物の無いノードと、根拠のノードが無い成果物の両方。
片方向だけ見ると、落としたノードか勝手に足した成果物のどちらかを必ず見逃す。

**3. 合格条件をテストデータで書く。仕様より先に。** あとから書くと実装に合わせて条件が緩む。
**決定論で判定できるものだけ**を実データで書き、**コピペでそのまま実行できる形**にする（実行コマンドまで）。
置き場は `.claude/tests/<ハーネス名>/`、詳細設計からはパスで参照する。

| 種類 | 書くテストデータ |
|---|---|
| hook | 流すイベント JSON と期待する終了コード。**通す入力で 0・止める入力で 2** を両方 |
| lint・スクリプト | 違反サンプルと合格サンプル、引数、期待する標準出力 |
| skill・agent | 登録を確かめるコマンド（`claude plugin validate --strict` / `/skills` / `/agents`） |
| 図 | `node scripts/harness-diagram-lint.js <file>`（構造の6点。`validate_diagram` は構文しか見ない） |

**終了コードだけを見る合格条件にしない。** 全部 exit 2 を返すだけの壊れた lint も
「違反サンプルで 2」を満たしてしまう。**違反サンプル1件につき、意図した指摘が1件だけ出ること**まで
確かめる。実測でここを見て初めて、判定が正しい理由で出ていると言える。

人間の目に頼る判定はテストにしない。それは `設計.md` の**成功指標**として書き、〈評価する〉で人間が測る。
決定論で書けるものをここで書き切っておくと、〈評価する〉の「合格条件を走らせる」が機械的に回る。

**4. 各成果物の仕様を書く。** 3 の合格条件を満たすための中身。
ここを書かずに実装へ渡すと、実装側が仕様を発明する。

| 種類 | 決めること |
|---|---|
| hook | イベント / `matcher` と `if` の2段 / 終了コード / 止めたとき Claude へ渡す文 |
| skill・agent | frontmatter の値そのもの（→ MAPPING.md 6.1 の綴り対照表） |
| スクリプト | 引数・標準入出力・終了コード |

**5. 人間の介入点5種を表にする。** 起動・承認ゲート・実行・エスカレーション先・基準の決定を、
**どの図のどのノードから来たか**と**どのファイルのどの記述で実現するか**の対で並べる。
1つも無いなら「無し」と明記する — 書かないのと「無い」と書くのは違う。

**6. 依存順序を決める。** 参照される実体を先、それを参照する設定を最後に。
実体の無い hook を `settings.json` から参照すると、書いた瞬間から毎回失敗する。

**先に `harness-design-reviewer` を通す。** 対応物の無いノードが残っていないか、
根拠の無い成果物が混じっていないか、各仕様に実装が発明せずに済むだけの情報があるか、
**合格条件がそのまま実行できる形か**、依存順序で参照先が先に来ているか、
実行を即座に変えるものが識別されているか。
直せる指摘は上限2回で直し、解けなければ ⚠ のまま人間へ上げる。

**そのうえで一覧と仕様と合格条件を人間に見せて承認を取る。** ⚠ 推測と、対応物が無くて落とした要素も一緒に。
**承認された合格条件はここで凍結する。**以降、通らないときに直すのは実装であって条件ではない。
機械的な抜けはレビュー役が先に落としているので、人間へ来るのは判断の要る論点だけになる。
一覧が違っていれば本文を書く作業がまるごと無駄になるので、中身を書く前にここで止める。
承認されたら `設計.md` の「詳細設計」節に残す。**〈設計する〉はここまでで、まだ1文字も書かない。**

**線引き**: 図に載るのは構造まで。プロンプトの文言・`matcher` の細部・hook スクリプトの中身は
詳細設計で決める（図には戻さない）。

## ハーネスを実装する

**承認済みの詳細設計だけを見て作る。** ここで設計をやり直さない。
足りないと気づいたら 〈詳細設計〉 に戻る。

### 依存順に1件ずつ

**まとめて作らない。** 参照される実体（スクリプト → skill / agent / rules）が先で、
それらを参照する `settings.json` が最後。この順にすると、最後に書くものが
ちょうど一番危ないものになる。

1件書くたびに次の「書けた ≠ 登録された」を通してから次へ進む。
全部できるまでこれを繰り返し、**実体が揃ってから設定へ移る**。

**既存ファイルを上書きしないことを先に確認する**（新規のつもりで既存を潰すのが一番痛い）。
書くときの型は MAPPING.md 6節。特に **skill と agent で同義フィールドの綴りが違う**
（skill は `disallowed-tools`、agent は `disallowedTools`）。

### 書けた ≠ 登録された

Claude Code は**壊れた定義を黙って無視する**。agent に `name` が無ければドキュメント扱いで
一覧にすら出ず、`description` 欠落や YAML 破損は debug ログにしか出ない。
書き込んだら4つとも確認する。

1. **読み戻す** — 内容が保存されているか
2. **その1件の合格条件を走らせる** — 〈設計する〉で凍結したもの。落ちたら**実装を直す**。条件のほうを直さない
3. **綴りを検証する** — `claude plugin validate <dir> --strict`
   （`--strict` 無しだと未知フィールドは警告のまま通る）。
   `settings.json` を触ったなら JSON パースも
   （`node -e "JSON.parse(require('fs').readFileSync('.claude/settings.json','utf8'))"`）
4. **登録を確認する** — `/hooks`（由来の設定ファイルまで出る）・`/skills`・`/agents` の一覧に出るか。
   ファイル監視で再起動なしに反映されるが、**セッション開始時に無かったディレクトリを新設したときだけ**
   再起動が要る

直らなければ **2回で打ち切ってオーナーに報告して止まる**。何がどう失敗したかを添える。直し続けない。

### 実行を変える設定は、書く前に内容を見せる

実体が揃ったら、`settings.json` に**実際に書き込む JSON そのもの**を提示して止まる。
仕様の再掲ではない。hook なら、イベント・`matcher` と `if` の2段・ブロックの終了コード・
**止めたとき Claude へ渡す文**まで含める。
「ダメです」だけ返すと Claude は別経路を探し始めるので、代わりにどうすればよいかを書く。

承認後に書き込み、JSON パースと `/hooks` の登録を確認する。hook はイベント JSON を
標準入力に流して終了コードを両方向で確かめる（→ 6節）。

最後に、参照した図のIDと `updated_at`・作った成果物・判断した ⚠・未完を記録する。

### 基準と合格条件はどこで作るか

判定に使うものは3層あり、**作る場所と作る人が違う**。混ぜると verifier-deployment gap が開く。

| | 何を測るか | 誰が作るか | いつ | どこに置くか |
|---|---|---|---|---|
| **成功指標** | 目的を達成したか（人間の目で測る） | **オーナー** | 〈目的を考える〉「目的を考える」 | `設計.md` |
| **評価基準** | GO / NO-GO の線（MUST / NICE） | エージェントが**降ろす**だけ | 〈設計する〉（概要設計で出所、詳細設計で仕様） | `.claude/rules/<topic>.md` のみ |
| **合格条件** | 決定論で判定できるテスト | エージェント | 〈設計する〉「詳細設計」〈詳細設計〉 の 3 | `.claude/tests/<ハーネス名>/` |

**評価基準はここで発明しない。** 〈目的を考える〉でオーナーが決めた「成功を何で測るか」「やらないこと」から
降ろすだけ。エージェントが基準そのものを起草すると、満たしやすい基準に寄る。

**評価基準を `CLAUDE.md` に置かない。** `CLAUDE.md` は実装役が通常運用で編集する場所なので、
そこに置いた瞬間に「生成側から書き換えない」が成立しなくなる。`.claude/rules/<topic>.md` に限る。

**評価基準ファイルも成果物の1つ**なので、詳細設計の一覧に載せて〈実装する〉で書く。
そのファイル自身に「**生成役はこれを書き換えない。基準の変更もオーナー承認を通す**」と書いておく。
このプラグイン自身の判定基準 [`reference/harness-design-criteria.md`](../../reference/harness-design-criteria.md)
がその書き方の実例で、`harness-design-reviewer` と `harness-evaluator` はこれを毎回読む。

合格条件と評価基準は生成側が書くが、**実装より先に書き・レビュー役を通し・オーナー承認で凍結する**の
3点で緩みを止める。順序が逆になった時点でこの防御は消える。

**凍結の解き方も決めておく。** 凍結したものを後から変えるときは `harness-improve` の
**評価基準の変更承認ゲート**を通す。「判定に落ちたから基準を緩める」向きの変更はここで却下される。
凍結だけして解き方を決めないと、結局は無審査で書き換えられる。

## ハーネスを評価する

**評価は直さない。測って報告する。** そして**作れたことと役に立ったことを分けて測る。**
壊れていないかだけを見る評価は、目的を一度も問わないまま合格を出す。

**この工程は自分で実行しない。`harness-evaluator` に渡す。**
実装したインスタンスに自己評価させない — エージェントは自分の成果物を自信を持って称賛するので、
同じ文脈を持ったまま測ると通ってしまう。渡すのは次の3つ。

- 〈実装する〉の記録（入力図のID・作った成果物・走らせた合格条件とその結果・⚠・未完）
- `設計.md`（処理一覧と成功指標。これが無いと実タスク通しも指標の測定も入力を持てない）
- 合格条件の置き場（`.claude/tests/<ハーネス名>/`）

基準は `.claude/rules/`、合格条件は〈設計する〉で凍結したもの。**評価側で条件を書き換えない。**

以下は `harness-evaluator` が何をするかで、**こちらが代行する手順ではない**。
渡す材料が揃っているかを確かめるために読む。

**1. 設計時の合格条件を走らせる。** 〈設計する〉で書いたテストデータをそのまま実行する。

```bash
echo '{"hook_event_name":"PreToolUse","tool_name":"Edit","tool_input":{"file_path":"frontend/src/x.ts"}}' \
  | node .claude/hooks/<name>.js; echo "exit=$?"
```

hook は stdin から JSON を読むので、素で実行すると健全な hook でも JSON.parse に失敗して
1 で落ちる（誤検知）。通す入力で 0、止める入力で 2 を両方確かめる。
`settings.json` の JSON パースと `/hooks` `/skills` `/agents` の登録確認もここに含む。

**1つでも落ちたら実タスクへ進まず差し戻す。** 壊れた部品の上で目的の達成を測っても、
何が効かなかったのかが分からない。

**2. 処理ごとに実タスクを通す。** テストが通ることと使えることは別。
ハーネスが持つ**処理を1つずつ**、実際の入力で最初から最後まで走らせる。1つ通して全部動くとみなさない。
**人間ゲートで実際に止まるか・エスカレーションが宛先に届くか・ループが上限で止まるかは、ここでしか分からない。**

**3. 目的の成功指標を測る。** `設計.md` の「成功を何で測るか」に戻る。
**ハーネス無し、または前の版で同じタスクを走らせた結果と比べる。**
ハーネスを更新したことは、ハーネスが効いたことを意味しない。比較対象が無いと、
変わったのか良くなったのかを区別できない。

**4. 過不足を監査する。** 3方向で見る。

| 向き | 見るもの |
|---|---|
| 図 → ファイル | 図にあってファイルに無いもの |
| ファイル → 図 | ファイルにあって図に無いもの |
| 実行ログ → ファイル | 一度も使われなかったもの（呼ばれない skill・発火ゼロの hook・参照されない rules） |

構造のズレだけを見て、散文の言い回しの違いはズレとしない。
**使われない部品はここでは削らない** — 1回のタスクで使われないのが正常な部品もある。
削る候補として報告し、削除は改善の工程でオーナーが決める。

**5. 達成の判定は人間がする。** テストが全部通っていても目的が未達なのは普通に起きる。
**合格基準は目的の代理でしかない**ので、数字だけ良くて中身が壊れている型を疑う。

不合格なら、何がどの基準になぜ違反したかを**再現手順つき**で書く。称賛は書かない。
判断できないものは判断できないと書く。

> `claude plugin eval` は 2026-08-22 時点の公式 plugins-reference に**記載が無い**
> （early access の可能性はあるが確認できていない）。当てにせず、構文と綴りは
> `claude plugin validate --strict`、挙動は上記の hook 実行で検証する。

## 改善は harness-improve へ

評価で出た指摘を直すのはこのスキルの仕事ではない。`harness-improve` に渡す。
構造を直したら、その図に限定して手順4から再実行する。

## 図に落ちない情報

構造から取れるのは「何が・誰から誰へ・どの順で」まで。次は**必ず備考か人間から取る**:
ループ上限 / タイムアウト / 権限の粒度 / プロンプトの文言 / 失敗時のエスカレーション先。

規約違反は機械が捕まえるが、「書けたはずのものを書いたか」は人間しか捕まえられない。
詳細設計のレビューを省略できる日は来ない。
