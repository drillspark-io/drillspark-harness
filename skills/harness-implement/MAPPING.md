# 対応表: DrillSpark図 → Claude Code構成要素

`harness-implement` と `harness-improve` が共有する唯一の対応表。
**推測禁止。この表に無い要素は「未マッピング」として詳細設計のレビューへ回す。**

検証: 2026-08-22。
- 作図規約は `get_diagram_rules()` の全文で裏取り（節番号は規約の節を指す）
- 実データは実運用中のハーネス図2件について、全図・全ノード・全エッジ・全備考を手で通した
- 右列の Claude Code 仕様は実物の `.claude/settings.json` / `.claude/agents/` で裏取りした

> 本文の `5_3` `6_4` は、**このスキル自身を設計した DrillSpark 図のノード番号**。
> その図は同梱していないので読み飛ばしてよい。残してあるのは指示の出所を追えるようにするため。

## 1. 単位のマッピング

**処理＝そのハーネスが持つ独立したワークフロー**（例: ブログを書く／動画を作る）。
工程ではない。工程は処理の中身。

| 単位 | 対応 |
|---|---|
| **フォルダ** | 1つのハーネス（＝1リポジトリ） |
| **プロジェクト** | **1つの処理**。処理が2つあればプロジェクトも2つ。同じフォルダに置く |
| **root 図** | その処理のフロー（工程を並べたマクロ図） |
| **ドリルダウン** | 1つの工程の中身 |
| **処理一覧** | 図にしない。`設計.md` に文章で持つ |
| **1プロジェクト（＝1処理）** | 1つの skill（`.claude/skills/<name>/SKILL.md`） |
| ドリルダウン1枚 | skill 内の節、または担当が変わるなら別 agent |

> **プロジェクトを跨ぐドリルダウンは無い**（ツールにも作図規約にも該当する仕組みが見当たらない）。
> だが困らない。処理どうしをつなぐ図は最初から存在せず、全体像は `設計.md` が持つ。
> 「目的と処理一覧は文章、フローは図」という線引きがそのまま効いている。
>
> ドラフトの「サブプロセスノード `[[…]]` ＝ skill」は誤り。`[[…]]` はドリルダウンの存在を示す印にすぎない。

## 2. レーン → 担当（ドリルダウンの場合）

**マクロ図とドリルダウンでレーンの切り方を変える**（オーナー判断 2026-08-22）。

| 図 | レーンの切り方 | 点線 `-.->` の意味 |
|---|---|---|
| **マクロ図（ルート）** | **工程**で切る（構想と作図／実装／評価と改善） | 工程の切り替わり |
| **ドリルダウン** | **担当**で切る（人間／agent／システム） | 別コンテキストへの委譲 |

理由: マクロ図を担当で切ると、担当が1〜3ノードずつに散ってフローがジグザグになり読めない。
担当はノードの備考に「担当は〇〇」と書いて保持する。

> **規約との差異**: DrillSpark の作図規約は「レーンは担当者で名付ける。工程名は BPMN 違反」と定めている。
> マクロ図での工程レーンはこれを承知のうえでのオーナー判断。`validate_diagram` は
> レーン名を機械チェックしないので通る。
>
> **決着済み（オーナー判断 2026-08-22）**: 「**DrillSpark で必ずレーンを担当者にする必要はない**」。
> レビュー役はこれを規約違反として MUST に挙げてくるが、**指摘としては正しく、判断としては却下**である。
> 同じ指摘が毎回上がるので、レビューを頼むときは「マクロ図の工程レーンは決着済み」と先に伝えること。
> 変更するならオーナーの再判断が要る。
>
> **点線の意味が変わる点に注意**（4節の決定論シグナルはドリルダウンでのみ成立する）。
> マクロ図で「点線＝委譲」と読むと誤読になる。

以下はドリルダウンでの対応。



| レーン種別 | 判定 | Claude Code |
|---|---|---|
| 人間 | 備考 `lane: human`、なければレーン名に「オーナー/人間/承認」等 | 承認ゲート。`permissions.ask` か、skill 本文の停止指示 |
| agent | 備考 `lane: agent`、なければレーン名が識別子形式（`article-writer` 等）／「〜エージェント」 | `.claude/agents/<name>.md`（frontmatter: `name` `description` `tools` `disallowedTools` `model`） |
| システム | 備考 `lane: system`、なければレーン名に「検証/lint/CI」等 | hook（`.claude/settings.json`）または `.claude/hooks/<name>.js` |
| **その図を回す本体** | レーン名が**その図に対応する skill 名そのもの**（`harness-implement（エージェント）` 等） | **新しい agent を作らない。** その skill の本文が担当。→ 1節「1図＝1 skill」 |

> **agent レーンと本体レーンの見分け（2026-08-22 に追加）**: レーン名が identifier 形式でも、
> それが**この図自身の skill 名**なら agent ファイルは作らない。作ると
> 「skill が同名 agent を呼ぶ」入れ子ができ、1図＝1 skill の対応が壊れる。
> **別の名前**の identifier レーン（`article-writer` / `harness-design-reviewer` 等）だけが agent。
> 実測で、この区別が無いために対応表の行き先が2通りに読める状態だった（評価役の指摘 F）。

- 規約はレーン名を「責任を持つ役割・部門・システム」で付けろと定めるだけで（§5, §10）、
  **人間／agent／システムの区別は規約に無い**。名前からの推測になる。
  推測で決めた分類は詳細設計のレビューで「⚠ 推測」と明示すること。今後の図では `lane:` 備考を推奨。
- レーン名は図ごとにローカル。**親子図で同名レーンは同一担当として名寄せする**
  （例: root の `article-writer（執筆）` と子図の `article-writer（Maker）` は同一 agent）。
  正規化キー＝表示名から全角括弧の補足を除いた部分。
- **担当が1つしかない図はレーンを省いてよい**（規約が単一アクターの場合の省略を明示的に許している）。
  省いた場合でも 2.1 節の「人間の介入点は無し」宣言は Start か End の備考に書く。
  なお `5_3`（概要設計）は当初この形だったが、レビュー役を足した時点で担当が2つになり
  レーンを切り直した。**レビューを入れると単一担当ではなくなる**ので、省略の判断は後で覆りうる。

## 2.1 人間の介入点（数え落とし厳禁）

**人間がどこに入るかは、ハーネス設計で最も落としやすく、最も影響が大きい。**
レーンが人間かどうかだけを見ると数え落とす。**5種類あり、全部を列挙する。**

| 種類 | 図での現れ方 | Claude Code |
|---|---|---|
| **起動** | Start が人間レーンにある | ユーザーが skill を呼んで始まる（自動起動させない） |
| **承認ゲート** | 人間レーンの decision | 止めて確認する。機械化できるなら `permissions.ask` |
| **実行** | 人間レーンの process / document | 人間がやる作業。エージェントに代行させない |
| **エスカレーション先** | ループ上限の備考 | 上限到達時に誰へ渡すか。**構造に現れないので最も落ちやすい** |
| **基準の決定** | 「別エージェントに書かせる」等の備考 | 誰が最終決定するか。diff レビューの通過点 |

数え落としの実例（2026-08-22・初回適用）: 承認ゲート2点だけを数えて
「人間が止めるのは2点だけ」と書いたが、実際は上の5種類すべてが図にあった。
**承認ゲート＝人間の介入点、と読むと必ず落とす。**

**ここだけは推測しない。** 他の要素は暫定で進めて詳細設計のレビューに ⚠ を付ければよいが、
人間の介入点を1つ落とすとエージェントが勝手に外へ出る。不明なら止めて聞く。

## 3. ノード → 構成要素

| ノード | 記法 | Claude Code |
|---|---|---|
| process | `["動詞＋名詞"]` | skill 本文の1手順。所属レーンが担当 |
| subroutine | `[["…"]]` | ドリルダウンあり。→ 1節 |
| decision（人間レーン） | `{"…?"}` | 停止点。`permissions.ask` / skill 本文の「ここで人間に確認」 |
| decision（システムレーン） | `{"…?"}` | hook の合否（ブロックは exit 2）またはスクリプト内分岐 |
| decision（agentレーン） | `{"…?"}` | skill/agent 本文の判断基準。機械ゲートではない |
| document | `id@{ shape: doc }` | 成果物ファイル。→ 下記の注意 |
| data store | `[("…")]` | 長期メモリ（`CLAUDE.md` 追記・`.claude/rules/<topic>.md`・教訓ファイル・skill 本文への追記） |
| io | `[/"…"/]` | 外部入出力。MCP ツール呼び出し・API・ファイル読み書き |
| terminal | `(["Start"])` `(["End"])` | 対応物なし。ただし **Start の所属レーンが起動主体**（人間レーン＝ユーザーが手動起動、agent レーン＝他 skill から呼ばれる） |

**document の注意**: 規約上は成果物（Forms, reports, deliverables）だが、
実データの doc ノードは**2件とも動詞ラベル**だった
（`9@{…label: "公開する"}` / `10@{…label: "最終成果物を出力する"}`）。
この作図者は doc を「成果物を出す処理」として使っている。
→ **処理としての手順と、出力先ファイルの両方**を起こし、出力先パスを詳細設計のレビューで確認する。

**data store（検証済み）**: 実例 `4[("長期メモリ（教訓・AGENTS.md・Skill）")]`。
入りエッジ＝書き込み（エッジラベルが操作。例 `8 -.->|"教訓を保存"| 4`）、
出エッジ＝読み込み（文脈注入。例 `4 --> 3`）。duration は 0。
規約§1により process ノード数の 5-10 制限には数えない（document も同様）。

## 3.1 置き場の決定（構造からは決まらない）

3節は「ノードが何になるか」までしか決めない。**同じ内容をどのチャネルに置くかは図に現れない設計判断**で、
外すと動きはするが毎セッション全員のトークンを食い、重要な指示への追従が薄まる。

| 内容 | 置き場 | 効く理由 |
|---|---|---|
| 全セッションで要る事実（構成・コマンド・規約） | `CLAUDE.md` | 開始から常駐。だから**目次**に留める。200行を超えたら下へ振り分ける |
| 30行を超える手順 | `.claude/skills/<name>/SKILL.md` | 開始時は name/description だけ載り、本文は起動時にだけ載る |
| 特定パスだけの制約 | `.claude/rules/<topic>.md` に `paths:` | **`paths:` の無い rule は `CLAUDE.md` に書くのと機械的に同じ**（常時ロード・常時課金） |
| 中間結果をメインに見せたくない脇道 | `.claude/agents/<name>.md` | 別コンテキストで走り、親には最終メッセージだけ返る |
| 「必ずやる」「絶対にするな」 | hook（`PreToolUse` の exit 2）＋ `permissions.deny` | 指示は長い会話・曖昧な状況・注入で破れる。柵は破れない |
| 役割そのものの変更 | output style | 既定を**置換**する。検証習慣ごと落ちるので最後の手段 |

**格上げは一方通行**: お願い → 仕組み。同じ失敗が2回起きたら注意書きではなく仕組みにする。
逆向きに、モデルが自力でやるようになった手順は**削る**。ハーネスの部品は
「モデルが自力でできないこと」のエンコードであって、増やすほど良くなるものではない
（Skill が5個から100個に増えると実使用精度が 29.6% → 3.3% に落ちた実測がある）。

→ この判断の流れは図 `5_3`（概要設計を固める）。固めたあと `harness-design-reviewer` が検証する。

## 4. エッジ（規約で強制されている＝決定論で読める）

規約 §5・§7・§9 が明確に定めている。慣習ではない。

| エッジ | 規約上の意味 | Claude Code |
|---|---|---|
| 実線 `-->` | Sequence Flow。**同一レーン内のみ** | 同一担当内の順次実行 |
| 点線 `-.->` | Message Flow。**レーンを跨ぐときのみ**（同一レーン内での使用は禁止） | 別コンテキストへの委譲（agent 呼び出し / Task） |
| ラベル付き `-->|"Yes"|` | XOR ゲートウェイの分岐条件 | ラベル文字列をそのまま条件文に使う |
| 太線 `==>` | 規約にあるが**実データでの使用例ゼロ** | 未マッピング。出てきたら詳細設計のレビューへ |
| 逆流エッジ（後続→先行） | ループ | 修正ループ。**上限は図に現れない** → 備考から取る（5節） |

> **エッジラベルの落とし穴（2026-08-22 実測）**: ラベルが **ASCII で始まり丸括弧を含む**と、
> パーサーがノード定義と誤認する。`|"No(未確定あり)"|` は `No(...)` というノードを生やし、
> 「Start が2つある」「IDが非数値」で検証が落ちた。日本語始まりの `|"要修正(上限3回)"|` は通る。
> ASCII 始まりのラベルでは括弧を使わない。

実データ全24エッジで規約違反ゼロ。**エッジのスタイルからレーン跨ぎを決定論で判定してよい**。
万一レーン所属と矛盾する図が来たら、レーン所属を正としてエッジ違反を詳細設計のレビューに報告する。

## 5. 備考 `%% note[id]:`

**備考の第一用途は「なぜそうするか」の散文であり、DSL ではない。**
実データの備考は全て自然言語（設計根拠・論文引用・数値）で、DSL 行は1行も無かった。

| 用途 | 落とし先 |
|---|---|
| 設計根拠・原則・引用（既定） | SKILL.md / agent 本文の地の文。**根拠ごと写す**（「なぜ」を落とすとルールが守られない） |
| ループ上限・回数制限 | skill 本文のハードキャップ。図の構造からは取れないので備考必須 |
| 生成先パス | document ノードの出力先 |
| DSL 行（オプトイン・散文と共存可） | 下記 |

DSL（行頭が下記のいずれかで始まる行だけを機械抽出、残りは散文として扱う）:

```
lane: human|agent|system
hook: <event> matcher:<ツール名正規表現> if:<条件> run:<コマンド>
permission: allow|deny|ask <パターン>
rule: <CLAUDE.md に入れる1文>
```

> **抽出時の注意（規約§6.1）**: 備考の改行は実際の改行ではなく **2文字の `\n`** でエスケープされる
> （生の改行はコメントを終わらせてしまうため）。DSL 行の判定は、備考文字列を `\n` で分割してから行頭を見る。

## 6. Claude Code 側の実仕様（推測防止用の裏取り）

hook イベント（本リポジトリで実績があるもの）: `PreToolUse` `PostToolUse` `Stop` `PreCompact` `Notification`。
`SessionStart` `SessionEnd` `UserPromptSubmit` `SubagentStop` も存在するが本リポジトリでは未使用 —
使うなら「実績なし」と詳細設計のレビューに明示する。

絞り込みは**2段**。`matcher` はツール名（`"Edit|Write"` `"Bash"`）、`if` は対象条件
（`"Edit(frontend/src/**)"` `"Bash(gh pr merge *)"`）。ドラフトの「matcher:<正規表現>」だけでは不足。

```json
{ "type": "command",
  "if": "Edit(frontend/src/**)",
  "command": "node \"$CLAUDE_PROJECT_DIR/.claude/hooks/quality-check.js\"",
  "statusMessage": "Quality check...",
  "async": true, "timeout": 330 }
```

ブロックは hook の **exit 2**。stderr に書いた文字列がそのまま Claude に渡る
（`PreToolUse` は `permissionDecisionReason`）。**「ダメです」だけ返すと別経路を探し始める**ので、
代わりにどうすればよいかまで書く。出力は 10,000 字で打ち切られる。

### 6.1 追加調査（公式ドキュメント 2026-08-22 取得）

> 上の記述は本リポジトリの実績からの裏取り。以下は公式ドキュメントで確認した仕様で、
> **旧記述の「frontmatter は skill が3つ・agent が5つ」は不足していた**（訂正）。

**frontmatter — skill と agent で同義フィールドの綴りが違う。ここは必ず間違える。**

| | skill（`SKILL.md`） | agent（`.claude/agents/*.md`） |
|---|---|---|
| ツール禁止 | `disallowed-tools`（ハイフン） | `disallowedTools`（キャメル） |
| ツール許可 | `allowed-tools` | `tools` |
| 発火の限定 | `paths`（glob） | — |
| ループ上限 | — | `maxTurns` |
| 権限モード | — | `permissionMode`（`default` / `acceptEdits` / `auto` / `dontAsk` / `bypassPermissions` / `plan` / `manual`） |
| 記憶 | — | `memory`（`user` / `project` / `local`） |
| 隔離 | — | `isolation: worktree` |
| その他 | `when_to_use` `argument-hint` `arguments` `disable-model-invocation` `user-invocable` `model` `effort` `context: fork` `agent` `background` `hooks` `shell` `metadata` | `model` `effort` `skills` `mcpServers` `hooks` `color` `background` |

- **`permissionMode` / `tools` / `disallowedTools` / `maxTurns` で権限とループ上限を agent 単位に絞れる**
  （`permissions.deny` はセッション全体に効くという以前の判断の**訂正**。禁止を agent 単位で掛けたいなら
  `settings.json` ではなく agent の frontmatter を使う）
- **subagent は skill を自動継承しない。** `skills:` に明示した場合だけ。組み込み subagent は skill 不可
- `description` ＋ `when_to_use` は skill 一覧で **1,536 字で打ち切られる**。要点を先頭に
- **配布を見据えるなら6フィールドに絞る**: claude.ai アップロード・Skills API・`package_skill.py` は
  `name` `description` `license` `compatibility` `metadata` `allowed-tools` **以外があるとハードエラー**。
  作った skill をあとからプラグインとして配る予定があるなら、ここは最初から効いてくる

**いつ効き始めるか（承認をどこで取るかを決める）**

| 成果物 | 効き始め | 承認 |
|---|---|---|
| `settings.json` の hooks / permissions | **保存した瞬間**（ファイル監視） | 書く前に内容そのもの |
| **既に `settings.json` から参照されている**スクリプト | **保存した瞬間**（次の発火から） | 書く前に内容そのもの |
| まだ参照されていないスクリプト | 参照する設定を書くまで不活性 | 詳細設計の承認で足りる |
| skill / agent / rules | 呼ばれる・該当パスに触れるまで不活性 | 詳細設計の承認で足りる |

図1枚単位の再実行（既存ハーネスの改修）では、2行目を必ず踏む。
「スクリプトだから安全」という判断は、そのスクリプトが既に参照されている時点で崩れる。

**書き方の目安**（Anthropic 公式 `skill-creator` より）

- `description` は「何をするか」と「いつ使うか」の両方を書き、**呼ばれなさすぎる方に倒れやすい**ので
  トリガーになる言い回しを具体的に入れる。目安 100 語程度
- `SKILL.md` 本文は **500 行未満**。超えそうなら見出しで階層を作り、別ファイルへの案内に切り替える
- 大文字の命令を並べるより**なぜそうするかを書く**ほうが従われる。繰り返し出る作業は
  `scripts/` に束ねて本文から呼ぶ（毎回モデルに推論させない）

**書いても登録されないことがある（サイレント失敗）**

- agent に `name` が無いと**ドキュメント扱いで黙って無視される**。`description` が無い・YAML が壊れている・
  `name` に `:` が入る場合は debug ログにしか出ない → `claude --debug`
- skill/agent/hook はファイル監視で**再起動なしに反映される**。ただし
  **セッション開始時に存在しなかったディレクトリを新設した場合だけは再起動が要る**
- **MCP ツールは `tools:` に書くだけでは呼べない（2026-08-22 実測）**。
  agent の frontmatter に `mcp__drillspark__get_diagram` 等を列挙しても、起動時点では
  **deferred（スキーマ未ロード）のまま**で直接呼び出せない。エージェント本文で
  `ToolSearch(query="select:<名前をカンマ区切り>")` を先に走らせて初めて使える。
  → **MCP を使う agent は `tools:` に `ToolSearch` を必ず含め、本文にロード手順を書く。**
  `tools:` への列挙は「許可」であって「ロード」ではない
- **訂正（2026-08-22 実測）**: 上の「ファイル監視で再起動なしに反映される」は
  **agent には当てはまらない**。
  既存の `.claude/agents/` に新規 `.md` を置き `claude plugin validate --strict` が exit 0 でも、
  **同一セッション内では `subagent_type` として解決されず** `Agent type '<name>' not found` になる
  （2回試行・ファイルは BOM 無し LF で既存 agent と同一構造）。
  Agent ツールが見る型の一覧は**セッション開始時に確定する**。
  → **新規 agent を作った回は、そのセッションでは実起動検証ができない。**
  詳細設計の合格条件に「実起動して動く」を入れるなら、**セッション再起動を手順に含める**こと。
  ファイルを書いた時点で「登録された」と書かない（図6 `6_4` の「書けた ≠ 登録された」の実例）
- ネストした `.claude/skills/` は起動時に読まれない。そのディレクトリのファイルを触って初めて出てくる
- 同名 skill の解決順は **個人 > プロジェクト > プラグイン**。組み込み skill と同名にすると置き換わり、
  組み込みの別名では呼べなくなる
- **`plugin.json` はキーごとに受ける形が違う**（実測 2026-08-23）。`agents` にディレクトリ文字列を
  渡すと `validate` が `agents: Invalid input` で落ちる。`["./agents/a.md","./agents/b.md"]` の
  **ファイルパス配列**にすると通る。`skills` はディレクトリ文字列で通る。
  公式ドキュメントは両方 `string|array` と書いているので、**ドキュメントだけを根拠にしない**
- **プラグインは rules を配布できない**（実測 2026-08-23）。`.claude/rules/*.md` に相当する機構が無く、
  プラグイン root の `CLAUDE.md` も読まれない。代わりに skill 本文へ書くか hook で検証する。
  判定基準のように**生成側が書き換えられない場所**が要るものは、プラグイン同梱の参照ファイルにして
  エージェントに `${CLAUDE_PLUGIN_ROOT}` 経由で明示的に読ませる（skill 本文でも展開される。2.1.196+）。
  自動注入されないぶん、**読めなかったときに判定させない指示**をエージェント側に足す必要がある
- **プラグイン root に `CLAUDE.md` を置くと `validate --strict` が落ちる**（実測 2026-08-23）。
  「プラグイン root の `CLAUDE.md` はプロジェクトコンテキストとして読み込まれない」という警告が出る。
  リポジトリ＝プラグイン root のとき（配布用の単独リポジトリはこの形）に必ず当たる。
  **`.claude/CLAUDE.md` に置けば読み込まれ、`--strict` も通る**（別プロセスで読み込みを確認済み）

**確認と検証の手段**

| 何を | どうやって |
|---|---|
| 綴り違い・未知フィールド | `claude plugin validate <dir> --strict`（v2.1.233+。`--strict` 無しだと警告のまま通る）<br/>プラグインでなくても通る — 本リポジトリの `.claude/agents` と `.claude/skills` に対して実行し exit 0 を確認済み（2026-08-22） |
| hook の登録状況 | `/hooks`（読み取り専用。どの設定ファイル由来かまで出る） |
| skill / agent の登録状況 | `/skills` / `/agents` |
| hook の入出力 | `claude --debug` |
| 環境全体 | `/doctor` |

> `claude plugin eval` は 2026-08-22 時点の plugins-reference に**記載が無い**（early access の可能性はある）。
> 当てにせず `claude plugin validate --strict` を使う。

**hook は5種。プログラムが書けなくても使える。**
`command`（プログラム判定）/ `prompt`（日本語のルール文をモデルが判定）/ `agent`（実験的）/ `http` / `mcp_tool`。
**発火は型によらず必ず起きる。違うのは判定者だけ。**取り返しのつかない操作は `command`、
条件が書き出しにくいものは `prompt`。パスは `${CLAUDE_PROJECT_DIR}` で書く（相対パスは危険、絶対パスは共有できない）。

設定の優先順位（強い順）: managed → `claude --settings` → `.claude/settings.local.json` →
`.claude/settings.json` → `~/.claude/settings.json`。
**`deny` と `ask` は即時に効くが、`allow` はワークスペースの信頼を受け入れるまで効かない。**

## 7. 無視する要素（生成物・表示用）

`click … call onMermaidClick(…)` / `classDef` / `class` / `style` / `linkStyle` /
`%% rowOrder:` / `%% Theme Definitions` ブロック / `%% duration[id]:` / `%% cost[id]:` /
`%% nodeStyle[id]:` / `%% noteStyle[id]:` / `%% subgraphStyle[名前]:` / ラベル内の `⏱ N 分` / `<br/>`。

duration・cost はハーネス設定に対応物が無い。SKILL.md の所要時間目安として本文に回すだけで、
設定生成には使わない。

> **図を書き戻すとき（harness-improve 用）**: `update_diagram` は図を**全置換**する（規約§6.2）。
> 省いた `%% note` `%% cost` `%% nodeStyle` `%% noteStyle` `%% subgraphStyle` は消える。
> 必ず `get_diagram` してから、変更しないメタデータを再送すること。
> `%% rowOrder` と Theme Definitions は保存時に再生成されるので送らない。
