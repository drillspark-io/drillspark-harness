# 対応表: DrillSpark図 → Claude Code構成要素

`harness-implement`・`harness-compose`・`harness-improve` が共有する唯一の対応表。
**推測禁止。この表に無い要素は「未マッピング」として実装のレビューへ回す。**

裏取り: 作図規約は `get_diagram_rules()` の全文（節番号は規約の節）、右列の Claude Code 仕様は
実運用のハーネス2件の実物と公式ドキュメント。実物は同梱していない。

## 1. 単位のマッピング

**処理＝そのハーネスが持つ独立したワークフロー**（例: ブログを書く／動画を作る）。
工程ではない。工程は処理の中身。

| 単位 | 対応 |
|---|---|
| **フォルダ** | 1つのハーネス（＝1リポジトリ） |
| **プロジェクト** | **1つの処理**。処理が2つあればプロジェクトも2つ。同じフォルダに置く |
| **root 図** | その処理のフロー（工程を並べたマクロ図） |
| **ドリルダウン** | 1つの工程の中身 |
| **処理一覧** | 図にしない。`設計.md` に文章で持つ |
| **1プロジェクト（＝1処理）** | **入口の skill 1つ**（`.claude/skills/<name>/SKILL.md`）＋その処理が使う agent・hook・rule。<br>処理は複数の部品が総合して動くので、**skill の数は処理の数ではない** |
| ドリルダウン1枚 | 入口 skill 内の節、または担当が変わるなら別 agent |

> **プロジェクトを跨ぐドリルダウンは無い**（ツールにも作図規約にも該当する仕組みが見当たらない）。
> だが困らない。処理どうしをつなぐ図は最初から存在せず、全体像は `設計.md` が持つ。
> 「目的と処理一覧は文章、フローは図」という線引きがそのまま効いている。
>
> 「サブプロセスノード `[[…]]` ＝ skill」と読みたくなるが誤り。`[[…]]` はドリルダウンの存在を示す印にすぎない。

## 2. レーン → 担当（ドリルダウンの場合）

**マクロ図とドリルダウンでレーンの切り方を変える**（設計判断）。

| 図 | レーンの切り方 | 点線 `-.->` の意味 |
|---|---|---|
| **マクロ図（ルート）** | **工程**で切る（例: 準備／作る／検証する） | 工程の切り替わり |
| **ドリルダウン** | **担当**で切る（人間／agent／システム／外部サービス） | 別コンテキストへの委譲 |

理由: マクロ図を担当で切ると、担当が1〜3ノードずつに散ってフローがジグザグになり読めない。
担当はノードの備考に「担当は〇〇」と書いて保持する。

> **規約との差異**: DrillSpark の作図規約は「レーンは担当者で名付ける。工程名は BPMN 違反」と定めている。
> マクロ図での工程レーンはこれを承知のうえでの設計判断。`validate_diagram` は
> レーン名を機械チェックしないので通る。
>
> **決着済み（設計判断）**: 「**DrillSpark で必ずレーンを担当者にする必要はない**」。
> この決着は判定基準（`reference/harness-design-criteria.md`）に「決着済み — 指摘しない」として
> 取り込み済みで、レビュー役はもう挙げない。変更するならオーナーの再判断が要る。
>
> **点線の意味が変わる点に注意**（4節の決定論シグナルはドリルダウンでのみ成立する）。
> マクロ図で「点線＝委譲」と読むと誤読になる。

以下はドリルダウンでの対応。

| レーン種別 | 判定 | Claude Code |
|---|---|---|
| 人間 | 備考 `lane: human`、なければレーン名に「オーナー/人間/承認」等 | 承認ゲート。`AskUserQuestion` で止める（→ 2.1）。機械化できるなら `permissions.ask` |
| agent | 備考 `lane: agent`、なければレーン名が識別子形式（`article-writer` 等）／「〜エージェント」 | `.claude/agents/<name>.md`（frontmatter: `name` `description` `tools` `disallowedTools` `model`） |
| システム | 備考 `lane: system`、なければレーン名に「検証/lint/CI」等 | hook（`.claude/settings.json`）または `.claude/hooks/<name>.js` |
| **外部サービス** | 備考 `lane: external`、なければレーン名がサービス名（`DrillSpark` 等） | **新しい部品を作らない。** MCP ツール呼び出し（io ノードと同じ）。呼ぶ skill / agent の `allowed-tools` / `tools` に `mcp__<server>__*` を列挙する |
| **その図を回す本体** | レーン名が**その図に対応する skill 名そのもの**（`harness-implement（エージェント）` 等） | **新しい agent を作らない。** その skill の本文が担当。→ 1節「1プロジェクト（＝1処理）＝入口の skill」 |

> **agent レーンと本体レーンの見分け**: レーン名が identifier 形式でも、
> それが**この図自身の skill 名**なら agent ファイルは作らない。作ると
> 「skill が同名 agent を呼ぶ」入れ子ができ、1処理＝1 skill の対応が壊れる。
> **別の名前**の identifier レーン（`article-writer` / `harness-design-reviewer` 等）だけが agent。
> この区別が無いと、対応表の行き先が2通りに読める。

- 規約はレーン名を「責任を持つ役割・部門・システム」で付けろと定めるだけで（§5, §10）、
  **人間／agent／システム／外部の区別は規約に無い**。だから**各レーンの先頭ノードの備考に
  `lane:` を1行書く**（〈処理を作る〉の規約。5節）。無い図を読むときは名前から推測し、
  推測で決めた分類は実装のレビューで「⚠ 推測」と明示する。
- レーン名は図ごとにローカル。**親子図で同名レーンは同一担当として名寄せする**
  （例: root の `article-writer（執筆）` と子図の `article-writer（下書き）` は同一 agent）。
  正規化キー＝表示名から全角括弧の補足を除いた部分。
- **担当が1つしかない図はレーンを省いてよい**（規約が単一アクターの場合の省略を明示的に許している）。
  省いた場合でも「人間の介入点は無し」の宣言は Start か End の備考に書く（判定基準の構造 MUST）。
  **レビュー役を足した時点で担当は2つになる**ので、省略の判断は後で覆りうる。

## 2.1 人間の介入点（数え落とし厳禁）

**人間がどこに入るかは、ハーネス設計で最も落としやすく、最も影響が大きい。**
レーンが人間かどうかだけを見ると数え落とす。**5種類あり、全部を列挙する。**

| 種類 | 図での現れ方 | Claude Code |
|---|---|---|
| **起動** | Start が人間レーンにある | ユーザーが skill を呼んで始まる（自動起動させない） |
| **承認ゲート** | 人間レーンの decision | `AskUserQuestion` で止めて確認する（テキストで質問を並べない）。機械化できるなら `permissions.ask` |
| **実行** | 人間レーンの process / document | 人間がやる作業。エージェントに代行させない。skill 本文に「【人間の実行】」と明記 |
| **エスカレーション先** | ループ上限の備考 | 上限到達時に誰へ渡すか。skill 本文の「オーナーへ報告して止まる」＋状態ファイルの記録（→ 3.2）。**構造に現れないので最も落ちやすい** |
| **基準の決定** | 「別エージェントに書かせる」等の備考 | 誰が最終決定するか。判定基準ファイルの置き場（`.claude/rules/<topic>.md`）と、その変更をオーナー承認に限る記述 |

**承認ゲート＝人間の介入点、と読むと必ず落とす。** 承認ゲートだけを数えると、
起動・実行・エスカレーション先・基準の決定の4種が図にあっても数に入らない。

**ここだけは推測しない。** 他の要素は暫定で進めて実装のレビューに ⚠ を付ければよいが、
人間の介入点を1つ落とすとエージェントが勝手に外へ出る。不明なら止めて聞く。

## 3. ノード → 構成要素

| ノード | 記法 | Claude Code |
|---|---|---|
| process | `["動詞＋名詞"]` | skill 本文の1手順。所属レーンが担当 |
| subroutine | `[["…"]]` | ドリルダウンあり。→ 1節 |
| decision（人間レーン） | `{"…?"}` | 停止点。`AskUserQuestion`（→ 2.1）／ `permissions.ask` |
| decision（システムレーン） | `{"…?"}` | hook の合否（ブロックは exit 2）またはスクリプト内分岐 |
| decision（agentレーン） | `{"…?"}` | skill/agent 本文の判断基準。機械ゲートではない |
| document | `id@{ shape: doc }` | 成果物ファイル。出力先パスを備考から取り、実装のレビューで確認する。<br>ラベルが動詞（「公開する」等）なら、**成果物ファイルと、それを出す手順の両方**を起こす |
| data store | `[("…")]` | 長期メモリ（`CLAUDE.md` 追記・`.claude/rules/<topic>.md`・教訓ファイル・skill 本文への追記）。<br>入りエッジ＝書き込み（エッジラベルが操作）、出エッジ＝読み込み（文脈注入）。duration は 0 |
| io | `[/"…"/]` | 外部入出力。MCP ツール呼び出し・API・ファイル読み書き。呼ぶ側の `allowed-tools` / `tools` に落ちる |
| terminal | `(["Start"])` `(["End"])` | 対応物なし。ただし **Start の所属レーンが起動主体**（人間レーン＝ユーザーが手動起動、agent レーン＝他 skill から呼ばれる） |

document・data store は規約上の process ノード数の制限（5〜15。10までが目安、15は lint の上限）に数えない。

## 3.1 置き場の決定（構造からは決まらない）

3節は「ノードが何になるか」までしか決めない。**同じ内容をどのチャネルに置くかは図に現れない設計判断**で、
外すと動きはするが毎セッション全員のトークンを食い、重要な指示への追従が薄まる。

| 内容 | 置き場 | 効く理由 |
|---|---|---|
| 全セッションで要る事実（構成・コマンド・規約） | `CLAUDE.md` | 開始から常駐。だから**目次**に留める。200行を超えたら下へ振り分ける |
| 30行を超える手順 | `.claude/skills/<name>/SKILL.md` | 開始時は name/description だけ載り、本文は起動時にだけ載る |
| 特定パスだけの制約 | `.claude/rules/<topic>.md` に `paths:` | **`paths:` の無い rule は `CLAUDE.md` に書くのと機械的に同じ**（常時ロード・常時課金） |
| 中間結果をメインに見せたくない脇道 | `.claude/agents/<name>.md` | 別コンテキストで走り、親には最終メッセージだけ返る |
| 「必ずやる」「絶対にするな」 | hook（`PreToolUse` の exit 2）＋ `permissions.deny` | 指示は長い会話・曖昧な状況・注入で破れる。柵は破れない |
| 役割そのものの変更 | output style | 既定を**置換**する。検証習慣ごと落ちるので最後の手段 |

**格上げは一方通行**: お願い → 仕組み。同じ失敗が2回起きたら注意書きではなく仕組みにする。
逆向きに、モデルが自力でやるようになった手順は**削る**。ハーネスの部品は
「モデルが自力でできないこと」のエンコードであって、増やすほど良くなるものではない。
Skill が増えるほど、1つ1つが選ばれる精度は落ちる。

→ この判断は〈実装する〉の実装前判断の1つ（置き場の判断。数も一覧も正本は SKILL.md の側）。
作り終えたあと `harness-design-reviewer` が検証する。

## 3.2 ループの止め方（構造からは取れない）

実装前判断「ループの止め方と再開点」の4項目を Claude Code の何で実現するか。
図には逆流エッジしか現れないので、**この表が無いと4項目のうち3つを推測で埋めることになる**。

| 項目 | 実現手段 | 備考 |
|---|---|---|
| 上限回数 | skill 本文のハードキャップ＋**状態ファイルのカウント** | 実行役は自分では数えられない。会話で数えず、ファイルに残して数える |
| 無進展の検知 | 直しの**通算**カウント（差し戻しと不合格を合算） | 種類別に数えると各カウンタが上限未満のまま回り続ける |
| 強制停止 | hook の exit 2 ／ `permissions.deny` | 指示は破れるが柵は破れない。「これ以上やるな」を指示文で書かない |
| 予算（トークン・費用） | **対応する機構が無い** | agent 単位の `maxTurns` が最も近い代用。処理単位の予算はオーナーの介入（起動を分ける・止める）に割り当て、その旨を実装.md に書く |

再開点は状態ファイル（`設計.md` の状態列・実装.md の未完）から復元する — 会話は次の回には無い。

## 4. エッジ（規約で強制されている＝決定論で読める）

規約 §5・§7・§9 が明確に定めている。慣習ではない。

| エッジ | 規約上の意味 | Claude Code |
|---|---|---|
| 実線 `-->` | Sequence Flow。**同一レーン内のみ** | 同一担当内の順次実行 |
| 点線 `-.->` | Message Flow。**レーンを跨ぐときのみ**（同一レーン内での使用は禁止） | 別コンテキストへの委譲（agent 呼び出し / Task）。**ただし人間レーンへ入る点線は Task にできない** — サブエージェントは利用者と対話できないので、本体が `AskUserQuestion` で止まる形になる |
| ラベル付き `-->|"Yes"|` | XOR ゲートウェイの分岐条件 | ラベル文字列をそのまま条件文に使う |
| 太線 `==>` | 規約にあるが対応物を決めていない | 未マッピング。出てきたら実装のレビューへ |
| 逆流エッジ（後続→先行） | ループ | 修正ループ。**上限は図に現れない** → 備考から取る（5節） |

> **エッジラベルの落とし穴**: ラベルが **ASCII で始まり丸括弧を含む**と、
> パーサーがノード定義と誤認する。`|"No(未確定あり)"|` は `No(...)` というノードを生やし、
> 「Start が2つある」「IDが非数値」で検証が落ちる。日本語始まりの `|"要修正(上限3回)"|` は通る。
> ASCII 始まりのラベルでは括弧を使わない。

**エッジのスタイルからレーン跨ぎを決定論で判定してよい**（規約が強制しており、`diagram-lint` の
`EDGE_STYLE` が見る）。万一レーン所属と矛盾する図が来たら、レーン所属を正としてエッジ違反を
実装のレビューに報告する。

## 5. 備考 `%% note[id]:`

**備考の第一用途は「なぜそうするか」の散文であり、DSL ではない。** DSL 行は散文と共存できる。

| 用途 | 落とし先 |
|---|---|
| 設計根拠・原則・引用（既定） | SKILL.md / agent 本文の地の文。**根拠ごと写す**（「なぜ」を落とすとルールが守られない） |
| ループ上限・回数制限 | skill 本文のハードキャップ。図の構造からは取れないので備考必須 |
| 生成先パス | document ノードの出力先 |
| DSL 行 | 下記 |

DSL（行頭が下記のいずれかで始まる行だけを機械抽出、残りは散文として扱う）:

```
lane: human|agent|system|external     ← 各レーンの先頭ノードに必ず書く（2節）
hook: <event> matcher:<ツール名正規表現> if:<条件> run:<コマンド>   ← 任意
permission: allow|deny|ask <パターン>                                ← 任意
rule: <CLAUDE.md に入れる1文>                                        ← 任意
```

`lane:` だけは必須。無いと2節の担当分類が名前からの推測になり、対応表の行き先が2通りに読める。
残り3つは、備考の散文で足りるなら書かなくてよい。

> **抽出時の注意（規約§6.1）**: 備考の改行は実際の改行ではなく **2文字の `\n`** でエスケープされる
> （生の改行はコメントを終わらせてしまうため）。DSL 行の判定は、備考文字列を `\n` で分割してから行頭を見る。

## 6. Claude Code 側の実仕様（推測防止用の裏取り）

裏取りの出所は実運用のハーネスと公式ドキュメント。**「実測」と印のあるものは版によって変わりうる** —
食い違ったら公式ドキュメントと実機を正とし、この表を直す。

### 6.1 frontmatter の綴り対照 — skill と agent で同義フィールドの綴りが違う

**ここは必ず間違える。**

| | skill（`SKILL.md`） | agent（`.claude/agents/*.md`） |
|---|---|---|
| ツール禁止 | `disallowed-tools`（ハイフン） | `disallowedTools`（キャメル） |
| ツール許可 | `allowed-tools` | `tools` |
| 発火の限定 | `paths`（glob） | — |
| ループ上限 | — | `maxTurns` |
| 権限モード | — | `permissionMode`（`default` / `acceptEdits` / `auto` / `dontAsk` / `bypassPermissions` / `plan`。`manual` は `default` の別名） |
| 記憶 | — | `memory`（`user` / `project` / `local`） |
| 隔離 | — | `isolation: worktree` |
| その他 | `when_to_use` `argument-hint` `arguments` `disable-model-invocation` `user-invocable` `model` `effort` `context: fork` `agent` `background` `hooks` `shell` `metadata` | `model` `effort` `skills` `mcpServers` `hooks` `color` `background` |

- **`permissionMode` / `tools` / `disallowedTools` / `maxTurns` で権限とループ上限を agent 単位に絞れる**
  （`settings.json` の `permissions.deny` はセッション全体に効く。禁止を agent 単位で掛けたいなら
  agent の frontmatter を使う）
- **subagent は skill を自動継承しない。** `skills:` に明示した場合だけ。組み込み subagent は skill 不可
- `description` ＋ `when_to_use` は skill 一覧で打ち切られる（実測 1,536 字）。要点を先頭に
- **配布を見据えるなら6フィールドに絞る**: claude.ai アップロード・Skills API・`package_skill.py` は
  `name` `description` `license` `compatibility` `metadata` `allowed-tools` **以外があるとハードエラー**。
  作った skill をあとからプラグインとして配る予定があるなら、ここは最初から効いてくる

### 6.2 hook

hook は5種 — `command`（プログラム判定）/ `prompt`（日本語のルール文をモデルが判定）/ `agent` / `http` / `mcp_tool`。
**発火は型によらず必ず起きる。違うのは判定者だけ。** 取り返しのつかない操作は `command`、
条件が書き出しにくいものは `prompt`。パスは `${CLAUDE_PROJECT_DIR}` で書く（相対パスは危険、絶対パスは共有できない）。

イベントで実績があるのは `PreToolUse` `PostToolUse` `Stop` `PreCompact` `Notification`。
ほかにも多数ある（`SessionStart` `UserPromptSubmit` `SubagentStop` `PostToolUseFailure` `PermissionRequest` 等。
一覧は公式ドキュメント）。実績の無いイベントを使うなら「実績なし」と実装のレビューに明示する。

絞り込みは**2段**。`matcher` はツール名（`"Edit|Write"` `"Bash"`）、`if` は対象条件
（`"Edit(frontend/src/**)"` `"Bash(gh pr merge *)"`）。`matcher` の1段だけでは不足。

```json
{ "type": "command",
  "if": "Edit(frontend/src/**)",
  "command": "node \"$CLAUDE_PROJECT_DIR/.claude/hooks/quality-check.js\"",
  "async": true, "timeout": 330 }
```

ブロックは hook の **exit 2**。stderr に書いた文字列がそのまま Claude に渡る
（`PreToolUse` は `permissionDecisionReason`）。**「ダメです」だけ返すと別経路を探し始める**ので、
代わりにどうすればよいかまで書く。出力は長いと打ち切られる（実測 10,000 字）。

設定の優先順位（強い順）: managed → `claude --settings` → `.claude/settings.local.json` →
`.claude/settings.json` → `~/.claude/settings.json`。
**`deny` と `ask` は即時に効くが、`allow` はワークスペースの信頼を受け入れるまで効かない。**

### 6.3 いつ効き始めるか（承認をどこで取るかを決める）

| 成果物 | 効き始め | 承認 |
|---|---|---|
| `settings.json` の hooks / permissions | **保存した瞬間**（ファイル監視） | 書く前に内容そのもの |
| **既に `settings.json` から参照されている**スクリプト | **保存した瞬間**（次の発火から） | 書く前に内容そのもの |
| まだ参照されていないスクリプト | 参照する設定を書くまで不活性 | 作ってから見せてよい |
| skill / agent / rules | 呼ばれる・該当パスに触れるまで不活性 | 作ってから見せてよい |

図1枚単位の再実行（既存ハーネスの改修）では、2行目を必ず踏む。
「スクリプトだから安全」という判断は、そのスクリプトが既に参照されている時点で崩れる。

### 6.4 書いても登録されないことがある（サイレント失敗）

- agent に `name` が無いと**ドキュメント扱いで黙って無視される**。`description` が無い・YAML が壊れている・
  `name` に `:` が入る場合は debug ログにしか出ない → `claude --debug`
- skill と hook はファイル監視で**再起動なしに反映される**。ただし
  **セッション開始時に存在しなかったディレクトリを新設した場合は再起動が要る**
- **新規 agent はファイル監視では反映されない。** `claude plugin validate --strict` が exit 0 でも、
  同一セッション内では `subagent_type` として解決されず `Agent type '<name>' not found` になる。
  Agent ツールが見る型の一覧は**セッション開始時に確定する**。
  → **新規 agent を作った回は、そのセッションでは実起動検証ができない。** 合格条件に「実起動して動く」を
  入れるなら再起動後に測る。再起動を頼むのは `harness-compose`、登録を確かめるのは `harness-evaluator`。
  ファイルを書いた時点で「登録された」と書かない
- **MCP ツールは `tools:` に書くだけでは呼べないことがある（実測）。** agent の frontmatter に
  `mcp__drillspark__get_diagram` 等を列挙しても、起動時点で deferred（スキーマ未ロード）のまま
  直接呼び出せない版がある。公式ドキュメントは自動ロードと記述しているが、
  → **MCP を使う agent は `tools:` に `ToolSearch` を含め、本文に
  `ToolSearch(query="select:<名前をカンマ区切り>")` のロード手順を書く**と、どちらの版でも動く。
  `tools:` への列挙は「許可」であって「ロード」ではない
- ネストした `.claude/skills/` は起動時に読まれない。そのディレクトリのファイルを触って初めて出てくる
- 同名 skill の解決順は **個人 > プロジェクト > プラグイン**。組み込み skill と同名にすると置き換わり、
  組み込みの別名では呼べなくなる

### 6.5 プラグインとして配るときの制約

- **`plugin.json` はキーごとに受ける形が違う**。`agents` にディレクトリ文字列を
  渡すと `validate` が `agents: Invalid input` で落ちる。`["./agents/a.md","./agents/b.md"]` の
  **ファイルパス配列**にすると通る。`skills` はディレクトリ文字列で通る。
  公式ドキュメントは両方 `string|array` と書いているので、**ドキュメントだけを根拠にしない**
- **プラグインは rules を配布できない**。`.claude/rules/*.md` に相当する機構が無く、
  プラグイン root の `CLAUDE.md` も読まれない。代わりに skill 本文へ書くか hook で検証する。
  判定基準のように**生成側が書き換えられない場所**が要るものは、プラグイン同梱の参照ファイルにして
  エージェントに `${CLAUDE_PLUGIN_ROOT}` 経由で明示的に読ませる（skill 本文でも展開される。2.1.196+）。
  自動注入されないぶん、**読めなかったときに判定させない指示**をエージェント側に足す必要がある
- **DrillSpark のエッジのラベルを数字で始めない**（`|"0（書き込まれる）"|`）。保存時にその数字がノードIDとして
  読まれ、別ノードが生えて既存ノードのラベルが壊れる。`validate_diagram` も diagram-lint も通るので、
  保存後にエディタで見るまで分からない。ラベルは「はい（exit 0）」のように語から始める（実測）
- **プラグインは hook を配れる**。`hooks/hooks.json` に `settings.json` の `hooks` と同じ形で書き、
  command は `node "${CLAUDE_PLUGIN_ROOT}/scripts/….js"` で自分の同梱スクリプトを指す（`validate --strict` も通る。実測）。
  対象を絞る `if` は使わず、スクリプト側でパスを見て対象外は exit 0 で素通しにする —
  全 Write に発火するので、判定しない経路を最初に短く抜ける
- **プラグイン root に `CLAUDE.md` を置くと `validate --strict` が落ちる**。
  「プラグイン root の `CLAUDE.md` はプロジェクトコンテキストとして読み込まれない」という警告が出る。
  リポジトリ＝プラグイン root のとき（配布用の単独リポジトリはこの形）に必ず当たる。
  **`.claude/CLAUDE.md` に置けば読み込まれ、`--strict` も通る**

### 6.6 確認と検証の手段

| 何を | どうやって |
|---|---|
| 綴り違い・未知フィールド | `claude plugin validate <dir> --strict`（v2.1.233+。`--strict` 無しだと警告のまま通る）<br/>プラグインでなくても通る — `.claude/agents` や `.claude/skills` のディレクトリを直接渡せる |
| hook の登録状況 | `/hooks`（読み取り専用。どの設定ファイル由来かまで出る） |
| skill / agent の登録状況 | `/skills` / `/agents` |
| hook の入出力 | `claude --debug` |
| 環境全体 | `/doctor` |

## 7. 無視する要素（生成物・表示用）

`click … call onMermaidClick(…)` / `classDef` / `class` / `style` / `linkStyle` /
`%% rowOrder:` / `%% Theme Definitions` ブロック / `%% duration[id]:` / `%% cost[id]:` /
`%% nodeStyle[id]:` / `%% noteStyle[id]:` / `%% subgraphStyle[名前]:` / ラベル内の `⏱ N 分` / `<br/>`。

duration・cost はハーネス設定に対応物が無い。SKILL.md の所要時間目安として本文に回すだけで、
設定生成には使わない。

> **図を書き戻すとき（harness-improve 用）**: `update_diagram` は図を**全置換**する（規約§6.2）。
> 省いた `%% note` `%% cost` `%% nodeStyle` `%% noteStyle` `%% subgraphStyle` は消える。
> 必ず `get_diagram` してから、変更しないメタデータを再送すること。
> `%% rowOrder` と Theme Definitions は保存時に再生成されるので送らない。
