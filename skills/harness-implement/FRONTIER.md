# フロンティア洗い出し — 図が決めていないことを潰す

図は**構造しか持たない**。「何が・誰から誰へ・どの順で」までで、
文言・上限・権限・宛先・パス規約・強制の在処は載らない。
**そこを黙って仮定すると、仮定した箇所がそのまま欠陥になる。**

思想の出典: [Grill me](https://www.aihero.dev/skills-grill-me) と
`mattpocock-skills:grilling` スキル。ハーネス設計に合わせて具体化してある。

## 進め方

1. **決定木として扱う。** 前提がすでに決まっている問いだけが「フロンティア」。
   ある問いの答えが同ラウンドの別の問いに依存するなら、それは**次**のラウンドの問い
2. **フロンティア全部を1ラウンドで出す。** 1問ずつ聞かない。番号を振り、各問に推奨回答を付ける

   ```
   ❓ Q1 — <見出し>: <本文。選択肢があれば列挙>
   ➡️ 推奨: <答え> / 理由: <なぜ> / 逆を選ぶと: <何が起きるか>
   ```

   **推奨には必ず「逆を選ぶとどうなるか」を付ける。**
   推奨だけ並べると「同意・同意・同意」で流れ、長いのに何も決まっていない状態になる
   （記事が最大の失敗モードとして挙げているのがこれ）
3. **事実を調べるのは自分の仕事。ユーザーに聞かない。**
   リポジトリ・既存スキル・設定ファイル・ドキュメントで分かることは調べる。
   調べられないものだけ聞く — オーナーの私的情報・組織の方針・まだ決めていない運用
   - 実例: ブログ執筆ハーネスを作ったとき、記事の文字数閾値は既存 skill の本文に書いてあったので
     調べて済ませ、記事に出してはいけない社名はどこにも無いので聞いた。**この線引きが正しい**
4. **調査で止まらない。** 調べ物はサブエージェントに投げ、その結果に依存する問いだけ次ラウンドへ回す。
   残りのフロンティアは先に聞く
5. **フロンティアが空になったら終わり。** 空＝黙って仮定した枝がゼロ。
   ここまで来てから合格条件を書く
6. **紙で答えが出ない問いは作って見る。** 「レーンを2つに割るべきか」「lint はうるさすぎないか」は
   議論では決まらない。dry-run して現物で判断する

## 網羅チェックリスト（ハーネスは必ずこれを持つ）

図に書いていないなら、書いていないこと自体が答えではない。**フロンティアの問いにする。**

| # | 観点 | 落ちていたときに起きること |
|---|---|---|
| 1 | **人間の介入点**（MAPPING.md 2.1 の5種） | エージェントが勝手に外に出る |
| 2 | **強制の在処と置き場** — お願いか、フックか、権限か。常時オンでよいか（MAPPING.md 3.1） | 仕組みを作ったのに誰も起動せず、実質ゼロ。置き場を誤ると全セッションのトークンを食う |
| 3 | **ループ上限とエスカレーション先** | Doom Loop。宛先未定義だと「人間へ」が誰にも届かない |
| 4 | **権限** — 何を禁止し、何を確認させるか | 検証基準を被検証者が書き換えられる |
| 5 | **検証基準の置き場所と、合格を決定論で判定できる形にしたか** — テストデータはどこに置き、何をもって通ったとするか | verifier-deployment gap。決定論に落とさないと、評価が「動いたように見える」の報告になる |
| 6 | **成果物のパスと命名規約** — `設計.md` は `docs/harness/<ハーネス名>/設計.md`、テストデータは `.claude/tests/<ハーネス名>/` | フックの `if:` 条件が書けない。評価役が物差しを見つけられない |
| 7 | **失敗時の挙動** — 止まるか、続けるか、誰に言うか | 黙って続行して被害が拡大する |
| 8 | **起動方法** — 手動か、自動か、何をトリガに | 自動化前提の設計を手動運用してしまう |
| 9 | **外に出る操作の実行手段** | `permissions.ask` のルールが書けない |
| 10 | **教訓の置き場所と上限** | 教訓プールが膨らみ実使用精度が崩落する |
| 11 | **処理と工程を混同していないか** | 工程が壊れる。一覧しか無いのに作図の操作を書くなど |

## 工程の混入（実測で2回起きた）

**処理**＝ハーネスが持つ独立したワークフロー（ブログを書く・動画を作る）。
**工程**＝その処理の中身。混ぜると工程が壊れる。→ [MAPPING.md](MAPPING.md) 1節

各図は**自分の工程の話だけ**をする。書き終えたら、前後の工程の操作が混じっていないか読み返す。

- **実例1**: 「処理の種類を考える」に「階層を1つ足す」「1図5〜10処理に収まる?」が入っていた。
  階層もレーンも**作図の操作**で、この工程ではまだ矢印を引いていない。
  同じ図の別ノードに「まだ矢印は引かない」と書いてあり、自己矛盾していた
- **実例2**: 上を直した直後、**親図の備考が古いまま残って**子図と食い違った。
  子を直したら親の備考も見る

見分け方は単純で、**そのノードの動詞が、いまの工程の成果物に対して実行できるか**。
手元に一覧しか無いのに「階層を足す」「レーンを切る」と書いてあれば混入している。

実測の裏付け（2026-08-22 初回適用）: 2番と1番を落とした。
lint を実装したのに起動する仕組みが無く（2番）、人間の介入点を5点中2点しか数えなかった（1番）。
**このチェックリストは、実際に落とした穴から作られている。**
