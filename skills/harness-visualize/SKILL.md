# harness-visualize — 処理1つを1枚の HTML にする

**これは処理であって工程ではない。** `目的を考える → … → 評価する →（改善する）` の連鎖には入らない。
`設計.md` を持つハーネスなら、**処理ごとに・いつでも**単独で呼べる。標準は〈評価する〉の直後。

**処理**＝ハーネスが持つ独立したワークフロー。**工程**＝その処理の中身。
可視化するのは**処理1つ分**で、複数の処理のノードを1枚に混ぜない。
ただし1枚の冒頭に**ハーネス全体の地図**（処理一覧・共有部品・介入点の総数）を持つ — 処理の粒度で書き、ノードは持たない。

1枚で答える問いは2つ。**この処理のどの作業が、どのファイルのどの部分で、何の仕組みとして効いているか。**
**このハーネス全体はどんな設計か（処理はいくつで、何を共有しているか）。**

## やらないこと（ここが濁ると役割が壊れる）

- **判定しない。** GO / NO-GO も合否も書かない。判定は `harness-evaluator` の仕事。
  評価結果があるなら**転記するだけ**で、可視化側で採点し直さない
  （判定を持たせると、生成側が自分の合格線を描くことになる）
- **直さない。** ズレを見つけても直さない。直すのは `harness-improve`
- **図を書き換えない。** 読むだけ。`update_diagram` はこのスキルの許可ツールに無い
- **推測で埋めない。** 入力に無いものは「無し」「未記録」と描く

## 入力（物差しは `docs/harness/<ハーネス名>/` のファイルだけ）

| 入力 | 出所 | 無いとき |
|---|---|---|
| 設計 | 索引 `docs/harness/<ハーネス名>/設計.md` と、描く処理の `処理/<処理名>/` | **これが無ければ実行しない。**止めてオーナーへ報告する |
| 図 | `処理/<処理名>/図.md` が指す DrillSpark（`get_project` / `get_diagram`）、または渡された `.mmd` | 「図 無し」と描き、工程は設計の記述から並べる。**ただし下を読む** |
| 実測 | `処理/<処理名>/実装.md`／`評価/<日付>.md`／**明示的に渡された記録ファイル** | 全工程を `設計のみ` と描き、そう明記する |
| 実装先 | `処理/<処理名>/実装.md` の**実物**を優先し、無ければ `合格条件.md` の成果物一覧。工程がどのファイルのどこになったか・何の仕組みか | その工程を `未記録` と描く |
| 全体 | `設計.md` の処理一覧（状態列）／`統合.md`（1つにまとめたもの・介入点の総数）／**他の処理の `実装.md` 2節**（作ったものの一覧だけ） | 統合が無ければ「統合 未実施」と書き、在るものだけで地図を描く |

**この処理だけは他の処理のフォルダを読んでよい。** 描く側が前の処理を見ない分離は作図の混入を防ぐためのもので、
可視化は描かないので当たらない（統合と同じ理由）。読むのは全体の地図に要る一覧だけで、他の処理のノードは持ち込まない。

**「図 無し」と「図が取れない」を混同しない。** `設計.md` が DrillSpark のプロジェクトを参照しているのに
`mcp__drillspark__*` が使えないなら、それは**図が無いのではなく繋がっていない**。
`設計.md` に図の参照があるときは `list_projects()`（接頭辞は `mcp__drillspark__` か `mcp__claude_ai_DrillSpark__`） を1回流して確かめ、
繋がらなければ**止めて案内する** → [`reference/drillspark-setup.md`](../../reference/drillspark-setup.md)。
黙って「図 無し」と描くと、**在る図を無いことにした1枚**が残り、次の人はそれを現状として読む。

**実測ファイルのパスを決め打ちしない。** `実行記録.md` のような名前を実行役は発明しがちだが、
`reference/設計.md.template` は定義していない。渡されたものを読む。
**渡されなければ聞かずに `設計のみ` で描く**（人間の介入点を増やさない。
承認を連打させる設計は承認そのものを無力化する）。

**止まるのは `設計.md` が無いときだけ**。物差しが無ければ描けるものが無い。

**設計側のファイルに無いものは描かない。**〈評価する〉と同じ物差しにしておかないと、
可視化だけが独自の事実を持ち始める。

## 手順

1. **入力を集める。** 上の表の5行。どれが手に入り、どれが無いかを先に確定させる。
   **`設計.md` が無ければここで止めてオーナーへ報告する**。
   **読むのはこの5行と、`skills/harness-implement/MAPPING.md` の 2.1節・3.1節だけ。**
   プラグインの `scripts/`・`tests/`・他の skill 本文・見本を読まない（契約は次節に全部書いてある）。
   `tests/run.sh` を走らせない。ブラウザで描画確認をしない — 1枚の合否は lint と読み戻しで決める。
   実測で、この範囲を超えて読んだ回は入力集めだけで時間を使い切り、1枚が出なかった
2. **構造を決定論で取り出す。** 図からノードID・形状・ラベル・レーン・エッジを機械的に拾う。
   LLM の読解で数え直さない。取れないもの（ループ上限・エスカレーション先）だけ備考と設計から読む
3. **実測と実装先を工程へ突き合わせる。** ノード単位で `通った` / `止まった` / `設計のみ` の3値にする。
   **実測が無い工程を `通った` にしない。**「記録が無い」と「通らなかった」は違うので、
   どちらも `設計のみ` に寄せて、記録が無い旨を書く。
   あわせて**実装先（ファイル＋箇所＋仕組み）を `処理/<処理名>/実装.md` から転記する**。
   仕組みの語彙は4つ — **指示**（本文のお願い）／**確認**（`permissions.ask`・`AskUserQuestion`）／
   **柵**（hook の exit 2・`permissions.deny`）／**agent**（別コンテキストへの委譲）。
   `skills/harness-implement/MAPPING.md` 3.1節の置き場と 2.1節の介入点から降ろした、この処理の正本の語彙。
   **実ファイルを読んで埋め直さない** — 読んで書くと、可視化が設計側と違う事実を持ち始める。
   （**全文の引用のために読むのは可**。禁じているのは「対応づけを実ファイルから起こすこと」で、
   そのまま貼る引用ではない）
   `実装.md` にも `合格条件.md` にも無ければ `未記録`。**`未記録` と「対応物が無い（`—`）」を混ぜない**
4. **ハーネス全体の地図を組む。** 処理一覧（状態・起動・成果物・介入点の内訳）、共有部品（`settings.json` の hooks と
   permissions・`CLAUDE.md`・評価基準・合格条件の置き場）、処理 × 部品の表、介入点の総数。
   材料は入力表の「全体」行だけで、**ノードの粒度には降りない**。この1枚の処理を目立たせる
5. **HTML を組み立てて書き出す。** 契約は次節。**HTML は直接 Write する** — 生成スクリプトや中間ファイル
   （JSON・一時ディレクトリ）を作らない。作業ディレクトリの外には何も書かない。
   **1枚の目安は 60〜120 KB。** 超える見込みなら、実ファイルの抜粋と子図の Mermaid 原文から削る（SVG と表は削らない）。
   材料が揃ったら**考え込まずに書く** — 書いてから lint と読み戻しで直すほうが、1回で完璧を狙うより速い。`docs/harness/<ハーネス名>/可視化/<処理名>-<日付>.html` に
   **Write で**書く（Edit で部分修正しない — 直すときも全体を書き直す）。
   先頭に**回数欄** `<!-- 直し: 0/2 -->` を置く（`<!doctype html>` の直後）。
   **同じ処理・同じ日に2回目を出すときは上書きしない。** `<処理名>-<日付>-2.html` のように連番を足す。
   「既存物を書き換えない」ことが、この処理に承認ゲートを置かなくてよい根拠になっている
6. **書き出しは PreToolUse hook（`scripts/harness-view-guard.js`。プラグインが `hooks/hooks.json` で配る）が
   書く前に検査する** — 既存の1枚への上書き／回数欄の上限／view-lint の違反／Edit を exit 2 で止め、
   代わりにどうすればよいかを返す。これは指示ではなく**柵**で、本文の指示より強い。
   止められたら**直すのは HTML のほう**。指摘どおり直し、**回数欄はそのままで** Write し直す —
   止められた回はファイルが書かれていないので進めない。進めるのは、書けた1枚を読み戻して直すとき（`1/2`、`2/2`）。
   回数は hook が数えるので自分で数えない。**上限2回**を超えたら hook が書かせない —
   **止めてオーナーへ報告する**（何がどう落ちたかを添える）。直し続けない。
   lint の実行エラー（exit 1）は HTML の直しでは消えないので、直さずに報告する。
   手で確かめるときは同じ lint を単体で走らせられる:

   ```bash
   node "${CLAUDE_PLUGIN_ROOT}/scripts/harness-view-lint.js" docs/harness/<名>/可視化/<処理名>-<日付>.html
   # exit 0 = 合格 / 2 = 違反あり / 1 = 実行エラー
   ```

7. **読み戻す。** 書いたファイルを開き直して中身を確認する。成功メッセージを完了根拠にしない。
   二重改行や重なりのような lint が見ない欠陥を見つけたら、直して回数欄を進め、5 から書き直す
   （その直しも上限2回に含まれる）

## 出力 HTML の契約（lint が見る）

| | |
|---|---|
| 置き場 | `docs/harness/<ハーネス名>/可視化/<処理名>-<日付>.html` |
| 形 | **1ファイル完結。** CSS / JS はインライン、画像は `data:` URI。**外部読み込みゼロ**（CDN も不可） |
| 回数欄 | 先頭に `<!-- 直し: N/2 -->`（初回 0）。hook が読み、上書きと上限を止める。lint は見ないが hook が見る |
| ノード注釈 | 工程・介入点の表の行に `data-node-id="2_1"`（数値ID形式・**ページ内で一意**） |
| 節 | `data-section` を7つ: `目的` `処理一覧` `工程` `介入点` `合格条件` `成果物` `未完` |
| 図 | Mermaid 原文を `<pre class="mermaid">` に置く（**`<details>` に畳んでよい**。下記） |
| 状態 | `設計のみ` / `通った` / `止まった` の3値 |

**`data-node-id` はページ内で一意。** 同じノードを2箇所に書けないので、
**節を増やして同じノードを再掲する形にはできない**。ノードごとの情報は
「そのノードが1回だけ出てくる表」に**列として足す**。
図・逆引き・実ファイルの部分など、**表の行以外から同じノードを指すときは `data-ref`** を使う
（lint は `data-node-id` しか数えない。この使い分けが両方向のリンクを成立させる）。
スクリプトの中に `data-node-id=` の並びを文字列で書かない — lint はそれも属性として拾う。
属性名と `=` を分けて連結する。

### 画面の作り（lint は見ない。だが必ずやる）

lint が見るのは上の表だけで、以下は**通ったことが根拠にならない**。それでも外すと1枚の価値が落ちる。
実例は同梱の見本ではなく、この節が正本。

**冒頭 — ハーネス全体の地図**（`処理一覧` の節に置く）

- **3レーンの SVG**: 起動する人 ／ 処理（1処理＝1プロジェクト＝入口の skill）／ ハーネスに1つしかないもの。
  処理の箱は枠線でその処理の実測（通った・止まった・設計のみ）を示し、**この1枚の処理を塗って目立たせる**。
  線の文法は1枚の中で1つ: **実線＝制御（起動・呼ぶ・工程の順）、点線＝データや部品の読み書き**。
  オーナーが起動しない処理には起動の線を引かない（「起動 0」の処理に線があると表と食い違う）
- **処理ごとのカード**: 状態・起動・成果物・介入点5種の内訳・その処理の1枚への相対リンク（`<a href="./…">`。
  読み込み位置ではないので lint は通す）。**リンクを張るのは `可視化/` にその1枚が実在するときだけ**。
  無ければ「まだ描いていない」と書く — 無いファイルへのリンクは推測で埋めたのと同じ
- **処理 × 部品の表**: 行＝ファイル、列＝処理、末尾に「1つだけ」列。この1枚の処理の列を強調する
- **介入点の総数の表**: `統合.md` の表をそのまま転記。統合が無ければ「統合 未実施」と書き、処理ごとの内訳だけ出す

**中央 — 工程 → 実装先**（`工程` と `介入点` の節）

- **この処理の root 図（第一階層）はインライン SVG で描く。** `<pre class="mermaid">` はブラウザで開いてもただのテキストなので、
  **図として読めない**。外部ライブラリは禁止なので、BPMN の形（角丸＝terminal / 角＝process /
  ひし形＝decision / 円柱＝data store / 底が波＝document）を**自分で SVG に描く**。
  **子図（ドリルダウン）は SVG にしない** — 決定論の表と `<details>` の Mermaid 原文で足りる。
  実測で、子図まで全部 SVG にすると1回の Write が大きすぎて1枚が出なかった。
  状態の3値は**枠線と印**に乗せる（通った ✓ 緑／止まった ■ 琥珀／設計のみ ○ 灰の破線）。
  印は図のノード・表の状態セル・凡例で同じ文字を使う — 色だけだと緑と琥珀の実線は区別できない。
  凡例を「枠の色と印＝状態」「線」「形＝種別」の3群に分けて添える
  — 状態と記法を1つの凡例に混ぜると、読み手は「緑の矢印」を探して見つけられない。
  **子の図（サブフロー）を持つノードは枠を太くして「▾ サブフロー」と添え、
  その節の先頭にパンくず（`記事を書く › 2 構成を作る`、現在地だけ塗る）と「階層 N」を置く**
- **図のノードは `<a href="#表の行" data-ref="…">` で包む。** クリックすると表の行が選択され、そこへ飛ぶ。
  `aria-label` にノードIDと工程名を入れる（読み上げとキーボードで同じ経路が通る）
- **Mermaid 原文は捨てず、`<details>` に畳む。** SVG は手で描いたものなので**原文が正**。
  ズレたときの突き合わせ先と、ノード記法の出所が要る
- **表の列は 8つ**: ノード／工程／状態／何になったか／**仕組み**／実装先ファイル／箇所／転記元。
  「何になったか」は MAPPING.md 3節、「仕組み」は手順3の4語で転記する。
  仕組みは色付きのチップ（指示 ·／確認 ?／柵 ⊘／agent ⇢）にし、**破れるもの（指示）と破れないもの（柵）が一目で分かる**ようにする。
  agent の色は状態「通った」の緑と別にする（同じ緑が2つの意味を持つと行を読み違える）。
  チップの語彙の説明は表の**上**（絞り込みの隣）に置く — 表を読み終えてから語彙を知るのでは遅い
- **成果物の節**は `実装.md` 1節の成果物（ファイル名と役割）を転記する。無ければ「無し」と書く
- **状態で絞り込むボタン**（すべて／通った／止まった／設計のみ）を表の上に置く。
  「止まった」だけを見る読み方が評価のあとの標準
- **実装先ファイル／箇所から、実ファイルの該当部分へ飛べるようにする**（インライン JS）。
  `<a href="#…">` を付けてキーボードからも到達できるようにする。
  マウス専用にすると Tab で辿れず、読み上げにもリンクとして出ない

**後半 — ファイル → ノード と 実ファイル**

- **`ファイル → ノード` の節（逆引き）を足す。** 行＝ファイルの部分、列＝担う作業（ノード）と仕組み。
  1つのファイルが複数の作業を担うとき、**部分ごとに分けて見る**のがこの節。ノードは `data-ref` で指す
- **`実ファイル` の節を足し、登場したファイルの効いている部分だけを行番号つきで `<details>` に畳んで埋め込む。**
  前後2〜3行を含めて**1ファイル最大 40 行**。**全文は埋め込まない** — 実測で全文だと 130 KB を超え、
  1回の Write で1枚が出なかった。プラグインが配るファイル（`${CLAUDE_PLUGIN_ROOT}` 配下）は読まず、パスと役割だけ書く。
  リンクにしない — 1ファイル完結なので、リンクは渡した先で切れる。
  **効いている部分は行の範囲で囲み、左に色の帯と「ノード 2 構成を作る（承認で止まる）」のラベルを付ける**。
  1行だけの印にしない — 手順の2〜3番のように、部分は複数行にまたがる。
  **部分をクリック（または Enter）すると図のノードと表の行が選択されて戻れる**（両方向）
- **埋め込むと私的情報チェックが本文にも効く**。実ファイルに絶対パスや UUID があれば
  この1枚は落ちる。これは不便ではなく、**渡せない1枚になったことがその場で分かる**という意味

**全体**

- **追従する目次**を先頭に置く（目的／ハーネス全体／工程 → 実装先／介入点／合格条件／成果物／ファイル → ノード／実ファイル／未完）。
  右端に「処理名／日付」を出し、いまどの処理の1枚を読んでいるかを常に見せる
- **決定論で作った表を必ず併記する。** SVG が壊れても表があれば情報は落ちない
- ダークテーマ（`prefers-color-scheme`）と `prefers-reduced-motion` に追従する。色だけで状態を伝えない（破線・印を併用）
- **色・字・余白は `:root` の意味役トークンで持つ**（neutral／accent 1色／状態 3／仕組み 4。
  罫線と余白で区切り、表は横罫だけ、影は最小、外部フォントなし）。生の色コードを本文に散らさない

**本文中のリンクは通る。** 出典 URL を `<a href="https://…">` で残してよい。
lint が見るのは**読み込み位置**（`link href` / `src` / `url()` / `@import`）だけ。

**節は中身が無くても出す。** 「無し」と書く。書かないのと「無い」と書いてあるのは違う。

## 合格条件

**1枚の合否**は手順6の lint（柵が書く前に掛ける）と手順7の読み戻しで決まる。

**このスキル自身**（lint と柵）の合格条件は、プラグイン同梱の `tests/ok-view-*.html` `tests/ng-view-*.html` に凍結してある。
各サンプルは**期待するコードと件数**を `expect:` 行に持ち、ランナーが**終了コードだけでなくそれも照合する**。
これはプラグインの保守用で、**可視化を実行するときには走らせない**（走らせても1枚の合否は変わらない）。

```bash
bash "${CLAUDE_PLUGIN_ROOT}/tests/run.sh"   # 保守用。lint の期待挙動 ＋ 同梱ファイルの存在（件数はランナーの出力が正）
```

**落ちたときに直すのは実装であって条件ではない。** `tests/run.sh` は凍結した合格条件で、
生成側の都合で書き換えない。

## 教訓（最大10行・超えたら統合してから追記）

- 可視化は「見た目が出た」で完了にできてしまう。**外部 CDN 1本**と**絶対パス1行**は目視で落ちるので、
  出したら必ず lint を通す
- 逆に **lint が通っても「読める1枚」にはならない**。lint は図が読めるかを見ていないので、
  `<pre class="mermaid">` を貼っただけの exit 0 が作れてしまう。**開いて見るまで完了にしない**
- 押せるものを足したら、**Tab で辿れるかを確かめる**。`href` の無い `<a>` は
  マウスでしか動かず、それは目で見ても分からない
- `<pre>` の中で行を `<span>` で包むと、改行が二重になる。`pre` を `white-space: normal`、行だけを `pre` にする。
  部分のラベルは行の上に置く — 重ねると本文と衝突する。**実描画でしか出ない**
