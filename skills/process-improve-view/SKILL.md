# process-improve-view — 改善計画を1枚にする

**業務ひとつを指定して単独で呼べます。** `process-improve` の連鎖には入りません。

```text
材料をそろえる → 1枚に組み立てる → 利用者に渡す
```

**判定はしません。描くだけです。** 合否を持つのは `process-improve-reviewer` と判定基準ファイルの側です。

## 1. 材料をそろえる

**利用者の `業務改善/` から4つ読みます** — 業務一覧 ／ 改善案 ／ AI化依頼書 ／ 保留。

**読めないものがあっても止まりません。無いものは「無い」と記録して先へ進みます。**
**1つも無いときだけ**「先に業務の棚卸しから始めてください」と1回案内して終わります。

### 対象の業務を1件に絞る

業務一覧から近い行を探します。**表記ゆれがあるので完全一致だけでなく近い行も残します。**

**1件に絞れないときは候補を並べて選んでもらいます。**
素人が見分けられる項目（担当・きっかけ・時間）を添えます。**生の行をそのまま出しません。**
**「どれでもない」も選べるようにします** — 選べないと、近いだけの別業務を選ばされます。

「どれでもない」なら「その業務は一覧に見つかりません。先に棚卸しをしてください」と伝えて終わります。**1枚は作りません。**

### 図を取り寄せる

業務一覧の**「図の在りか」列**（DrillSpark の URL）から取ります。**列の最初の URL が現状の図**です。
`改善後:` に続く URL があれば改善後の図で、1枚にはその業務の見出しにリンクとして添えます（図の中身は取り寄せません）。
**まだ図を描いていない業務は列が空**なので、呼ぶ先がありません。そのまま次へ進みます。

**「未確認」「一般例」の印も、どのノードの分かが分かる形で一緒に取ります。**
切り離すと、1枚に載せるときに付け直せません。

**図が返ってこなかったら、試したことと返ってきたものを事実だけ書き留めます。**
文章にするのは次の工程です。

### 取り寄せられなかった経緯を書き起こす

**「図 無し」と1語で済ませません。** 5つを1つの文章にします。

> いつ ／ どの業務の図を ／ どう取ろうとして ／ 何が返ったか ／ **次に何をすれば取れるか**

**読み手は業務改善の素人で、この文章はそのまま1枚に載って社内で共有されます。**
エラー文言をそのまま載せず、「業務一覧に図の在りかが書かれていなかった」のように
**心当たりを持てる言い方**にします。**次にやること**（「先にこの業務の図を描いてから、もう一度呼ぶ」）まで書きます。

**記録に無いことをここで補いません。** 補うと、確かめていない話が1枚に載ります。

## 2. 1枚に組み立てる

**8つの塊**の置き場所を先に固定します。

```text
成功の形 → 図または取れなかった経緯 → 改善案 → 誰がやるか → 優先度 → ECRSのどれか
  → AI化依頼書 → 保留
```

**この8つの名前は検査が見る文字列そのものです。** 言い換えずにこのまま使ってください
（`data-block` の値になります）。

| 塊 | 置き方 |
|---|---|
| **成功の形** | **1枚の先頭に1回だけ。** 業務に1つの値なので表の列にしない |
| 業務の図 | 工程（第一階層）を並べ、開くと作業（第二階層）が出る形。<br>**取れなかった回は経緯の文章が図の場所に入る** — 隅の注記ではなく図の代わり |
| 改善案 | **図のどの工程に付くかを線でつなぐ。** 工程に紐づかない改善案を宙に浮かせない |
| 誰がやるか・優先度・ECRS | 色を分け、**優先度の順に並べる**。<br>**「人がやる」は今日から始められるので上に置く** |
| AI化依頼書・保留 | 末尾。保留には相談先の名前が入っている |

**改善案の並びは変えません。** `process-improve` が並べた順のままで、並べ替えも取捨もしません。

### 「不要」の語は1枚に出さない

業務一覧で「仕事の目的」が `不要` の業務は、**「なくす候補（本人申告）」と言い換えて**載せます。
1枚はそのまま社内で共有されます。本人が自分の業務に付けた `不要` の語が共有物に残ると、
「自分の仕事を減らす報告書を自分で書かされる道具」になります。
1枚の末尾に定型の1行を入れます — 「この計画は業務の手順を見直すためのもので、担当者の評価には使いません」。

### 印を目立たせる

**「未確認」（聞けなかった）と「一般例」（AIが一般論から補った）を、本文と同じ強さで見せます。**

小さく添えると読み飛ばされ、**確かめていないことが確かめた事実として社内に広まります。**

### 転記するだけ

**自分で事実を作りません。** 材料に無いものを1枚に足しません。
足りない塊は消さず、**「用意できなかった」と理由つきで**書きます。

## 3. 検査して直す

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/process-plan-lint.js" 業務改善/改善計画-<業務名>.html
```

**8つの塊と印がそろっているかを機械で数えます。人は止めません。**
書き出しは Write で行い、プラグインの PreToolUse hook が書く前に同じ検査を掛けます —
落ちた1枚はファイルになりません（壊れた1枚が良い1枚を上書きすることもありません）。
落ちたら**落ちた箇所だけ**を直します。1枚を作り直しません。

**上限3回。** 3回目でも足りないときは「用意できなかった」と明示して先へ進みます。

### 保存して伝える

名前は **`業務改善/改善計画-<業務名>.html`**（業務名は業務一覧の「業務名」列の綴りそのまま）。
**同じ業務を2回可視化したら上書きします。日付や連番で版を増やしません** —
版が並ぶと、素人には最新がどれか分かりません。業務が違えばファイルも別です。

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/file-saved-lint.js" <保存したパス>
```

**書き出したあとに実在を確かめます。** 確かめずに「保存しました」と伝えると、
読み手が存在しないファイルを探しに行きます。

伝えるのは**どこに置いたか**と**どう開くか**の両方です（ダブルクリックでブラウザが開きます）。
2回目からは前の1枚を置き換えたことも伝えます。

**保存できなかったときは**「保存できませんでした」で終わらせず、
どこに書こうとして何が起きたか・次に何をすればよいかまで伝えます。

## 人が止まる場所

| | |
|---|---|
| **起動** | 利用者が呼ぶ。**`process-improve` から自動で続きません**。業務を1つ指定します |
| **確認** | **無し。** 描くだけで判定しないので、承認する対象がありません |
| **人にしかできない作業** | 業務が1件に絞れないときに候補から1つ選ぶ（**可否を問うのではなく、どれかを決めてもらうだけ**） |
| **分からないときの相手** | 詰まった時点で利用者が指名する相手 |
| **合否の線** | **無し。判定しません。** 合否を持つのは判定基準ファイルの側（基準の決定＝無し。基準ファイルは `process-improve` 側のもの） |

## 書いてよい場所

**`業務改善/` 配下だけ。** DrillSpark は**読むだけ**で、図を書き換えません。
利用者の `.claude/` や `settings.json` も触りません。
