# harness-improve — ハーネス全体を改善する

7つの工程のうち**〈改善する〉**。対応表は harness-implement と共有する
→ [MAPPING.md](../harness-implement/MAPPING.md)

```text
処理を洗い出して表にする →［承認①］→ 処理ごとに理想図を対話で育てる →［承認②］
  → 処理ごとの差分 → 全処理ぶん繰り返す → 横断差分 → 設計.md に記録して終わる
```

## この工程の固有の仕事

**既存の実ファイルから契約を起こすこと。** `harness-implement` は**目的から**図を降ろす。
改善は**実ファイルから**図を起こす。成果物は同じ「図」でも、入力が逆を向いている。
この向きの手順を持っているのは改善だけで、だから引き継いだハーネスの入口になる。

**症状1つを直す工程ではない。** 直す対象を1枚に特定できるのは、図が既にあって
どこが壊れたか分かっている場合だけ。引き継いだ直後はその条件が揃わない。

### やらないこと

| | 誰の仕事か |
|---|---|
| **実ファイルを直す** | `harness-implement`〈実装する〉。改善は差分を作業指示として渡すだけ |
| **合格条件を決める** | `harness-implement`〈合格条件を決める〉 |
| **監査**（承認済みの図 ↔ 実ファイル） | 評価役。→ 末尾「監査との違い」 |
| **判定基準を動かす** | 改善は決めない。`reference/harness-design-criteria.md` は読むだけ |

## 前提 — 何も準備されていないところから始める

入口は2つある。**自分が作ったハーネス**と、**他人が作ったハーネスを引き継いだとき**。
**手順は分けない。違うのは「在るもの」だけ**で、それは0節で数えれば分かる。

| | 引き継いだとき | 自分で作ったとき |
|---|---|---|
| 図 | DrillSpark は作った人のアカウントにあり git の外。**読めないのが普通** | 在ることが多いが古い |
| `docs/harness/<名前>/設計.md` | 無い | 在るが実物とずれている |
| `.claude/rules/` `.claude/tests/` | 無い | 作った工程しだい |
| なぜそう作ったか | どこにも書かれていない | 覚えている。ただし**書かれていないことに変わりはない** |

> **分からない ≠ 欠陥。** 引き継いだハーネスには、こちらが知らない理由で置かれている部品がある。
> 意図が読めないものを「無駄」と判定しない。**一覧に載せてオーナーに聞く。**
> 自分で作ったハーネスでも、**覚えている理由は根拠にならない**。表に書いて初めて根拠になる。

**準備されていないものの中に、DrillSpark への接続だけは含めない。**
2節で理想図を作るので**必須**。0節を数える前に `mcp__drillspark__list_projects()` を1回だけ流し、
繋がらなければ**そこで止めて案内する** →
[`reference/drillspark-setup.md`](../../reference/drillspark-setup.md)。
1節の承認①を通してから詰まると、処理一覧の合意が宙に浮く。

## 0. 在るものを数える

一覧を作る材料であり、**どの節を書き換えてよいか**の判定でもある。

| 探すもの | 見るところ | 無いとき |
|---|---|---|
| 実ファイル | `.claude/{agents,skills,rules,tests}/`・`settings.json`・<br>`CLAUDE.md`・hooks が指すスクリプトの実体 | ここだけは必ず在る。**在るのがこれだけ、という状態があり得る** |
| 設計書 | `docs/harness/<ハーネス名>/設計.md` | 5節で**作る**（改善の主要な成果物） |
| 図 | `設計.md` のリンク／README／`.claude/` 内の DrillSpark URL | 2節で**新規に作る**。既存があっても他人のものは触らない |
| 凍結した合格条件 | `.claude/tests/`、`設計.md` の合格条件節 | **在るなら絶対に触らない**（5節） |

**自分で作ったハーネスでも数える。記憶で代用しない。** Glob と Read で済む。

## 1. 処理を洗い出して表にする

### 処理とは何か

**複数の skill・agent・hook・rules が総合して動く1つのワークフロー。**
ブログを書く、動画を作る、といった単位。

**skill を数えても処理の数にはならない。** このリポジトリ自身が反例で、
`harness-implement` は skill 1つだが中身は6工程、`harness-visualize` は skill 1つで処理1つ。
1:1 に見えるのは偶然で、あてにすると理想図が6工程分を1枚に押し込む形になり、
ノード数の上限で必ず破綻する。

**切り出す軸は「起動」。** 同じきっかけで動きだし、1つの成果物を出しきるまでが1処理。
部品の数ではなく、**流れの単位**で切る。

### 表の列

`docs/harness/<ハーネス名>/設計.md` に置く。**ここに無いものは評価が測れない。**

| 処理名 | 起動 | 使っている部品 | 成果物 | 何のために在るか | DrillSpark |
|---|---|---|---|---|---|

- **使っている部品** — skill / agent / hook / rules を実名で。
  **同じ部品が2つの処理に出てきたら、それが処理をまたぐ重複**で、4節の材料になる
- **DrillSpark** — 2節で作ったプロジェクトの URL。処理ごとに1つ。
  名前の規約は `<ハーネス名> / <処理名>`。**URL 列と名前規約の両方を持つ** —
  図が処理ごとに散っているので、表から辿れないと全体像が機能しない

### 「何のために在るか」だけは調べられない

**事実を調べるのは自分の仕事。** 処理名・起動・部品・成果物は実ファイルから調べる。
オーナーに聞かない。**調べられないのはこの1列だけ**で、ここを空のまま出す。

| 値 | 意味 |
|---|---|
| 散文1行 | この処理が在る理由 |
| **不要** | オーナーが要らないと判断した処理 |
| 空欄 | **まだ答えていない。承認が終わっていない** |

**「不要」を選択肢として先に見せる。** 人は理由を聞かれると後付けで作るので、
逃げ道が無いと惰性で在るだけの処理にももっともらしい理由が付いてしまい、
**消す候補が1件も出なくなる**。「不要」のほうが楽な状態にしておく。

引き継いだハーネスには目的が書かれていない。だからこの列は**既にある目的を参照する列ではなく、
目的を処理ごとに組み立てる列**。「このハーネスの目的は?」と白紙で聞く代わりに、
「この処理は何のために在るか」を処理の数だけ聞き、その答えを束ねたものが目的になる。

### ［承認①］処理一覧

**空欄を埋める作業が承認そのもの。** 全行が埋まった時点で承認が成立する。
粒度が違うと以降の図が全部ずれるので、**図より前にここを固める**。

## 2. 処理ごとに理想図を対話で育てる

**「不要」の処理には図を描かない。** 消すものの理想の姿を描く意味がない。
3節の差分表へ直行させる（「この処理を構成する部品を消す」1件）。

### 図は1枚だけ育てる

現状を描く → オーナーと話し合う → **その場で理想へ直す**。**現状図と理想図を2枚描かない。**
2枚残すと、次に引き継いだ人がどちらを契約と読むか分からない
（往復に不動点が無いという失敗が、そのまま再発する）。
経緯は DrillSpark の版履歴に残るので、**最新版が常に理想＝契約**になる。

**理想の出どころは目的だけ。** 判定基準 `reference/harness-design-criteria.md` は
あとから通す検査であって、理想の出どころではない。混ぜると「基準を満たす図」が
「目的を果たす図」を押しのける。

### 手順

1. **プロジェクトを新規に作る**（`create_project`）。処理1つに1つ。名前は `<ハーネス名> / <処理名>`。
   **他人のプロジェクトは読むだけ。** `update_diagram` は全置換で、図は git の外にあり、
   書き戻しに失敗して復旧できるのは作った人だけ。`update_diagram` を使うのは
   **この節で自分が作ったプロジェクトに対してだけ**
2. 実ファイルから読み取れた現状を描く。作図規約は `get_diagram_rules()`
3. **読めなかった箇所もノードとして置き、備考に「実ファイルから読めない。要確認」と書く。**
   図は空欄を描けない（ノードを置かないと線が繋がらない）。
   印を付けずに推測で描くと、**推測が図に定着してそのまま承認される** —
   オーナーは全ノードを疑って読むわけではない。話し合いはこの備考から始める
4. `validate_diagram` で**保存せずに検証する**。ただし**構文しか見ない**（2026-08-22 実測）。
   次は通ってしまうので自分で確かめる:
   - **タスクから複数の出力**は規約違反。分岐は decision `{}` から出す
   - **到達不能ノード**（database を後から足すと入力エッジを忘れやすい）
   - 差し戻しの**上限を超えたときの行き先**（上限だけ書いて行き先が無いと上限が無効）
5. 保存し、**読み戻す**（`get_diagram`）。success が返っても内容が巻き戻っていた実例がある。
   壊れていたら `list_versions` → `restore_version`
6. オーナーに URL を出して話し合う。**CLI に mermaid を貼らない** — 図はリンクに任せ、
   CLI にはレーンごとの箇条書きで「どの順に何をするか」だけ出す

### 往復は3回で切る

**3往復で合意に至らなければ、決まらなかった点を⚠オーナー判断として `設計.md` に書き残し、
その処理は保留して次の処理へ進む。** 上限だけ書いて行き先が無いと上限は無効なので、
行き先は**すべてオーナー**に統一する（目的が答えられない・処理が切り出せない場合も同じ扱い）。

**保留は失敗ではない。** 1つの処理で止まるとハーネス全体が進まず、全体を見た意味が消える。
**保留と記録されたこと自体が成果**で、次の改善の入口になる。

### ［承認②］理想図

**差分（3節）はこのゲートの材料**として一緒に出す。承認を2回に割らない。

> 既に `settings.json` から参照されているスクリプトに関わる変更は、**書く前に内容の承認**が要る
> （保存した瞬間から次の発火に効く）。→ harness-implement の「絶対に飛ばさない4点」1

## 3. 処理ごとの差分

**理想図が承認された時点で、実ファイル側が間違っていることは確定する。**
だから「どちらが正か」は差分表に要らない。要るのは**渡し方**。

| 差分の種類 | 理想図のノード | いまの実ファイル | implement へ渡す単位 | 優先度 |
|---|---|---|---|---|

**見るのは構造だけ。散文の言い回しの違いはズレではない。**
文言まで数えると件数が爆発し、承認が「全部まとめて OK」になる。それは承認ではない。

- 図のレーン ↔ `.claude/agents/*.md` の集合
- 図のサブプロセス ↔ skill
- システムレーンの工程 ↔ `settings.json` の hooks・スクリプト実体
- decision の停止点 ↔ `permissions` と skill 本文の停止指示
- 人間ゲートの数と位置

**優先度の列を空にしない。** 無ければ implement 側が順序を勝手に決める。
根拠は「何のために在るか」— 目的への効き方以外に優先度の根拠は無い。

## 4. 横断差分（全処理が終わってから1枚）

**処理ごとの図を見ていても絶対に気づかないもの**を、ここでだけ出す。

| 見るもの | 出し方 |
|---|---|
| **重複** | 同じ部品が2つ以上の処理の「使っている部品」列に出ている |
| **未使用** | 実ファイルに在るのに、どの処理の「使っている部品」列にも出てこない |
| **やり方の不一致** | 同じことを処理ごとに別々の方法でやっている |
| **人間ゲートの総数** | ハーネス全体で**オーナーが何回止められるか**。処理ごとに2回×5処理＝10回 |

**未使用は報告するだけ。削除はオーナーが決める。** 1回のタスクで使われないのが正常な部品もある。
引き継いだハーネスでは特に、使われない＝不要ではなく、こちらが踏んでいない場面のための部品かもしれない。
**「なぜ在るのか分からない」は報告の理由であって、削除の理由ではない。**

### 「不要」の処理はここまで実行できない

1節で「不要」と付いた処理の部品を、**必要な処理も使っていることがある**。
どれが共有かを持っているのは**この節の「重複」だけ**。だから順序が決まる:

```text
一覧の承認 → 必要な処理だけ理想図を育てる → 横断差分 → 「不要」行の部品を確定 → implement へ
```

## 5. `設計.md` に記録して終わる

置き場は `docs/harness/<ハーネス名>/設計.md`。
雛形: [`reference/設計.md.template`](../../reference/設計.md.template)

| 状態 | どうする |
|---|---|
| 無い（引き継ぎの既定） | **作る。** 処理一覧・理想図のリンク・差分・保留が入る最初の1本になる |
| 在る（自作の既定） | **「処理一覧」「理想図」「差分」の節だけを書き換える。他の節に触らない** |

**凍結した合格条件には絶対に触らない。** 満たす側が判定の線を動かせないことで機能しているので、
「整合させました」の名目で書き換わると、その線が裏口から破れる。
**触ってよい節を限定することが、凍結を守る唯一の形。**

### 終了条件

**全処理の一覧が承認され、必要な処理の理想図が承認され、横断差分が出て、設計.md に載ったら終わり。**
**⚠保留が残っていても終えてよい** — 保留ゼロを終了条件にすると、上限を置いた意味が消え、
オーナーに「とりあえず埋めておく」誘因が生まれて保留の記録価値が壊れる。

差分がゼロになるのは implement の仕事の終わりであって、改善の終わりではない。

## 書いてよい場所

**`docs/harness/` 配下と、自分が作った DrillSpark プロジェクトだけ。**
`.claude/` 配下は**読むだけ**。直すのは implement。

> **これは本文のお願いにとどまる。** このハーネス自身が「本文に『必ず通すこと』と書くだけだと破れる。
> 機械が必ず走る形にした」と書いているとおり、柵にはなっていない。確実にするには改善先の
> リポジトリに hook が要るが、**hook が無いのがこの工程の前提**。既知の弱点として残す。

| **承認ゲート** | **2つだけ** — ①処理一覧 ②各処理の理想図（差分は②の材料） |

利用者に見せるときは、この5語に必ず注釈を付ける

## 監査との違い

**理想図の差分（3・4節）は監査ではない。**

| | 何と何を比べるか | 誰が |
|---|---|---|
| **理想図の差分** | **まだ承認されていない**理想図 ↔ 実ファイル | 改善役（この工程） |
| **監査** | **承認済みの**図 ↔ 実ファイル | 評価役 |

区別を消すと、**評価役がまだ承認されていない下書きを基準に判定する**ことになり、
判定役の独立性が壊れる（オーナー判断 2026-08-22「監査は評価の工程」はこの線で保たれている）。
承認された瞬間に理想図は契約になり、そこから先の突き合わせは評価役の仕事。
