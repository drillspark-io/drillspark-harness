# harness-improve — ハーネスを直す

7つの工程のうち**〈改善する〉**。対応表は harness-implement と共有する
→ [MAPPING.md](../harness-implement/MAPPING.md)

> 本文の `8_2` `8_8` は、**このスキル自身を設計した DrillSpark 図のノード番号**。
> その図は同梱していないので読み飛ばしてよい。残してあるのは指示の出所を追えるようにするため。

## 図の自動同期はしない

実ファイルを直したら図も直す、という往復は**しない**。往復に不動点が無く、
どちらが正かを見失う（逆パースは把握用の使い捨てスナップショットであってソースオブトゥルースではない）。
だから最初に経路を決める。

## まず経路を決める（これを飛ばさない）

| 症状 | 経路 |
|---|---|
| 言い方が悪い・抜けを補いたい・同じ失敗を繰り返した | **A. ファイルを直す。図は触らない** |
| 工程が足りない・ゲートの位置が違う・役割の分け方が違う | **B. 図を1枚直して再生成** |
| **判定の線そのものを動かす**（評価基準・合格条件） | **C. オーナー承認を取ってから直す** |
| 直すものが無い | 何もしない。**素通りする** |

**【人間の実行】経路を選ぶのはオーナー**（`8_2`）。エージェントは症状と推奨経路を並べて**そこで止める**。
自分で選んで直し始めない — 経路の選択は「どこまで作り直すか」の決定で、影響範囲がまるごと変わる。
迷ったときの推奨は A。構造を触るのは、担当・順序・分岐が変わるときだけ。
**合格した回に無理に何かを直さない** — 教訓プールだけが膨らむ。

> **監査はこのスキルの仕事ではない**（オーナー判断 2026-08-22）。
> 図と実ファイルのズレを測って報告するのは**評価の工程**であり、改善は「直す」ことに専念する。
> 「直さない経路」を改善の中に置くと役割が濁る。監査の結果を受けて、どちらが正しいかを人間が決め、
> A か B か C を選んでからここへ来る。

## A. ワクチン（文言・教訓の追記）

その場のプロンプトで直さず、**環境側を強固にする**。直す先は該当する skill / agent / rules ファイル。

- 教訓は該当 skill の「教訓」セクションに1行
- 恒常ルールなら `CLAUDE.md` または `.claude/rules/<topic>.md`
- 検証基準の変更は `.claude/rules/` 側だけ。**生成側のファイルに基準を書かない**（verifier-deployment gap）

**貯めすぎない。** 教訓プールが5→100に増えると実使用精度は29.6%→3.3%に崩落する。
追記する前に、既存の行に統合できないか・古くなった行を消せないかを見る。

図は触らない。文言は元々図に載っていない（図に載るのは構造まで）。

## B. 構造の変更

1. **対象のドリルダウン1枚だけ**を `get_diagram` で取る（親図は読むだけ）
2. 直す。作図規約は `get_diagram_rules()` で確認する
3. `validate_diagram` で**保存せずに検証する**。ここで通してから保存すれば、
   構文ミスでバージョン履歴を汚さずに済む。
   ただし **`validate_diagram` は構文しか見ない**（2026-08-22 実測）。次は通ってしまうので自分で確かめる:
   - **タスクから複数の出力**（`4[..] -->|"A"| 5` と `4 -->|"B"| 6`）は規約違反。分岐は decision `{}` から出す。
     ノード数の上限で decision を足せないなら、**直列に組み替える**か2ノードを統合して枠を作る
   - **到達不能ノード**（database を後から足すと入力エッジを忘れやすい）
   - 差し戻しの**上限を超えたときの行き先**（上限だけ書いて行き先が無いと上限が無効）
   - **親図の備考との食い違い**（子を直したら親も読む）
   正規化後のコードが返るので、`⏱ N 分`・`click`・Theme Definitions が
   自動生成されること（＝自分で書かなくてよいこと）もここで確認できる。
   ただし `validate_diagram` はプロジェクト文脈を持たないため、
   ドリルダウンの有無に依存する `classDef drillDown` / `class N drillDown` は
   正規化出力に**現れない**。保存後には復活するので、消えたと勘違いしないこと
4. `update_diagram` で保存する。**全置換**なので注意:
   - 変更しない `%% note` `%% cost` `%% nodeStyle` `%% noteStyle` `%% subgraphStyle` を**再送する**。省いたものは消える
   - `%% rowOrder` と Theme Definitions は保存時に再生成されるので送らない
   - ノードIDを振り直したらメタデータも新IDへ移す（放置すると備考が迷子になる）
5. **読み戻す。** `get_diagram` で保存後の内容を確認する。
   success が返っても内容が巻き戻っていた実例がある。壊れていたら `list_versions` → `restore_version`
6. `harness-implement` を**その図に限定して**再実行し、詳細設計のゲートを通す

全体を作り直さない。1枚直したら、その図に対応する成果物だけが出直すのが正しい。

> 既に `settings.json` から参照されているスクリプトを直す場合は、**書く前に内容の承認**が要る
> （保存した瞬間から次の発火に効く）。→ harness-implement の「絶対に飛ばさない4点」1

## C. 判定の線を動かす（評価基準・合格条件）

**この経路だけは単独で進めない。** 評価基準（`.claude/rules/`）と〈設計する〉で凍結した合格条件
（`.claude/tests/`）は、**満たす側が書き換えられない**ことで機能している。
改善役が無審査で直せるなら、凍結した意味が消える。

1. **変更の差分をオーナーに見せて承認を取る**（図8 `8_8`）。何を・なぜ・どの評価結果を受けて
2. **「判定に落ちたから基準を緩める」向きの変更は却下される。** 基準が通らないときに動かすのは
   実装であって基準ではない。落ちた事実のほうが情報
3. 承認が下りたときだけ経路Aで直す。**承認できないなら直さずに終える**

基準そのものが目的とずれていた場合（〈目的を考える〉の成功指標から降りていない、測れない書き方になっている）は
基準を直す正当な理由になる。その場合も承認は要る。

## 監査（評価工程で行う）

図と実ファイルの**構造のズレ**は、改善の前に評価の工程で測る。見るのは構造だけで、
散文の言い回しの違いはズレではない。

- 図のレーン ↔ `.claude/agents/*.md` の集合（片側にしか無いものは？）
- 図のサブプロセス ↔ skill / ドリルダウンの対応
- システムレーンの工程 ↔ `.claude/settings.json` の hooks・スクリプト実体
- decision の停止点 ↔ `permissions` と skill 本文の停止指示
- 人間ゲートの数と位置（増減はハーネスの性格が変わったということ）
- **一度も使われなかったもの** — 呼ばれない skill・発火ゼロの hook・参照されない rules。
  評価は削る候補として報告するだけで、**削除はここでオーナーが決める**。
  1回のタスクで使われないのが正常な部品もあるので、報告＝即削除にしない

ズレが出たら、**図とファイルのどちらが正しいかを人間が決める**。
ファイルが正しければ経路A、図が正しければ経路B。ここで勝手に直さない。
