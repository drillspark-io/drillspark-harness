# harness-compose — 処理を束ねて1つのハーネスにする

工程のうち**〈統合する〉**（工程の全体は harness-implement が定義する）。対応表も harness-implement と共有する
→ [MAPPING.md](../harness-implement/MAPPING.md)

```text
在るものを数える → 衝突を洗い出す →［承認①］統合の方針
  → 1つしかないものを書く →［承認②］書き込む内容そのもの → 書き込んで読み戻す
  → 再起動を頼む → 統合.md に記録して終わる
```

**処理は `harness-implement` が1つずつ作る。1回の起動＝1処理で、セッションも別。**
だから**ハーネス全体を見る場所がどこにも無い**。それがこの工程である。

**このセッションで初めて全処理が1つの文脈に載る。** 作図の混入を避けるために分けた文脈を、
ここでは意図的に合流させる。**ただし合流させるのは「1つしかないもの」を決めるためだけ**で、
処理の中身を作り直すためではない。

## この工程の固有の仕事

**ハーネスに1つしかないものを1つにすること。** 処理ごとに書くと、2処理目が1処理目を上書きする。

| ハーネスに1つしかない | 処理ごとにある |
|---|---|
| `settings.json` の `hooks` と `permissions` | hook の実体（`.claude/hooks/<name>.js`） |
| `CLAUDE.md`（常時オン・目次・200行以内） | skill / agent / `paths:` 付き rule / スクリプト |
| 合格条件の置き場 `.claude/tests/<ハーネス名>/` | その処理の合格条件そのもの |
| 評価基準 `.claude/rules/<topic>.md` | その処理の図（1処理＝1 DrillSpark プロジェクト） |

### やらないこと

- **図を描かない・直さない。** `update_diagram` を持たない。図が要る直しは `harness-implement` へ戻す
- **凍結した合格条件の中身を変えない。** ここでやるのは**機械的な合併だけ**。
  1件でも書き換えたら、実装より先に凍結した意味がその瞬間に消える
- **処理ごとの skill / agent / rule を書き直さない。** 衝突は**報告して差し戻す**
- **評価しない。** GO / NO-GO は `harness-evaluator`

## 始める前に

**DrillSpark に繋がるか確かめる。** `mcp__drillspark__list_projects()` を1回だけ流す。
繋がっていれば何も言わずに進む。繋がらなければ止めて案内する
（→ [`reference/drillspark-setup.md`](../../reference/drillspark-setup.md)）。
統合そのものは図を書かないが、**介入点の照合で処理ごとの図を読む**ので必要。

**読むのは `docs/harness/<ハーネス名>/` のファイル一式。**

```text
設計.md                      索引。処理一覧と状態列を見る
処理/<処理名>/図.md           図のURL・キーと枚数・承認日・その図が宣言した介入点
処理/<処理名>/合格条件.md      凍結済み。集めるだけで中身に触らない
処理/<処理名>/実装.md          作ったものと箇所・統合へ渡す hook 定義の仕様・⚠ 推測・未完
統合.md                       この工程が書く先
```

**この工程は全処理のフォルダを読んでよい**（可視化も同じ）。作図の混入を防ぐための分離は
「描く側が前の処理を見ない」ためのもので、統合は描かないので当たらない。

**全処理が〈実装する〉まで終わっていること。** `設計.md` の処理一覧の状態列で見る。
**終わっていない処理があれば、そこで止めて聞く** — 除いて統合するか、そろうまで待つか。
勝手に除かない。除いた処理は**〈評価する〉の実タスク通しと過不足監査から丸ごと漏れる**。

## 0. 在るものを数える

**記憶で代用しない。** 数えるのは4つ。

| 数える | どこ |
|---|---|
| 処理の数と状態 | `設計.md` の処理一覧（索引） |
| 各処理の実装の記録（成果物・箇所・統合へ渡す仕様・⚠ 推測・未完） | `処理/<処理名>/実装.md` を処理の数だけ |
| 実ファイル | `.claude/skills` `.claude/agents` `.claude/hooks` `.claude/rules` `.claude/tests` |
| 図 | 処理ごとの DrillSpark プロジェクト（読むだけ） |

**記録にあってファイルに無いもの・ファイルにあって記録に無いもの**を両方向で数え、そのまま出す。
ここで直さない。片方向だけ見ると、落とした成果物か勝手に増えた成果物のどちらかを必ず見逃す。

## 1. 衝突を洗い出す

**処理ごとの図では絶対に見えない6点。** 1つずつ数えて表にする。

| 見るもの | 何が起きているか | 既定の扱い |
|---|---|---|
| **同名のファイル** | 2つの処理が同じ skill / agent 名を要求している | 中身が同じなら1つにする。**違うなら差し戻す** |
| **hook の重なり** | 同じイベント・同じ `matcher` に2本以上 | 実行順と、**片方が exit 2 したときの扱い**を決める |
| **権限の矛盾** | 片方が `deny`、片方が `allow` | **`deny` を勝たせる。** `allow` で上書きしない |
| **常時オンの肥大** | `CLAUDE.md` が200行を超える | skill か `paths:` 付き rule へ落とす |
| **用語の不一致** | 同じものを処理ごとに別の名前で呼んでいる | `設計.md` の用語に寄せる。**実装の綴りまで直すのは implement** |
| **人間の介入点の総数** | ゲートが多すぎて承認が連打になる | **数えて出す。減らすのはオーナーの判断** |

**介入点は5種すべてを数える**（起動・承認ゲート・実行・エスカレーション先・基準の決定）。
承認ゲートだけを数えると必ず落とす（→ MAPPING.md 2.1節）。
**処理ごとに妥当でも、合計すると1つの仕事で人間が7回止まる**ということが起きる。
これは統合の場でしか見えない。

**衝突の解消は3往復まで。** 決着しなければ**⚠ 保留**として記録し、オーナーへ報告して止まる。
勝手に4回目を試さない。会話で数えず、`統合.md` に何往復目かを書いて数える。

## 2.［承認①］統合の方針

**出すのは3つだけ** — ①決まったこと ②**守られない可能性がある点**（リスクの言葉で）
③判断してほしい1点。衝突の一覧そのものは `統合.md` に置き、CLI に流さない
（→ harness-implement〈出力の作法〉）。

**判断してもらうのは、既定の扱いで決められないものだけ。**
`deny` を勝たせる・同名で中身が違えば差し戻す、は既定なので聞かない。

## 3. 1つしかないものを書く

**依存順は、参照される実体が先、`settings.json` が最後。** 実体は各処理が作り終えている。

| 何 | どう書くか |
|---|---|
| `hooks` | 各処理が作った**実体を参照するだけ**。ここで実体（`.js`）を書かない |
| `permissions` | `deny` → `ask` → `allow` の順に見る。**`deny` は消さない** |
| `CLAUDE.md` | 常時オンにしてよいものだけ。目次にする。30行を超える手順は skill へ |
| 合格条件 | 処理ごとの `合格条件.md` が指すものを `.claude/tests/<ハーネス名>/` へ**そのまま**集める。<br>**凍結の単位はファイルなので、開いて中身を編集しない。**同名で当たるならファイル名に処理名を足して避ける |
| 評価基準 | `.claude/rules/<topic>.md`。**`CLAUDE.md` に置かない**（実装役が編集する場所だから） |

**合格条件は集めた直後に全部走らせる。** 集め方を間違えていないかは、走らせないと分からない。
落ちたら**実装を直す。条件のほうを直さない。**

## 4.［承認②］書き込む内容そのものを見せて止まる

**絶対に飛ばさない。** `settings.json` に**実際に書き込む JSON そのもの**を提示する。仕様の再掲ではない。
hook なら、イベント・`matcher` と `if` の2段・ブロックの終了コード・
**止めたとき Claude へ渡す文**まで含める。
「ダメです」だけ返すと Claude は別経路を探し始めるので、代わりにどうすればよいかを書く。

**hook は書いた瞬間から全操作に効く。** 書いてから見せるのでは遅い。

承認後に書き込み、**JSON パースと `/hooks` の登録を確認し、書いたものを読み戻す。**
成功メッセージを完了根拠にしない。

## 5. セッションの再起動を頼む

**【人間の実行】これは機械にはできない。** **書けた ≠ 登録された。**
再起動しないと skill・agent・hook が登録されず、
**書けたが動かないものを合格と数えたまま**〈評価する〉へ進む。

## 6. `統合.md` に記録して終わる

書くのは4つ — **何を1つにまとめたか / 衝突と決着（差し戻したものを含む） / ⚠ 推測 / 未完と⚠ 保留**。
置き場は `docs/harness/<ハーネス名>/統合.md`。雛形は
[`reference/設計.md.template`](../../reference/設計.md.template)。
これが `harness-evaluator` への入力になる。ここに無いものは測れない。

書いたら**保存を機械で確かめる。**「書き出した」は、書き出したつもりで終わっていても同じ言葉で報告できる。

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/file-saved-lint.js" docs/harness/<ハーネス名>/統合.md
```

次は〈評価する〉。**自動で連鎖させない。** オーナーが指示してから進む。

## 人間の介入点

| 種類 | どこ |
|---|---|
| 起動 | オーナーがこのスキルを呼ぶ。〈実装する〉から自動で続かない |
| 承認ゲート | ①統合の方針 ②`settings.json` に書き込む内容そのもの |
| 実行 | セッションの再起動 |
| エスカレーション先 | オーナー（衝突が3往復で決着しないとき／未実装の処理があるとき） |
| 基準の決定 | オーナー（権限の線と、人間ゲートを減らすかどうか） |

## 改善は harness-improve へ

統合で見つかった「重複している」「一度も使われない」は**報告するだけ**で、消すのはこの工程ではない。
削除は `harness-improve` でオーナーが決める。**1回の統合で使われないのが正常な部品もある。**
