# ハーネス設計のGO基準

`harness-design-reviewer` と `harness-evaluator` が判定に使う唯一の判定線。
両エージェントは記憶で判定せず、**起動のたびにこのファイルを読む**。

このファイルは **`harness-implement` / `harness-improve` が書き換えてはならない**。
基準を満たす側が基準を編集できると検証が意味を失う（verifier-deployment gap）。

**プラグインとして配られている限り、この防御は構造で保たれる。**
ファイルはインストール先（`<plugin-root>/reference/`）にあり、
作業対象のリポジトリの外なので、生成役が通常の編集で触ることがない。
基準を変えたいときはプラグイン本体へ PR を出す。
**「判定に落ちたから基準を緩める」向きの変更はそこで却下される。**

判定の対象は DrillSpark の図と、そこから生成された Codex の設定ファイル。
設計**時**の問いは [FRONTIER.md](../skills/harness-implement/FRONTIER.md) の網羅チェックリスト、
ここはレビュー**時**の判定線。時点が違うので、片方を他方の写しにしない。

## MUST（1つでも欠けたら差し戻し）

### 作図

- 数値ID / 二重引用符ラベル / 全ノードに `%% duration`
- process 系ノードが **5〜15**（10までが目安。document・database は数えない。上限15は設計判断 — 分かりやすさのための追加を上限で阻まない）
- 実線 `-->` は同一レーン内、点線 `-.->` は**レーンを跨ぐときだけ**
- 分岐は decision `{}` から出す。**タスクから複数の出力を直接引かない**
- Start / End が各1つ。到達不能ノードと出口の無いノードが無い
- decision は疑問形、task は「動詞＋名詞」
- **制御フローがデータ系ノードを貫通していない。** document / database は読み書きの対象であって
  手順ではない。Start の唯一の後続がデータストア、のような形は経路を通さず脇へ寄せる
- 数値ID・二重引用符ラベル・duration・多出力・到達性・レーンと線種・ID の重複は
  `node "<plugin-root>/scripts/diagram-lint.js" <file>` が機械で見る。**目視で数え直さない**

> **決着済み — 指摘しない**: レーン名を担当者にする必要はない（設計判断）。
> 工程名のレーンを規約違反として挙げないこと。承認済みの図のノード名の改名も提案しない。

### 構造

- **全ループに上限回数とエスカレーション先がある。** 上限だけあって
  「超えたらどこへ行くか」が無いものは不合格 — 上限が実質的に無効になる。
  ただし**上限ラベルが要るのは「同じことをやり直す」ループだけ**。次の2つは対象外:
  **件数で終わる反復**（「残っている工程は?」→次の1枚へ。件数が減るので必ず止まる）と、
  **人間が毎回判断するループ**（人間ゲートの「続ける」経路。止めるのは人間）。
  この線引きが無いと、健全な反復まで差し戻し対象に挙がる
- **人間の介入点5種**（起動 / 承認ゲート / 実行 / エスカレーション先 / 基準の決定）が
  図のどこにあるか明記されている。1つも無いなら「無し」と書いてある。
  **書いていないのと「無い」と書いてあるのは違う**
- **宣言の単位は図1枚**（設計判断）。ドリルダウンも自分の分を Start の備考で宣言する。
  親が代弁していても省かない。再適用は**該当ドリルダウン1枚だけ**を取って直す運用なので、
  1枚で読めないと運用と噛み合わない
- **起動は各工程の Start に存在する**（設計判断）。工程は自動で連鎖せず、
  1工程ごとにオーナーが次を指示する。承認ゲートを通ったことは「次を始めてよい」ではない。
  ドリルダウンは親工程の内側なので別途の起動を持たない（その旨を明記する）
- **親子の備考が食い違っていない。** 子を直して親が古いまま、が最も起きやすい
- **工程の混入が無い。** その工程でまだ手元に無い成果物への操作が書かれていない
- **工程ごとの出力が図にある。** 各工程に document ノード（備考に生成先パス）があるか、
  備考に「出力: 無し」と書いてある。書いていないのと「無い」と書いてあるのは違う
- **次の工程の入力になる成果物には、書いた側と別レーンの検査ノードがある**か、置かない理由が `図.md` にある。
  実装では書き込み道具を持たない agent になっている

### 検証の独立性

- 生成役と検証役が**別インスタンス**（エージェントは自分の成果物を自信を持って称賛する）
- 判定基準が、それを**満たす側から書き換えられない場所**にある。
  評価基準は所有者が管理する領域に置き、生成役が通常編集しない構成にする。AGENTS.mdへ混ぜない。実際の書込制限を確認する
- 決定論で判定できる**合格条件**があり、そのまま実行できる形（実行コマンドまで書いてある）
- 合格条件が**実装より先**に書かれ、承認で凍結されている

### 実装

- [Codex対応表](MAPPING.md) の形式で構文検査し、新規セッションでスキル/agent/hookの読込と起動を確認済み
- hooks.jsonはJSON、config.tomlとagent定義はTOMLとしてパースが通る
- hook は**通す入力で exit 0、止める入力で exit 2** の両方を確認済み
- skill 本文の各工程が、前の工程の出力ファイルの有無を機械で確かめてから始まる（落ちたら前の工程へ戻る）

### 目的の達成（〈評価する〉で測る）

**このハーネスの成功指標は `docs/harness/<ハーネス名>/設計.md` の1節が持つ。**
基準はここで発明せず、そこから降ろすだけ。降ろした結果が次の1行:

- **人間の介入点の数え落としが0件。** 図の介入点5種と実ファイルの実装を突き合わせ、
  片方にしか無いものが1つでもあれば**不合格**。実際に数え落としが起きた項目で、
  落ちるとエージェントが人間に断らずに外へ出る

以下は**記録するが差し戻さない**（傾向として版ごとに並べる）:

- 図とファイルの構造ズレの件数
- レビュー役の MUST 指摘件数（版を追って減っているか）
- **ハーネス無しとの差** — 同じ図を素の Codex に渡した場合と、介入点5種を何点数えたか /
  ループに上限とエスカレーション先を書いたか / 判定基準を生成側が書けない場所に置いたか、で比べる。
  ベースラインは図ごとに1回取れば再利用してよい（図を直したら取り直す）

**差が縮んだら合格ではなく引き算の合図。** モデルが自力でできるようになった部品は削る。

## NICE（指摘はするが差し戻さない）

- 備考が手順だけで、**なぜそのノードがあるか**が読み取れない
- 同じ根拠が複数の図に重複している（片方だけ直すとずれる）。
  ただし**人間の介入点の宣言は例外**で、親子で重複してよい。これは削るべき重複ではなく
  **照合のための冗長性**である。図の宣言と `設計.md` の表と実ファイルを
  三点で突き合わせて初めて表の抜けが見つかる。宣言を1箇所に減らすと二点照合になり、
  「どちらにも無い」で一致してしまって落ちたこと自体に気づけなくなる
- 親の所要時間と子の合計の不一致（規約上の要件ではない）
- ID の欠番、流れの順序と ID 順の乖離

## 判定の書き方

- **称賛を書かない。** 「よくできている」「適切です」は1行も要らない
- 各指摘に**どのノード・どの基準・放置するとどうなるか**を付ける
- **推測で埋めない。** 判断できないものは「判断できない」と書く
