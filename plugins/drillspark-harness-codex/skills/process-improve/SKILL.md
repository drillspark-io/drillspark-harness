# 業務を棚卸しして改善する

最初に [実行規約](../../reference/runtime.md) と [共通手順](../../reference/workflow-contract.md) を読む。
MCP接続を確認し、既存の `業務改善/` を読んで再開する。情報がある項目は聞き直さない。
表の形式は [表の雛形](../../reference/business-improvement-tables.md)、
判定は [評価基準](../../reference/business-improvement-criteria.md) を読む。

1. [Sites入力画面](../../reference/inventory-sites.md) を読み、Sitesが利用可能なら同梱フォームを使う。
   最初に区切り文字付きの表をチャットへ入力させない。入力画面のURLを渡し、入力完了を待つ。
   最初は業務名・担当・頻度と時間・実測/未計測・目的だけ。開始条件・作業・道具・渡し先は
   改善対象に選んでから聞き、それまでは「後で聞く」とする。聞いた相手は実際の回答者を記録する。
   Sitesが使えない場合だけ、質問UIまたは会話で一問ずつ聞く。件数の下限や表の書式を要求しない。
   未確認は相談先付きで保存。利用者に一覧を確認してもらい、確定前に作図へ進まない。
2. `node <plugin-root>/scripts/process-abc.js 業務改善/業務一覧.md` で月間時間を計算し、
   改善対象を利用者と決める。未計測の時間を実績や保証された削減効果として扱わない。
3. `process-expert` を別エージェントとして起動して段階の案を得る。一般論は一般例の印を保持。
   get_diagram_rulesを取得し、現状の工程だけを第一階層に描く。create_project直後にURLを
   業務一覧の「図の在りか」へ記録してからupdate_diagramを使う。工程を利用者に確認する。
   次に工程ひとつの作業を第二階層に描き、その都度確認する。一度に全階層を生成しない。
   diagram-lintとvalidate_diagramを通し、process-coverageで工程の抜けを検査する。
4. 成功の形を定め、ECRSの順で一問ずつ検討する。改善後は別の図を作り、そのURLを
   同じ業務の「図の在りか」に `改善後:` として記録する。現状図を消して置換しない。
   改善案を担当（人/AI）と優先度で整理し、効果の数値には根拠と実測/未計測を添える。
5. AI化依頼書へ表の定義どおりH1–H5・承認する操作・保留と相談先を記録する。
   承認要否の判断は利用者に聞く。依頼書をもって自動化の実装依頼とは扱わない。
6. `process-improve-reviewer` を別エージェントで起動し、4つの表と図を独自に読ませる。
   指摘と修正回数を記録し、基準を緩めず修正する。合意できない点は保留と相談先に戻す。
   保存とlintを確認して、何をAIに任せるか、どこで人が判断するか、次の依頼を利用者へ渡す。

出力先は業務改善/業務一覧.md、改善案.md、AI化依頼書.md、保留.md。
業務一覧と依存する他の表は別パッチで更新する。各保存後にfile-saved-lint、表にはprocess-table-lint。
HTMLの改善計画は別の `process-improve-view`。次の業務・設定生成は利用者の依頼で開始する。
