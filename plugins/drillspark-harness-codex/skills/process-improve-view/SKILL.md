# 改善計画を1枚にする

[実行規約](../../reference/runtime.md)、[共通手順](../../reference/workflow-contract.md)、
[表の雛形](../../reference/business-improvement-tables.md) を読む。
業務改善/ の業務一覧・改善案・AI化依頼書・保留を読み、対象業務を1件に絞る。
全部無ければ棚卸しを案内する。一部不足は理由付きで表示し、創作して補わない。
対象が曖昧な場合だけ担当・きっかけ・時間を添えて選んでもらう。「該当なし」を認める。

1. 一覧の「図の在りか」の最初のURLから現状図を取得する。改善後URLはリンクとして添える。
   取得失敗は日時・対象・試行・返答・次の操作を平易に書き、図の代わりに置く。
2. `業務改善/改善計画-<業務名>.html` を作る。CSS/JSを内包し、外部読込を持たない。
   data-blockの8値は `成功の形`、`図または取れなかった経緯`、`改善案`、`誰がやるか`、`優先度`、`ECRSのどれか`、
   `AI化依頼書`、`保留`。実際の許容値はprocess-plan-lint.jsを確認して使う。
   表の順序を維持し、工程と改善案を結び、未確認/一般例を本文と同じ強さで示す。
   不足ブロックは理由付きで残す。仕事の目的「不要」は「なくす候補（本人申告）」と表示する。
   「この計画は業務の手順を見直すためのもので、担当者の評価には使いません」を添える。
3. apply_patchで保存する。process-plan-lintを実行し、失敗箇所だけ修正する（最大3回）。
   上限で不合格なら未完として返す。lintを無効化して保存を強行しない。
4. file-saved-lintと読み戻しで確認し、ローカルファイルへのリンクを渡す。

同じ業務は同じファイルを更新する。新たな合否判定・作図・業務の並べ替えはしない。
依頼されたローカル資料作成から外部公開へ自動で進まない。
