# フロンティア洗い出し — 図が決めていないことを潰す

図は**構造しか持たない**。「何が・誰から誰へ・どの順で」までで、
文言・上限・権限・宛先・パス規約・強制の在処は載らない。
**そこを黙って仮定すると、仮定した箇所がそのまま欠陥になる。**

## 進め方

1. **決定木として扱う。** 前提がすでに決まっている問いだけが「フロンティア」。
   ある問いの答えが同ラウンドの別の問いに依存するなら、それは**次**のラウンドの問い
2. **フロンティア全部を1ラウンドで出す。** 1問ずつ聞かない。番号を振り、各問に推奨回答を付ける

   ```
   ❓ Q1 — <見出し>: <本文。選択肢があれば列挙>
   ➡️ 推奨: <答え> / 理由: <なぜ> / 逆を選ぶと: <何が起きるか>
   ```

   **推奨には必ず「逆を選ぶとどうなるか」を付ける。**
   推奨だけ並べると「同意・同意・同意」で流れ、長いのに何も決まっていない状態になる。
   **これがこの手順の最大の失敗モード**
3. **事実を調べるのは自分の仕事。ユーザーに聞かない。**
   リポジトリ・既存スキル・設定ファイル・ドキュメントで分かることは調べる。
   調べられないものだけ聞く — オーナーの私的情報・組織の方針・まだ決めていない運用
   - 例: 記事の文字数の閾値が既存 skill の本文に書いてあるなら調べて済ませる。
     記事に出してはいけない社名はどこにも無いので聞く。**この線引きが正しい**
4. **調査で止まらない。** 調べ物はサブエージェントに投げ、その結果に依存する問いだけ次ラウンドへ回す。
   残りのフロンティアは先に聞く
5. **フロンティアが空になったら終わり。** 空＝黙って仮定した枝がゼロ。
   ここまで来てから合格条件を書く
6. **紙で答えが出ない問いは作って見る。** 「レーンを2つに割るべきか」「lint はうるさすぎないか」は
   議論では決まらない。dry-run して現物で判断する

## 観点の借り方 — 専門家のフレームワークを網として使う

候補出しと抜け探しを白紙からやらない。**確立したフレームワークを観点の網として重ねる。**
用途はそこまで — **合否には使わない**。「◯◯を使ったか」を判定基準に入れると手段が目的化する。
`reference/harness-design-criteria.md` はこの節の都合で動かさない。

| 工程 | 借りる観点 | 使い方 |
|---|---|---|
| 目的を考える | **SMART**（具体・測定可能・達成可能・関連・期限つき） | 成功指標の**案を出すときの形**。合否の線（MUST）を1〜2本に絞る規約と Goodhart 対策（満点でも未達になる型を1つ書く）はそのまま |
| 処理の種類を考える | **SIPOC**（供給者・入力・処理・出力・顧客） | 5観点の抜け探しに重ねる — 入口＝供給者＋入力、出口＝出力＋顧客。見つけたものは**5観点の欄に書く**。表を二重にしない |
| 処理を作る（レーン） | **RACI**（実行・説明責任・相談・報告） | レーンは R（実行する者）で切る。A（説明責任）が人間なら承認ゲートの候補。C・I はレーンにせず備考へ |
| 改善する | **ECRS**（なくす→まとめる→並び替える→簡単にする） | 担当は `harness-improve` ／業務側は `process-expert`（[`agents/process-expert.md`](../../agents/process-expert.md)）。S を先に出すと不要な作業の高速化になる — 順序が本体 |

**フレームワークから出た候補は「一般例」の扱い。** 実物（リポジトリ・既存設定・オーナーの答え）で
裏が取れるまで事実にしない。`process-expert` が一般論から補った箇所に印を付けて返すのと同じ規約 —
流暢に埋まった一般論は、空欄と違って気づかれないまま定着する。

## 網羅チェックリスト（ハーネスは必ずこれを持つ）

図に書いていないなら、書いていないこと自体が答えではない。**フロンティアの問いにする。**

| # | 観点 | 落ちていたときに起きること |
|---|---|---|
| 1 | **人間の介入点**（MAPPING.md 2.1 の5種） | エージェントが勝手に外に出る |
| 2 | **強制の在処と置き場** — お願いか、フックか、権限か。常時オンでよいか（MAPPING.md 3.1） | 仕組みを作ったのに誰も起動せず、実質ゼロ。置き場を誤ると全セッションのトークンを食う |
| 3 | **ループ上限とエスカレーション先** | 出口の無い修正ループ。宛先未定義だと「人間へ」が誰にも届かない |
| 4 | **権限** — 何を禁止し、何を確認させるか | 検証基準を被検証者が書き換えられる |
| 5 | **検証基準の置き場所と、合格を決定論で判定できる形にしたか** — テストデータはどこに置き、何をもって通ったとするか | 決定論に落とさないと、評価が「動いたように見える」の報告になる |
| 6 | **成果物のパスと命名規約** — `設計.md` は `docs/harness/<ハーネス名>/設計.md`、テストデータは `tests/harness/<ハーネス名>/`、工程ごとの出力は図の document ノードの備考にある生成先パス | フックの `if:` 条件が書けない。評価役が物差しを見つけられない。出力先が無い工程は会話に出力を置き、次の工程に渡らない |
| 7 | **失敗時の挙動** — 止まるか、続けるか、誰に言うか | 黙って続行して被害が拡大する |
| 8 | **起動方法** — 手動か、自動か、何をトリガに | 自動化前提の設計を手動運用してしまう |
| 9 | **外に出る操作の実行手段** | 業務上の承認とCodexの操作許可（対応表を参照） のルールが書けない |
| 10 | **教訓の置き場所と上限** | 教訓プールが膨らみ実使用精度が崩落する |
| 11 | **処理と工程を混同していないか** | 工程が壊れる。一覧しか無いのに作図の操作を書くなど |

## 工程の混入

処理と工程の定義 → [MAPPING.md](../../reference/MAPPING.md) 1節。混ぜると工程が壊れる。

各図は**自分の工程の話だけ**をする。書き終えたら、前後の工程の操作が混じっていないか読み返す。

- **例1**: 「処理の種類を考える」に「階層を1つ足す」「1図5〜10処理に収まる?」が入っていた。
  階層もレーンも**作図の操作**で、この工程ではまだ矢印を引いていない。
  同じ図の別ノードに「まだ矢印は引かない」と書いてあり、自己矛盾していた
- **例2**: 上を直した直後、**親図の備考が古いまま残って**子図と食い違った。
  子を直したら親の備考も見る

見分け方は単純で、**そのノードの動詞が、いまの工程の成果物に対して実行できるか**。
手元に一覧しか無いのに「階層を足す」「レーンを切る」と書いてあれば混入している。

**このチェックリストは、実際に落とした穴から作られている** —
lint を実装したのに起動する仕組みを決めておらず、人間の介入点も数え漏らしていた。
