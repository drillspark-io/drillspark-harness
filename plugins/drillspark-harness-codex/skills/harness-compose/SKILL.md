# Codexハーネスを統合する

[実行規約](../../reference/runtime.md)、[共通手順](../../reference/workflow-contract.md)、
[対応表](../../reference/MAPPING.md) を読む。接続を確認し、全処理の図と成果物を読む。
未実装の処理を勝手に除かない。除外の指示がなければ不足として利用者へ返す。

1. 設計.md、処理ごとの図.md/合格条件.md/実装.md、実ファイルを両方向で照合する。
2. 同名ファイル、hookの重複、権限の矛盾、常駐指示の肥大、用語、介入点5種の総数を整理する。
   同名で内容が異なる実体は実装へ差し戻す。制限を黙って削らない。
   複数フックは並行起動するので順序依存を設定の並び順で表現しない。
   衝突解消は最大3往復。未決は統合.mdへ保留として記録する。
3. 既存AGENTS.md、.codex/config.toml、.codex/hooks.jsonを読む。
   個人の秘密値を取り込まず、既存の無関係な設定を保持する差分を作る。
   hooks.jsonの合流案は `node <plugin-root>/scripts/merge-codex-hooks.js <既存JSONのパス|-> <追加案JSONのパス>`
   で作れる。これは表示だけで書き込まない。同じ追加案は重複せず、既存の検査を保持する。
   TOMLはこのJSON用スクリプトに渡さず、構文対応の編集・パーサーで別に扱う。
   AGENTS.mdは短い索引、skillへの参照を中心にする。テストはtests/harness/<name>/へ改変せず集める。
   フックは各処理が作った実体への参照だけ。統合時に実体の仕様を変えない。
4. 方針上未決の判断と、実際の設定差分を利用者に示す。承認範囲を記録し、回答前に適用しない。
   書込後はJSON/TOMLの構文検査、読み戻し、凍結テストを行う。
   パーサーが無いときは構文検証未実施を記録し、有効化確認を省略しない。
5. 統合.mdへ合流したもの・衝突と決着・根拠・未完を保存し、file-saved-lintで確認する。
   新規セッションのスキル/agent読込、/mcp、/hooksの信頼と発火は利用者と実測する。

この工程は図や処理別実装を作り直さない。設定を書けたことと利用可能になったことは別。
次は別エージェントのharness-evaluator。実機確認が済んでいなければ未検証として引き渡す。
